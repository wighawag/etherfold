A terminated worker can wedge one IndexedDB database for ever

Summary. If a dedicated worker is terminated while it has BOTH a readwrite and a readonly transaction in flight on the same database, that database can be left permanently unable to run any transaction at all. indexedDB.open keeps succeeding, and every transaction taken on the resulting connection then hangs for ever: no complete, no abort, no error. It affects readonly transactions as much as readwrite ones, in the page as well as in any later worker. Other databases in the same origin are unaffected. A page reload does NOT clear it, and a deleteDatabase issued afterwards never completes, so a web application has no recovery available to it.

Reproduces on: WebKit only, and on real hardware, not just a test build.

  • iPhone 12, iOS 18.3.2, Safari 18.3.1: 12 wedged in 200 (6%), foreground tab, this page, over plain HTTP on a LAN address.
  • Playwright 1.62.1 WebKit on Linux (build 2359, user agent Version/26.5): 7–13 in 200 across runs.
  • Playwright Chromium 141: 0 in 200. Playwright Firefox 145: 0 in 200.

So it is present both in a shipping iOS release and in a much newer upstream build, on two different ports, which suggests cross-platform code rather than one port's plumbing.

It needs two transactions in flight in the DYING context. One transaction alone never does it, whatever shape it has and wherever the kill lands (0 in 200). Two overlapping readwrite transactions do not do it (0 in 200). An overlapping readonly belonging to a context that SURVIVES the kill (the page, on its own connection) does not do it either (0 in 200). It is specifically a readonly and a readwrite of the terminated worker, overlapping at the moment of terminate().

Steps

  1. Serve this directory over HTTP (IndexedDB needs a real origin): python3 -m http.server 8000.
  2. Open http://localhost:8000/ in Safari and press Run.
  3. Each iteration starts a worker that opens a fresh database with two object stores, runs a loop of one-put readwrite transactions on one store and a loop of get readonly transactions on the other, and is terminated by the page at a random point. The page then opens that database and asks for a single readonly transaction.
  4. A WEDGED line is a database on which that transaction never settled within 4 s. Expect a few percent. Each wedged line then confirms that an unrelated database is healthy and that a same-page reload does not recover the wedged one.

If you are running this on a phone, read this first

  • Keep this tab in the foreground and the screen awake. A backgrounded page is SUSPENDED, and IndexedDB after suspension is a different, already-reported problem (WebKit 197050, 202705). The run below detects being hidden and marks its own result as contaminated, so a wedge seen after a backgrounding proves nothing.
  • Use a normal tab, not a private one.
  • This deliberately leaves unusable databases behind on this origin, and they cannot be deleted from script (that is the bug). To clean up afterwards: Settings → Safari → Advanced → Website Data, and remove this site.
