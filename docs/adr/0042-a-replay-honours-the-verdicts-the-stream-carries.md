# A replay honours the verdicts the stream carries, and rebuilds the window by walking it

A stored event stream is an EMISSION stream: it already records what was applied and what was taken back, at the original block, flagged `removed`. A FETCH is the opposite kind of input: a complete re-read of a block range that carries no verdicts at all, from which the engine DERIVES every retraction by comparing the cursor's unconfirmed window against the incoming blocks. Those two were routed through one function, `generateStreamToAppend`, and a rebuild off a cached stream is exactly the case where that is wrong: a rebuild starts from a fresh cursor whose window is EMPTY, so there was nothing to derive a retraction from, and `groupLogsPerBlock` drops the `removed` events out of what it is handed. A stream containing a reorg therefore replayed as BOTH branches applied as live blocks with no revert anywhere, which the entity store refuses (`block 104 is already recorded`) and which is silently wrong state derived partly from a dead branch on any path that tolerates the double-apply.

We decided that **the IN direction splits on the KIND of the input, at the entry**: `IndexerGeneration.feed()` takes a fetch and derives the verdicts; `IndexerGeneration.replay()` takes a stored stream and honours the ones it carries (`generateStreamFromReplay`). This is the missing half of a distinction the OUT direction already makes (`groupLogsPerBlock` for logs coming in from a fetch, `groupStreamPerBlock` for the stream going out to a processor), so the vocabulary is the one already in the code rather than a new axis. `feed()` now REFUSES a batch carrying `removed` markers, naming `replay()`, on the same ground `assertWellFormed` refuses one on the wire: a caller that ships verdicts to a function that derives them has to be told, because the failure mode is silent.

## Considered options

- **Teach `generateStreamToAppend` to accept a stream** (a flag, or sniffing for a `removed` marker). Rejected: that function's whole contract is "a complete range plus a window decides what changed", and every line of it, the by-NUMBER matching, the absence-versus-contradiction cause, `startingBlockForNewEvent`, is about a range it can re-read. A replay decides nothing; it obeys. Two contracts in one function is how this defect existed in the first place, and sniffing would make the behaviour depend on whether the data happened to contain a reorg.
- **Loosen `groupLogsPerBlock` to keep `removed` events.** Rejected, and it is the tempting one-line "fix". That function is the FETCH rule, and a `removed` marker arriving from a stateless `eth_getLogs` means the fetch is not what it claims to be. Loosening it would make a wire batch carrying forged retractions apply them, and ADR-0004 puts every reorg decision on the receiver.
- **Store `unconfirmedBlocks` in the stream keeper again.** Rejected: ADR-0035, as amended, deleted that copy deliberately because nothing read it, and a keeper's window is the wrong home anyway, since a stream can be replayed into a cursor that is not the one that wrote it. The window is DERIVABLE from the stream, which is why it was droppable.

## Consequences

- **The window a replay leaves behind is reconstructed by WALKING the stream, not by filtering it.** An applied block enters the window, a retracted block LEAVES it, and the finality prune happens once at the end against `lastToBlock`. Filtering out the `removed` entries instead, which is the obvious shortcut, leaves BOTH branches of a reorg in the window at one height. That is a window no live run ever held, and the next tip cycle then applies the replacement block a SECOND time. That second symptom is the same defect, and it is why "emit the right stream" was not a sufficient fix.
- **The walk is keyed by block HASH.** A hash names one block; a height names whichever branch won, which is the thing under dispute. It is also what DE-DUPLICATES the catch-up shape of a replay (a kept state whose stream is ahead re-offers the finality window it reached back over): a block already in the window is skipped rather than applied twice, which is the same job `startingBlockForNewEvent` does on the fetch path.
- **ADR-0035's amendment still holds, with one word moved.** It says the window is "rebuilt from the replayed events by `generateStreamToAppend`". The property is unchanged, no keeper stores the window and none needs to, but the function that rebuilds it on the REPLAY path is now `generateStreamFromReplay`.
- **`groupStreamPerBlock` groups CONSECUTIVE runs** rather than keying a map over the whole list. Grouping a whole stored stream by `{removed, hash}` folds a re-application of the same block (the chain went A, then B, then back to A) back into the first group, delivering it before the retraction it undoes. A run is one emission, which is the unit the stream is written in.
