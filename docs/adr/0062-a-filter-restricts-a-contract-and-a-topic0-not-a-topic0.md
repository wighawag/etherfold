# A filter restricts a (contract, `topic0`) pair, not a `topic0`

`LogParseConfig.filters` is a LIST of rules (`FilterRule`: an `event`, an optional `contracts` scope, and a `match` of positional `ArgumentFilter` entries OR-ed together) rather than a map keyed by event NAME, and a rule restricts the `topic0`s it reaches AT THE ADDRESSES IT NAMES and nowhere else. Every address a rule did not reach is collected into a LEFTOVER request that asks for that `topic0` unfiltered: AN ADDRESS NOBODY FILTERED IS NOT FILTERED. Everything a rule cannot mean is REFUSED at construction with a stated remedy.

The old shape could not express its own primary use case. A filter was keyed by NAME, applied to every contract declaring that name, and REMOVED the `topic0` from the shared request entirely, so "filter the NFT's `Transfer`s and leave the ERC-20's alone" was inexpressible even in principle. Its element type carried no `null`, so the wildcard `eth_getLogs` defines was unwritable and "Transfers TO me" -- a constraint on the SECOND indexed argument, and the single most obvious client-side filter there is -- was unwritable with it (`work/notes/findings/topic-filters-cannot-express-the-null-wildcard.md`; both call sites in this repository carried an `as unknown as` cast). And one name can cover two `topic0`s (two versions across an upgrade) or, since ADR-0061, one `topic0` with two decoding shapes at two addresses, so a POSITIONAL filter under one name meant different things at different addresses.

## What a filter restricts, and what a leftover is

Per live `topic0` T the planner emits one request per (rule targeting T, entry in that rule's `match`), scoped to that rule's addresses, with topics `[T, ...entry]` and trailing wildcards trimmed. It then computes the addresses that DECLARE T minus the union of addresses covered by rules targeting T, collects those (T, leftover) pairs, groups them by address SET, and emits one request per group with that group's `topic0`s NESTED as an OR list in slot 0. A `topic0` no rule mentions at all is UNSCOPED and joins the group holding the whole source, so with no rule configured the planner emits exactly one request over every address with every `topic0` nested in slot 0: byte for byte what the no-filter path always produced, pinned by test.

Emitting more requests is always safe for correctness, because `getLogsWithVariousFilters` unions and de-duplicates them; it costs round trips and nothing else. That is what makes the leftover affordable, and it is why the honest answer to "this rule reaches an address it should not" is a second request rather than a narrower one.

## Filters stay POSITIONAL, and named-argument filters were REJECTED

A named filter (`{from: me}`) reads better than `[me, null]` and was rejected anyway, because argument NAMES are not canonical across real ABIs. WETH9, the most deployed ERC-20 there is, declares `Transfer(address indexed src, address indexed dst, uint wad)`, so a rule written as `{from: me}` matches nothing there while an identically-meant rule against OpenZeppelin's `Transfer(address indexed from, address indexed to, uint256 value)` matches everything. That breaks on exactly the mixed ERC-721-plus-ERC-20 source that motivated ADR-0061, and it breaks by SILENTLY MATCHING NOTHING rather than by erroring, which is the failure class this whole area exists to avoid. Names are also the part of an ABI a recompilation can move without moving `topic0` at all, which is precisely the asymmetry ADR-0034 rests on: the fetch filter is a function of types and `indexed` flags, and the decode is a function of names. A filter is a FETCH concern, so it may not depend on the half of the ABI the fetch is deliberately blind to.

The residue is accepted rather than denied: a positional filter is harder to read, and an author has to count indexed arguments. `null` is what makes counting possible at all, and R4 turns a miscount into a refusal that names the count.

## One `event` field carries both a NAME and a canonical SIGNATURE

A Solidity event name is an identifier and can never contain `(`; a canonical signature always does. So `event` is read as a SIGNATURE if and only if it contains `(`, and no second field, no tagged union and no `eventSignature` sibling is needed. A NAME covers every `topic0` it declares, which is what a filter that should follow an upgrade wants; a SIGNATURE covers exactly one, which is what a filter that should not wants. The comparison against a signature is STRICT byte equality with `canonicalSignatureOf` (viem's `toEventSignature`, which emits no spaces): there is deliberately no lenient canonicaliser, no `uint` alias and no whitespace tolerance, because every leniency is a second spelling of one filter and therefore a second stream identity to reconcile. A near miss is refused naming the canonical signatures that DO exist for that name, which is the whole cost of the strictness paid back at the point of the mistake.

## The refusals, and why refusal

Eight, all at construction, all naming a remedy: R1 an `event` the source declares nothing by; R2 an address in `contracts` declaring no matching event; R3 a `topic0` the rule reaches whose scoped declarations carry more than one `decodingShapeOf`; R4 a `match` entry deeper than that shape's indexed-argument count; R5 an empty `match`, an empty entry, or an all-null entry; R6 `contracts` on an address-less source; R7 an `event` containing `(` that is not byte-equal to any declared canonical signature; R8 an `event` resolving only to anonymous declarations, which carry no `topic0` (anonymous declarations are ignored during resolution, so this arrives at R1's refusal carrying its own sentence).

The two alternatives are both silent, and each is a known failure class. SILENTLY WIDENING (ignore the part of the rule that does not fit) hands back a superset stream nobody asked for, at a stream identity that claims to be the filtered one. SILENTLY NARROWING (drop the part that does not fit) unrequests logs, and afterwards nothing distinguishes "the chain had none" from "we never asked" -- the absence-versus-never-asked failure ADR-0031 exists to prevent, and the same shape as `absence` versus `contradiction` in the reorg model. A refusal at construction cannot be mistaken for either. R3 is the sharpest case: it is the ADR-0061 tolerated collision meeting a filter, which ADR-0061 recorded as an inherent hazard, and it becomes a MISCONFIGURATION WITH A REMEDY ("add `contracts` to scope this rule to one of them") rather than a quiet result. Each of these is content to be relaxed later on evidence; none of them may be relaxed into silence.

## Stream identity moves only for deployments that set filters

`parse` is hashed into `streamDigestOf` on the strength of `filters`, so the rules are CANONICALISED inside `resolveStreamConfig` before anything hashes them, exactly as an unset `finality` is defaulted there: rules and `match` entries sorted and de-duplicated (both are SETs, since the OR is commutative), `contracts` normalised through `normalizeAddress` and sorted, trailing wildcards trimmed, an empty rule list dropped. Two authored spellings of one meaning are therefore ONE stream, and reordering two rules -- which changes not a single request -- does not fork a stream and re-fetch a history. What is deliberately NOT canonicalised is `event`: a NAME and the canonical SIGNATURE it happens to cover today stay two streams, because resolving one into the other needs the SOURCE, which a config normalisation does not have, and because they are different intents anyway.

A config with `filters: undefined` hashes IDENTICALLY before and after this change, pinned by a literal digest in `packages/core/test/streamIdentity.test.ts`, so nobody who does not use filters re-fetches anything. For anyone who does, the digest moving is correct rather than collateral damage: the commit before this one establishes that a stream fetched under the old shape was missing every event that had no filter, so it has to be rebuilt regardless.

## Consequences

`filters` had exactly one consumer in this repository and it is migrated in the same change, with its `as unknown as` cast deleted; the cast disappearing is the evidence the new type is right. `ExtraFilters` is a LIST rather than a map keyed by `topic0`, because two rules can now target one `topic0` and a map could hold only the last of them. `RangeLogFetcher` no longer forks on `if (this.conf.filters)`: there is ONE planner and the unfiltered case is the one-request answer it returns, with the sort and the de-duplication skipped for a single request so that path is the call it always was. The branch that makes NO call at all when range narrowing leaves no live topic is untouched and must stay: an empty topic list reads as a wildcard at the node.
