# The learned range is REPORTED and CONFIGURED BACK IN, never persisted

The range fetcher discovers how wide an `eth_getLogs` range a provider will answer by being refused and adapting, and it holds what it learned -- a ceiling, a largest-known-safe span, and the size it will ask for next -- in memory. That state is now READABLE (`LogFetcher.limits`, and the `fetcher` field of `/status`) and ACCEPTABLE BACK as configuration (`fetch.learnedRange`, `LEARNED_RANGE`). It is deliberately NOT persisted by the fetcher, by any store it could reach, or by the wire.

Recorded because the obvious move is the wrong one, and because it settles a rule that reads as if it had already been broken. The fetching half of ADR-0003 holds no state worth losing, and `LogFetcher`'s own docstring states the test for what it may hold: **losing it must cost ONE extra request and nothing else**. That is true of the cursor hint (a `409` corrects it) and it is NOT true of the learned range, which on a restart re-pays a walk up from the 50-block starting range. So the range fails the test, and yet it is only performance -- exactly the shape of thing somebody later "fixes" by giving the fetcher a little store.

## What was decided against

- **Persisting it in the fetcher** (a file, a keyspace, a row). It buys a few round trips at the price of the property the whole component is built on: a fetcher that writes something down is a fetcher that can be restored from a stale copy of it, needs to own that copy's lifecycle, and has a place for the next block number to be put. ADR-0004 removes the split brain by making the RECEIVER authoritative about the only durable number in this half of the system, and the second store is how that comes back.
- **Pushing it to the receiver**, which is durable, and reading it back on `expectedFromBlock`. It puts a fact about ONE SENDER'S PROVIDER into the wire contract and into the receiver's state, where it means nothing: two fetchers pushing to one receiver read different nodes with different caps, and the receiver has no way to tell whose number it is holding. The envelope deliberately carries no sender identity (ADR-0004), and this would be the first reason to add one.
- **Leaving it invisible.** That was the status quo, and it is what makes the persistence question feel forced: with no way to read the value, "remember it" and "write it down inside the fetcher" are the same sentence.

## Consequences

- **The memory moves OUT of the stateless component to whoever is already durable**: an operator, a deployment config, a supervisor that reads `/status` and sets `LEARNED_RANGE` on the next start. That resolves the tension rather than trading it away, and it costs a deployment that wants the effect exactly one piece of glue.
- **A configured range is a STARTING POINT and never a promise.** It is bounded by this deployment's own `maxBlocksPerFetch`, adaptation runs over it unchanged, and a provider that has tightened since refuses it and lowers the ceiling on the first round trip. A stale value therefore costs a retry and can never wedge -- which is what makes it safe to paste a six-month-old number in.
- **The `/status` field is TYPED, unlike the cursor beside it.** ADR-0047 makes the cursor an envelope around a value the server never parses, because a cursor's meaning lives behind the storage seam and belongs to a processor (ADR-0027). A learned range has no such seam: it is `@etherfold/core`'s, a package `@etherfold/server` already depends on, and it is three numbers. So the field is `{reported: true, learnedRange, suspectResultCount}` with named keys a dashboard may read, and the envelope is kept only for the half of ADR-0047 that still applies -- a reporter that cannot answer degrades to `{reported: false, reason}` rather than to an omission, because "this deployment runs no fetcher" and "this deployment's reporter is broken" are different news.
- **Only the COMBINED shape reports it today.** `/status` belongs to the receiving half, so `etherfold run` (which holds both halves) injects the reporter, and `index`, `serve` and the Workers host carry no `fetcher` field at all. A SPLIT `etherfold fetch` process has no HTTP surface of its own, so what it can say about its learned range is its startup line and its logs. Giving the fetching half a status surface is a separate question and not one this decision answers.
- **The reported shape is now a thing an operator copies**, which is the usual cost of reporting anything: `{ceiling?, safeSpan?, nextSize}` is documented on both ends and an unrecognised key in a configured value is IGNORED rather than refused, so a report that grows a field does not turn a supervisor that pastes it into an outage.
