# The way BACK is an authenticated admin route under the named indexer, and the pointer moves without a fold

Moving the **canonical pointer** BACK is the operator's undo for a bad upgrade, and it needed an AFFORDANCE. It is `POST /{indexer}/admin/canonical-generation` on the indexer-server, guarded by a NEW `ADMIN_TOKEN` that fails closed when unset, and it moves the pointer to any REGISTERED generation whether or not this host holds a FOLD for it.

**HTTP, because it is the only affordance that exists on every deployment shape.** On Cloudflare there is no CLI at all -- a Worker is reachable only over HTTP -- so a flag on a command cannot serve a serverless deployment, and a library call with no operator surface does not deliver the story anywhere. The command set is pinned at five verbs with no default command (`one-command-runs-the-whole-pipeline`), so a sixth is unavailable, and hanging `--revert` on `run` would conflate a long-running fold with a one-shot control action. `/admin/setup` already exists, so `/admin` is an ESTABLISHED namespace rather than a new class of surface; what is new is the `/{indexer}` prefix on it, because a pointer belongs to ONE named indexer while `setup` migrates the fixed tables and knows no name. The CLI inherits the route by hosting the same app, so there is one implementation and not one per runtime.

**A SECOND credential, and never the ingest one.** `INGEST_TOKEN` is handed to a log shipper and guards the WRITE path; letting it also change WHICH GENERATION ANSWERS READS would give a fetcher control-plane authority over the deployment it feeds. `ADMIN_TOKEN` refuses everyone when unset, exactly as the ingest guard does, and the two share ONE constant-time comparison (`api/auth.ts`) so that "is a token accepted" has one answer rather than two that can drift. It does NOT retrofit `POST /admin/setup`, which stays unauthenticated: that is idempotent DDL and plausibly a deliberate bootstrap choice, and changing it is a decision of its own rather than a side effect of introducing this one.

**The move does not require a fold, and that is what makes the revert REAL rather than theoretical.** On this runtime reads resolve the pointer to a table NAMESPACE (ADR-0053), so the canonical generation answers with no engine at all -- which is precisely the ordinary case: a host redeployed with the new processor holds only the new fold, and the generation an operator wants back is in the durable registry with its state where it left it. Requiring a held fold would mean a revert could only be performed by a process first rebuilt with the OLD processor, which is the re-index this whole design exists to remove. The refusal is therefore the registry's (`UnknownGenerationError`, surfaced as `400 unknown-generation` naming every generation the name holds), and a host with no generation registry at all answers `501`.

**A BACKWARDS move drops nothing, under any promotion config.** `ReceivingIndexer` now tracks whether the pointer has EVER named a held fold, exactly as the chain-facing container's `everCanonical` flag does, and drop-on-promotion applies only to a FORWARD move: a revert supersedes nothing, and dropping what it moved away from would delete the very generation a second move forward wants (ADR-0046). A target this container holds no fold for is treated as a revert too, which is the safe direction, since the only consequence is that nothing is dropped.

## Considered Options

- **A `--revert` flag or a sixth CLI verb.** Rejected above: it cannot serve a Worker, which is the deployment shape that most needs an operator surface, and the verb set is pinned.
- **Reuse `INGEST_TOKEN`.** Rejected: one secret for two audiences, where one of them is a fetch process that should never hold control-plane authority. The cost of the alternative is one more secret to deploy, and a deployment that never reverts by hand simply never sets it.
- **A `revert` verb beside `promote`.** Rejected as two names for ONE record write. Moving the pointer IS promotion and moving it back IS revert (`CONTEXT.md`); a second verb would be a second place for the rules to diverge, and the direction is not a property the caller has to declare -- the container derives it from whether the pointer has named that generation before.
- **Take the opaque generation DIGEST as the target** (the value the feed advertises). Rejected as the sole form: the digest is deliberately not reversible and the registry KEYS on `{stream, processor}`, so accepting only a digest would make this route resolve one by scanning. The `GET` on the same path reports both forms per generation, so an operator matches the advertised digest against the listing and sends the pair.
- **Refuse a target this host holds no fold for**, as the container's `promote` did before this. Rejected above: it makes the ordinary post-redeploy revert impossible.

## Consequences

- **A deployment that wants the way back must configure `ADMIN_TOKEN`.** With none set the route answers `401` to everyone, including the operator, which is the fail-closed direction and is the same behaviour the ingest surface has had.
- **The affordance is available wherever the app is hosted, including the CLI**, but a host only ANSWERS it once its registry entry holds generations: `IndexerRegistryEntry.generations` / `promote` are OPTIONAL, and a host holding one fold and no registry (`singleContextEntry`, the Worker host today, `etherfold index` today) answers `501 generations-not-held`. Threading the CLI's own container into that entry is `the-cli-and-the-server-hold-generations-the-same-way`.
- **`everCanonical` is in memory**, like the promotion arming it sits beside (ADR-0046), so a restart forgets which generations the pointer has named. The cost is bounded to drop-on-promotion, and it falls on the retaining side.
