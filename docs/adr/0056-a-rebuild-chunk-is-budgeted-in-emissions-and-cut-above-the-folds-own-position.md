# A rebuild chunk is BUDGETED in emissions, CUT on a block boundary, and always ends ABOVE the fold's own position

A successor catches up by replaying the stored emission stream in bounded chunks against a durable checkpoint (ADR-0008's mechanism, over the generation model). We decided that **the checkpoint is the successor's own SYNC CURSOR and there is no second durable value**; that **a chunk is a budget in EMISSIONS whose cut lands on a BLOCK BOUNDARY**; and that **a chunk always covers at least one block above what the fold already covers**, so the budget is a budget and not a bound. Completeness — the thing a scheduler loops on, and therefore the thing the promotion trigger fires behind — is "this fold has reached the stream's own COVERAGE CLAIM", not "the read hit its budget" and not a `seq` comparison.

## The checkpoint

`EventProcessor.process` persists the `LastSync` describing each block in the SAME transaction as that block, because the cursor lives behind the storage seam precisely so that only the store — which holds the transaction — can write it (ADR-0027). So "the state and the checkpoint commit together" is a property the seam already guarantees, and a rebuild table beside it could only ever disagree with the state it describes: a crash between the two writes would leave a checkpoint that re-applies or skips a chunk, which is the failure the whole chunking exists to survive. `GenerationRebuild` therefore holds no position between calls at all, and a new process, a new isolate or a new container resumes from what the store committed.

## Why the cut is a block boundary and not a row

The stored stream is `seq`-ordered, and a reorg puts an application, its retraction and its replacement at ONE block at arbitrarily separated `seq` values — the retraction is appended at its ORIGINAL block, possibly long after higher blocks were written. A chunk that ended at an arbitrary row would therefore leave rows BELOW its own resume point, and the next chunk resumes above them: they would be skipped for ever, silently, and the rebuilt state would differ from the fold it is supposed to reproduce. Cutting on a block boundary makes a chunk complete by construction, because every row of every block in the range is in it whatever `seq` it carries. The price is that a single block carrying more emissions than the budget is replayed whole.

## Why a chunk must end ABOVE the fold's own position

A resume point REACHES BACK: `getFromBlock` returns `min(lastToBlock + 1, latestBlock - finality)`, so a fold level with (or near) the tip asks for blocks it has already folded. That reach-back is not optional — it is the only way a replay sees a retraction appended below its own cursor. But it means a budget spent inside the reorg window cuts the chunk at or below where the fold already is, the fold claims nothing new, and the identical chunk is asked for again: a rebuild that never completes and a pointer that never moves, with no error anywhere. So the reader is told `foldedThrough` and guarantees a cut strictly above it. The extra work that can cost is bounded by the reorg window, which is exactly what one cycle of a live indexer already pays.

## Considered options for "when is it caught up"

- **The stream's COVERAGE CLAIM (chosen).** `_stream_coverage.lastToBlock` (ADR-0055) is moved by every batch including the ones that carried no logs, so it cannot under-claim over a quiet range the way `MAX(blockNumber)` does. It is also the SAME space the promotion trigger already compares in (`hasReachedCursor` over `lastToBlock`, ADR-0046), so no second notion of "level" enters the system, and because the append is ordered before the fold (ADR-0052), reaching the stream's claim implies reaching the incumbent's cursor.
- **The emission `seq` HIGH-WATER.** The task launched with this answer, and it is exact in stream space — but it cannot be evaluated without persisting a consumed-`seq`, and that value cannot be written in the store's block transaction, so it would be the second durable checkpoint this ADR rejects above. Worse, the naive form is wrong in the steady state: the resume point walks past old rows, so a level fold reads no rows at all and its highest observed `seq` sits permanently below the high-water. The high-water is still READ and REPORTED on every chunk (`RebuildReport.highWater`), because it is the honest measure of the size of what is being folded; it is simply not the predicate.
- **"The read hit its budget".** The obvious answer, and it is the stall above wearing a different hat: a level fold re-reads its reorg window every call and hits a small budget for ever, so a rebuild that had finished would report unfinished indefinitely.

## Consequences

- **`ReplaySource.readChunk` takes `foldedThrough`**, which reads oddly until the reach-back is understood — a reader that only knew `fromBlock` could not keep the guarantee. Any second implementation of the port (an IndexedDB one, say) owes the same rule.
- **The budget is advisory in two named places** (one oversized block; the reorg window). `RebuildReport.scanned` is what a host watches, and a deployment whose blocks are that busy lowers nothing — it is already paying that cost per cycle in the live path.
- **Pair-compaction stays load-bearing off by default.** A rebuild needs the stream, and this chunking reads it whole; nothing here changes ADR-0006's argument.
- **No index was added for the block-ordered probe.** The canonical index is partial on `alive = 1`, so a scan over a stream that includes retractions is a table scan over that `(indexer, stream)`'s rows whatever the order — the same position `compactEmissionPairs` is in, and the same answer for now: a third index on a table already weighed against D1's 10GB ceiling is paid for by every deployment, and nothing here has been measured against a stream large enough to say it earns its keep.
