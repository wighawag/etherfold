# A generation is held by NAMED DURABLE SLOTS, and `canonical` is merely the first one

> **AMENDED 2026-09-26 (ADR-0088):** an OPEN on the chain-facing container whose own specs would displace one another in `successor` is REFUSED before any of them is deleted, rather than holding an engine for the spec it displaced; see the fourth amendment at the end.
>
> **AMENDED 2026-09-26 (ADR-0094, `an-arrival-of-the-predecessor-re-arms-it-as-successor`):** an ARRIVAL of the generation `predecessor` names (an upload to a `node`, a configured start whose `-p` names it) is no longer "left where it is": it is RE-ARMED into `successor`, and the policy promotes it; see the third amendment at the end.
>
> **AMENDED 2026-09-26 (ADR-0094, `a-configured-start-folds-toward-exactly-its-configuration`):** a START whose configured processor names the CANONICAL generation no longer "changes nothing": it DISCARDS a different pending successor, behind the same guard; see the second amendment at the end.
>
> **AMENDED 2026-09-26 (`an-uploaded-processor-survives-a-restart`):** a START may no longer SILENTLY replace a different pending `successor`; see the amendment at the end, which changes the redeploy-per-commit case this ADR's second symptom describes.
>
> **AMENDED 2026-09-25 (ADR-0092):** the 2026-09-19 LANDED block's "nothing retains, re-imports or reconstructs past processor code" no longer describes the deployment; its dated amendment sits right under that sentence.

A registry holds generations keyed by CONTENT (`GenerationId` is `{stream, processor}`) and exactly one durable named pointer at them, `canonical`. Every other lifecycle question -- which generation is a pending successor, which is dead work, which a revert returns to -- is answered in MEMORY, by what one container has done since it opened. We propose to record that a generation is held by a small set of DURABLE NAMED SLOTS, of which `canonical` is simply the one that already exists: a slot is an assignment pointing at a generation, `successor` holds at most one so registering into it REPLACES what it held, `predecessor` is what a revert returns to, and a generation no slot names is dead.

## One missing fact, showing up as four separate bugs

The registry records THAT a generation is not canonical and never WHY. Four independent problems are that one gap:

**The abandoned-successor predicate could not be durable.** `a-successor-that-was-never-canonical-is-superseded` needed "has this generation EVER been canonical" and found the durable answer does not exist: the row is `{stream, processor, createdAt}` and nothing more, and it cannot be derived, because with the pointer at C and a newer generation N, "N was never canonical" and "N was canonical and the pointer was reverted away from it" are indistinguishable from the rows. It narrowed to what one process can honestly answer, and the code states the residual: across a restart nothing is recognised as abandoned, so nothing is dropped.

**That residual becomes a start-up outage once `version` is generated.** `assertProcessorVersion` already tells authors to generate it ("ideally generated, so it changes whenever the code does"). Then every build is a new identity, so every restart registers a new generation; `maxGenerations` is four; and a cap REFUSES at `open`. A deployment redeploying per commit stops STARTING on about the fourth deploy, with no remedy but deleting generations by hand.

**The promotion policy is silently inert on every path but one.** `open()` adds the fold the host was built with and only THEN sets `opened = true`; `add()` ends in `applyPolicyTo`, whose first line is `if (!this.opened) return`; `settlePromotion()`'s first line is `if (this.candidates.size === 0) return`. So a generation arriving at open is never armed and therefore can never be promoted -- not late, ever. Restarting with a changed processor leaves the incumbent canonical permanently, and on `index` the successor is not even advanced (`an-index-process-can-never-finish-a-processor-upgrade`). The gate's reasoning is sound and is exactly this ADR's subject: applying the policy at open would let `immediate` promote whatever the host was built with, and `on-catch-up` undo a revert recorded in a previous session. Telling a deliberate revert from a fresh successor needs the missing fact.

**The armed-candidate set has to be in memory.** `candidates` is documented as deliberately not "every non-canonical generation", because that rule would re-promote a successor on the cycle after a revert. It is the same distinction again, kept in memory because nothing durable carries it.

A slot carries it. `successor` names a generation meant to take over; `predecessor` names one a revert returned to; the difference is read rather than inferred, by any process, after any restart.

## What a slot is, and what it is not

A slot is an ASSIGNMENT: a durable name pointing at a generation, exactly as `canonical` already is. It is NOT part of the identity. The same content under two slots must remain ONE generation, because identity is content-addressed for reasons ADR-0053 and ADR-0036 record, and a slot inside `GenerationId` would fork one fold into two namespaces both folding the same stream.

- **`canonical`** -- what answers every read. Unchanged; this ADR renames nothing that exists.
- **`successor`** -- the generation being built beside it, and the only thing auto-promotion promotes. Holds AT MOST ONE: registering into an occupied `successor` replaces its occupant, whatever stream either sits on.
- **`predecessor`** -- what a revert moves back to, which is what retention after a promotion is for.

A generation no slot names, and that is not canonical, is GARBAGE and may be collected. That is a refcount, and far easier to prove safe than the three-way in-memory predicate it replaces.

## Naming, which is a decision and not a detail

The working name through the design discussion was `staging`, and it is rejected for two specific reasons rather than taste. It collides with this repo's own protocol vocabulary, where STAGING is the review-first position of `work/tasks/backlog/`. And the industry meaning actively misleads: a staging ENVIRONMENT is one you deliberately do not promote automatically, whereas this slot's defining property is that it is exactly what auto-promotion promotes.

`next` was considered and rejected because "the next generation" is unavoidable in this domain's prose and reads as "the following one in a listing", so the slot name would be ambiguous in every sentence it appears in. `candidate` was considered and rejected because it is taken by the in-memory armed set that this replaces, and one word meaning both a thing and its replacement is the collision `a-successor-that-was-never-canonical-is-superseded` refused when it declined to reuse `superseded` and `retired`.

`successor` and `predecessor` are chosen because they are ALREADY the words the prose and the ADRs use for exactly these two roles ("a successor is registered beside the incumbent"; "the incumbent becomes the predecessor and is RETAINED, because the pointer must be able to move back to it"). The three slots therefore introduce no new vocabulary at all: they promote three existing nouns to durable names.

**The slots are exactly three, and arbitrary named slots are NOT built.** An earlier draft kept hash-named slots as an opt-in for several coexisting successors. Dropped: nothing wants it, it is API surface with no consumer, and it was the sole source of ambiguity in the naming above, since a generation could then be conceptually a successor while not being in the `successor` slot. With three fixed slots the words mean one thing each. Adding a fourth, or arbitrary ones, stays cheap if something ever needs it.

## Considered options

**A durable `everCanonical` column**, which `a-successor-that-was-never-canonical-is-superseded` weighed and rejected. It answers a harder question than the one that needs answering, costs a field plus a migration across the SQL, IndexedDB and memory substrates plus the conformance surface, forces a decision about what legacy rows default to (and "never canonical" would make the first pass eligible to delete precisely the predecessor a revert wants), and amends ADR-0046 and ADR-0057. Decisively it would still not bound restart accumulation, and still not tell a deliberate revert from a fresh successor at open: knowing a promotion from a revert is not knowing what a generation is FOR.

**The in-memory narrowed predicate**, which is what shipped. Correct, and mostly unnecessary under slots: what it infers, a slot reads.

**Raising the caps.** Moves the wall, which is the argument `SERVER_GENERATION_CAPS` already makes against itself.

**A slot as part of `GenerationId`.** Rejected above: it would make one fold into two.

## Consequences

**The cap stops being load-bearing without being removed.** `open` no longer grows the count (it finds the pointer already names its fold, or replaces what `successor` holds), so the start-up refusal becomes unreachable on the default path. The cap survives as a backstop on the deliberate opt-in of several coexisting successors, which is what a cap is for. It should NOT be removed: `BROWSER_GENERATION_CAPS` guards a storage quota whose overflow surfaces as an error at an arbitrary write, which is a worse failure than a refusal at registration. What is missing beside it is an operator verb for "what is held, and reclaim what no slot names".

> **AMENDED 2026-09-16 (`a-generation-no-slot-names-is-reclaimed-on-request`): that verb EXISTS, on the receiving container and over HTTP.** `ReceivingIndexer.reclaim()` drops every registered generation no slot names, through the registry's existing deletion (the row, the state namespace as ADR-0053's `DROP`, and the stream reaped where nothing is left folding it), and DECLINES the one case the existing drops decline -- a writer whose stream another held fold follows (ADR-0044). The operator affordance over it is `POST /{indexer}/admin/reclaim-generations`, on the `ADMIN_TOKEN` and beside the pointer move for ADR-0057's reasons, with `GET /{indexer}/admin/canonical-generation` widened to report each slot, what it names, and everything no slot names. It is a VERB an operator runs and deliberately NOT a collector: nothing fires it on a timer or at `open`, because an automatic reclaim deletes with nobody present and this ADR does not make that decision. The caps are UNCHANGED, as this consequence says they should be. The chain-facing container has no such verb yet: it HAS slots since `the-chain-facing-container-holds-its-generations-in-slots`, and the verb was deliberately not ported with them, because that task's acceptance is the replacement rule and an operator affordance on a browser tab is a different question (there is no operator and no `ADMIN_TOKEN` there) with no consumer asking for it yet.

> **AMENDED 2026-09-16 (`the-chain-facing-container-holds-its-generations-in-slots`): what a cap of TWO means under THREE slots, measured rather than argued.** Three slots occupied at once is three generations, and `BROWSER_GENERATION_CAPS` is two. So a tab holds `canonical` + `successor` (the reconfigure loop, which slots make unbounded: a save REPLACES the pending successor, so a developer may save all afternoon at a count of two) OR `canonical` + `predecessor` (the revert window a promotion opens), and never all three; a registration that would need all three meets `maxGenerations` and is REFUSED. That is UNCHANGED behaviour rather than a new wall -- the same registration was refused before slots, and for the same reason -- and it is the right end of the trade, which is why the caps stay where they are and the revert target is never dropped to make room: an eviction picks a victim by a policy that cannot know which generation was being kept, and on a public node the re-index it costs may not be available at all. What is bounded now is CHURN, which is what a cap was always the wrong instrument against. Raising `BROWSER_GENERATION_CAPS.maxGenerations` to three, so that all three slots are expressible at once, is a separate decision with its own storage argument and is deliberately NOT taken here.

> **AMENDED 2026-09-22 (ADR-0089, `a-promotion-in-a-browser-tab-assigns-no-predecessor`): `predecessor` is ASSIGNED BY THE RECEIVING RUNTIME ONLY, and the cap arithmetic above is restated.** The three slots and their meanings are unchanged: `predecessor` still names the generation the pointer was last moved off, is still assigned by that move in the same commit, and is still never inferred. What changes is WHO assigns it. A pointer move on the CHAIN-FACING container (`Indexer`, a browser tab) assigns none, because the code that generation's fold needs is absent from the build there, so the slot would name something the runtime cannot instantiate (ADR-0089). The move itself never DRAFTS the assignment -- `moveCanonicalTo` takes the runtime's answer and applies it inside the one commit -- so there is no second act that could leave the slot populated. On the receiving container nothing changes and the revert window is exactly what it was.
>
> So the arithmetic above stops describing anything reachable in a browser, and its replacement is narrower than "the seat is free". A tab now holds `canonical` + `successor` and nothing else, and a superseded generation is UNSLOTTED -- collectable by this ADR's own rule, and collected by nothing on that runtime, since the `reclaim` verb is still the receiving container's alone. Whether the second seat is freed therefore depends on the DROP rule and not on any slot: a CROSS-STREAM save drops the superseded generation, which was alone on its old stream, and lands; a SAME-STREAM save loop still meets `maxGenerations`, because that generation is the FETCHER of the stream the arriving fold is on (ADR-0044) and dropping it would leave that fold folding a stream nothing appends to. Both are asserted in `packages/browser/test/aTabHoldsItsGenerationsInSlots.test.ts`. The caps are UNCHANGED, the refusal is still the right end of the trade, and `BROWSER_GENERATION_CAPS.maxGenerations: 3` stays deferred exactly as above.
>
> **Appended 2026-09-22 (ADR-0090's point 3, `a-generation-this-tab-holds-no-fold-for-is-collected-when-room-is-needed`): "collected by nothing on that runtime" now holds only while that runtime HOLDS ITS FOLD.** A generation the chain-facing container holds NO FOLD for, that no slot names and that is not canonical, is COLLECTED by an arriving registration there, because on that runtime it can never answer a read or fetch again and nothing else would ever take it. The RECLAIM VERB is untouched and is still the receiving container's alone, nothing fires on a timer or at `open`, and the caps are still UNCHANGED with `maxGenerations: 3` still deferred. The IN-SESSION half of the paragraph above stands exactly as written: while the superseded fold is held it is the stream's fetcher, the drop is declined and the same-stream save still meets `maxGenerations`.

**The `opened` gate can key on the slot instead of on arrival.** Arm what `successor` names; never arm what `predecessor` names. The restart path then gets the documented promotion behaviour while the hazard the gate exists to prevent stays prevented, so the gate's reasoning is honoured rather than reversed. This removes the correctness cliff where a restarted deployment waits for ever for a promotion that cannot happen.

> **LANDED 2026-09-19 (`promotion-arms-from-the-slot-so-a-restart-can-finish-an-upgrade`), and the front-matter status line comes off with it.** It was the last open consequence, and it turned out to be THREE parts rather than one, none of them sufficient alone -- which is what a measured build found when it implemented the gate narrowing exactly as written and watched the pointer stay where it was (pinned by `packages/core/test/aSuccessorIsPromotedOverAnIncumbentNoFoldHereHolds.test.ts`, which fails against the old rule; this citation used to name the observation note that recorded the measurement, retired on 2026-09-26).
>
> 1. **The gate.** `applyPolicyTo` arms what `successor` names and nothing else; `opened` and the in-memory `candidates` set are DELETED, and `settlePromotion` reads the slot.
> 2. **The TRIGGER had to be evaluable with no held fold for the canonical generation**, which is the restart shape itself: a redeployed process holds one fold, the new one, and the old processor's code is not in the build. A generation's position is now read the way the read tier already resolves its state -- by NAMESPACE, through an injected seam beside `dropState` (`GenerationRegistryPort.readStateCursor`) -- so measuring a generation needs no engine, exactly as ANSWERING from one does. Nothing retains, re-imports or reconstructs past processor code; the comparison needs a number, and the number is a row.
>
> **AMENDED 2026-09-25 (ADR-0092):** "nothing retains, re-imports or reconstructs past processor code" stopped being true of the deployment, though it is still true of this TRIGGER. A Node deployment now stores each generation's bundle beside its state (`a-generation-keeps-the-bundle-that-folds-it`), and a pointer move onto a same-stream generation the process holds no fold for instantiates it from those bytes so it folds (`a-revert-resumes-folding`). The comparison here still reads a number from a row and loads no code.
>
> **AMENDED 2026-09-25 (ADR-0092, `an-upgrading-restart-keeps-the-incumbent-folding`):** "a redeployed process holds one fold, the new one" is no longer the restart shape on a Node deployment. The canonical generation is instantiated at `open` from its stored bundle when the process holds no fold for it, so the incumbent is HELD and its cursor MOVES while the successor catches up. The trigger is unchanged in what it reads (a row, through `readStateCursor`), and where the incumbent is held the comparison and the move are serialised on that fold's advance chain, so the successor is promoted at or past where the incumbent finally stood. The fold instantiated for the incumbent stops being folded once a promotion moves the pointer off it; the generation is retained as `predecessor` exactly as before.
> 3. **Something had to CALL the settle** in that shape: `run` gated its `rebuildMore` on holding a follower, and a successor registered at `open` is not one (it is fed by the wire), so the trigger was never reached at all.
>
> Asserted end to end on a deployment stood up, stopped and re-run over the same substrate with a changed processor, plus the revert case driven through a restart (`packages/cli/test/aRestartFinishesTheUpgrade.test.ts`). ADR-0046 carries the amendment for the arming rule it wrote; the chain-facing `Indexer` still arms in memory and is deliberately untouched here.

**The in-memory `candidates` set collapses into the slot**, since the candidate for promotion IS what `successor` names, subject to the policy. Together with the abandoned-successor predicate, three in-memory structures reduce to one durable fact.

**One pending successor, whatever stream it sits on.** With exactly three slots there is no per-identity alternative to weigh, so the cross-stream question that `a-successor-that-was-never-canonical-is-superseded` answered by fiat is answered structurally instead: a newer successor replaces the pending one wherever either sits, because there is only one place for a pending successor to be.

**BOTH containers get slots, and the chain-facing one is where it matters most.** `a-successor-that-was-never-canonical-is-superseded` scoped itself to the RECEIVING container and left `Indexer` (`container.ts`, chain-facing, what a browser tab runs) unchanged, which is defensible for an in-memory rule and wrong for a durable one. A browser tab is the shape that restarts most (a page reload is a fresh process with empty memory), runs against the tightest caps (`BROWSER_GENERATION_CAPS`, two of each), and is the one an HMR loop reconfigures on every save. So the in-memory rule protects the case that needs it least. The two twins differ in shape (`everCanonical` is a boolean on the entry there, a set here) and in cap arithmetic, so this is two pieces of work and not one, and the receiving container goes first because it owns the endpoint and the tests.

> **AMENDED 2026-09-16 (`the-chain-facing-container-holds-its-generations-in-slots`): BOTH containers now have them, and exactly ONE thing is shared.** `Indexer.add` registers into `successor`, replaces what it held and drops it (row, state store, and the stream where no registered generation is left folding it), and `everCanonical` is DELETED there as it was here. What the twins SHARE is the rule and only the rule: `displacedBySuccessor` (`generation/registry.ts`) answers "what does a registration into `successor` displace", including the one clause the whole thing is safe on -- a generation any OTHER slot names is untouchable -- so the revert target cannot be deleted by the twin nobody was reading. What is REPEATED, deliberately and worded alike in both, is the ACTION: whether a drop would strand a follower, and what stopping a fold means, differ because a fold is an ENGINE on one side and a RECEIVER on the other. A shared abstraction over the two would have to be parameterised over storage, caps and what a fold IS, which is the options-growing base class ADR-0071's closing section already refused.

**The safety obligation moves and gets easier.** It becomes: replacing what `successor` holds must be provably unable to touch `canonical` or `predecessor`. That is a statement about one slot, assertable directly, rather than a conjunction of three in-memory facts.

**No upgrade path is provided, deliberately.** A registry predating slots holds generations no slot names, and `predecessor` could not be reconstructed for them: which generation a revert would want is exactly the fact that was never recorded, so the missing fact this ADR exists to supply is also the one its own migration would need. That is moot rather than unsolved. Nobody runs these packages, every consumer is a repository we own, and `CONTEXT.md` records this as a standing convention, so the correct shape is built directly and no persisted state is carried forward. This consequence is the one to revisit if slots land after something outside our repositories holds state.

**Reaping follows the generation, unchanged.** Replacing a successor that was the last registered on its stream reaps that stream, which is already what `deleteGeneration` does and already why a drop is declined while another held fold follows the stream.

## Amendment, 2026-09-26 (`an-uploaded-processor-survives-a-restart`, ADR-0093): a START may not silently replace a pending successor

"Registering into an occupied `successor` replaces its occupant" is unchanged, and so is what a replacement deletes: the row, the state namespace and, since ADR-0092, the stored bundle. What changed is that the replace is no longer SILENT when a process STARTS. Uploads (ADR-0085's amendment) made a pending successor something a person sent to a running node, often the only copy of that code, and a restart with a configured processor would delete it with nobody asked. The maintainer decided on 2026-09-26:

- **A configured `--processor` is an arrival.** Where it names a processor different from the canonical generation's, it registers as the new `successor` exactly as before, and the promotion policy decides from there. Where it names the canonical generation, or the successor already pending, it changes nothing.
- **Where a START would replace a DIFFERENT pending successor**, however that successor arrived, it is asked about BEFORE anything is registered. An interactive start (stdin is a TTY) asks, naming both generations, and proceeds only on a yes. A non-interactive start is REFUSED by name, with nothing registered or deleted, unless `--override` is given.
- **Only the START is guarded.** The re-read (`POST /{indexer}/admin/reconfigure`) and an upload are already deliberate acts on a running node, and replace a pending successor without a question, as before.

> **AMENDED 2026-09-26 (ADR-0094, `the-re-read-endpoint-is-deleted`):** the re-read endpoint is DELETED, so the upload (on `etherfold node`) is the one deliberate act left that registers a successor on a running node, and it still replaces a pending successor without a question. Only the START is guarded, unchanged.

This changes the redeploy-per-commit case in "One missing fact": a pipeline that restarts with a new processor while the previous one is still catching up now passes `--override`, once, in its deploy configuration. The slots still keep such a deployment starting (the count does not grow), which was the point of that paragraph; what it gains is that the deletion is something the pipeline said it wanted.

Where it lives: the container asks through `ReceivingIndexerOptions.confirmReplacingSuccessorAtStart` from `open` alone, before `add`, and never from `add` itself (`@etherfold/core`). Every CLI command that STARTS with a configured `--processor` answers it the same way (`startGuardFor`, `packages/cli/src/startGuard.ts`) and takes `--override`: `run`, `build` and `index`, because all three open the same container over the same registry and slots (`openFolding`), so an `index -p X` or a re-run `build -p X` against a database holding an uploaded pending successor would otherwise delete it silently. `fetch` and `serve` hold no processor, register nothing, and refuse the flag.

## Amendment, 2026-09-26 (ADR-0094, `a-configured-start-folds-toward-exactly-its-configuration`): a start naming the canonical generation DISCARDS a different pending successor

The first bullet of the amendment above said a configured `--processor` naming the canonical generation "changes nothing". That is no longer true. It left the pending successor to be promoted, so a configured command (`run`, a re-run `build`, an `index` receiver) could serve, or publish, code its configuration does not name. ADR-0094's third consequence makes configuration the truth on those commands, and the maintainer extended it to all three on 2026-09-26:

- **A configured start naming the CANONICAL generation, while a DIFFERENT generation is pending in `successor`, DISCARDS that successor**: row, state namespace and stored bundle, through the registry's `deleteGeneration`, exactly what a replaced successor loses, and the `successor` slot is left EMPTY. The stream is kept (ADR-0087). The canonical generation keeps folding, and nothing is promoted over it.
- **It is guarded exactly as a replacement is**: asked at a terminal, REFUSED by name elsewhere unless `--override`, and a refusal leaves the registry, the slots, the state and the bytes untouched. The host's question carries which of the two deletions it is (`SuccessorReplacementAtStart.kind`, `replace` or `discard`), and the CLI words each on its own terms (`startGuardFor`).
- **It happens in `open`, BEFORE `foldTheSuccessor`**, so no engine is built for a generation about to be deleted, and it is performed there rather than in `add`, because `add` registers nothing for a generation already canonical and so displaces nothing. A delete that FAILS refuses the start rather than being logged past, unlike a failed replacement: nothing takes the slot here, so a successor that failed to go would still be promoted.
- **Unchanged:** a configured processor naming the pending successor itself changes nothing; one naming the canonical generation with nothing pending changes nothing and asks nothing; one naming a different processor registers it as successor, guarded where it replaces a different pending one. A start naming what `predecessor` holds RE-ARMS it (the amendment below). `node` has no configured processor and so discards nothing at start, and an upload to it still replaces a pending successor without a question.

## Amendment, 2026-09-26 (ADR-0094, `an-arrival-of-the-predecessor-re-arms-it-as-successor`): an arrival of the predecessor RE-ARMS it as successor

The registry's rule "a generation ALREADY IN A SLOT stays where it is" (the slot rules in `GenerationRegistry.create`) protected two cases: a redeploy naming the canonical generation, and one naming what `predecessor` holds, which "must not be re-armed by the act of starting up". The second half no longer holds. It meant that the bytes of the previous version, uploaded to a `node`, were registered and FOLDED while staying in `predecessor`: a rollback that did not roll back, and an engine for a generation nobody reads (ADR-0092). The maintainer decided on 2026-09-26 (ADR-0094) to RE-ARM it:

- **An arrival of the generation `predecessor` names, into `successor`, MOVES it there**, and `predecessor` is emptied in the SAME commit: one generation is never named by two slots. It resolves to the record it already is (no second row, no new bytes). The pointer does NOT move: from `successor` the promotion policy decides as for any successor, so under `on-catch-up` it catches up from where its own state stood and is promoted, and the generation it replaces as canonical becomes `predecessor`; under `manual` it waits. The rule is the REGISTRY's, the same for every arrival and both containers, and `displacedBySuccessor` no longer treats "some slot names the arrival" as "displaces nothing": an arrival of the predecessor takes `successor`, so it displaces what `successor` held, exactly as any arrival does. What `canonical` or `successor` already names is unchanged: it stays where it is.
- **The arrivals.** An upload on `node`, which replaces a different pending successor without asking, as any upload does. And a configured start on `run`, `build` or `index` whose `-p` names it: a rollback by configuration (ADR-0094: configuration is the truth). Replacing a DIFFERENT pending successor is guarded by the start guard with `kind: 'replace'`, as any start is; with nothing pending there is nothing to ask. A generation this process already FOLDS is re-armed without a second fold being built. _Amended 2026-09-26 (`a-promotion-leaves-no-engine-for-the-predecessor`, ADR-0092's third amendment): the parenthesis here read "a same-stream promotion keeps the superseded fold it built"; on a host that can instantiate stored bytes (the CLI's commands) a promotion now stops folding what it superseded however it arrived, so a predecessor is held there only on a host with no `instantiateGeneration`, and elsewhere the arrival itself is the fold that is re-armed._
- **What this changes about a revert surviving a restart.** "Arm what `successor` names; never arm what `predecessor` names" is unchanged, and so is the operator's revert (ADR-0057): it is a pointer move, not an arrival. But a `run` restarted with an UNCHANGED `-p` after a revert names the generation reverted AWAY from, which is what `predecessor` holds, so it is re-armed and promoted: configuration is the truth on `run`, and a revert there that should outlive a restart is made durable by changing `-p` to the generation reverted TO. A `node` has no configured processor, so a restart of one keeps the revert, under every policy value (`packages/cli/test/aRestartFinishesTheUpgrade.test.ts`). The chain-facing container assigns no `predecessor` (ADR-0089), so there the clause only ever meets a registry another runtime wrote.

## Amendment, 2026-09-26 (ADR-0088): one open may not displace its own specs

"`successor` holds AT MOST ONE, and registering into it replaces its occupant" is unchanged. What this amendment adds is the one place where "replaces" had no honest meaning: two specs handed to ONE `open` of the chain-facing container (`openIndexer`, `@etherfold/core`).

`open` registers every spec before it builds any engine (ADR-0088), and every distinct spec beside the canonical generation registers into `successor`. With three distinct specs on a fresh registry the first took `canonical`, the second took `successor`, and the third DISPLACED the second through the shared rule (`displacedBySuccessor`, ADR-0071), deleting its row and its state; phase two then built an engine for all three. Measured on 2026-09-26 against the code before this change: the container held a fold for the displaced spec, which the registry no longer named, and the displaced spec's state had been dropped. The caps do not prevent it: the displaced record is dropped BEFORE the arriving one is created, so the count never exceeds the cap, and it reproduces under the browser's own caps (two generations). What keeps a browser tab clear of it is that every browser host opens with ONE spec; it is reachable through `openIndexer` with several.

**Such an open is now REFUSED, by name, before any of its own specs is deleted** (`OpenedSpecsDisplaceOneAnotherError`, naming the spec already in `successor` and the one that would have displaced it). The earlier spec keeps its row, its slot and its state; the refused spec is not registered; a successor an EARLIER session left pending may already have been replaced by an earlier spec of the open, exactly as any arrival replaces it; and what its factories opened is left exactly as a cap refusal leaves it.

**Refusal rather than "hold only what survived"**, because a list is not a sequence of arrivals. The replacement rule is right for an ARRIVAL, where the newer successor is the one a person just sent; nothing in one array is newer than anything else in it, so letting the last-listed spec win would make which generation survives, and whose state is deleted, a function of how the caller spelled its array. That is the order dependence ADR-0088 removed from `follows`, and it would also delete, with nobody asking, state the same call had asked to hold. What is NOT refused: a spec named twice resolves to one generation, and a spec that replaces a successor an EARLIER session left pending is an arrival like any other and replaces it as before. The receiving container is not affected: its `open` registers at most one configured fold and builds the canonical and successor folds from the slots AFTER that registration (`foldTheCanonicalGeneration`, `foldTheSuccessor`), so it can only ever build what the registry names.
