# An unresolvable block address is an error, not an empty result

> **AMENDED 2026-09-30 (ADR-0099): the query layer's refusal of an unresolvable hash is `block-not-recorded`, and it does NOT name a reorg**; see the amendment at the end.

Reading state as of a block **hash** that the store has no row for throws `NoSuchBlockError` instead of answering `undefined`, because "there is no such block" and "that block is known and the entity was absent from it" are different news and must not arrive in the same shape. The soft form exists alongside it: `resolveBlockNumber(address)` answers `undefined` and throws nothing, for callers where an unknown hash is expected rather than alarming.

This is the read side of the asymmetry `docs/design/historical-state-database.md` §3 settles: a consumer that pins a block **number** gets a silently different answer after a reorg, while a consumer that pins the **hash** gets nothing back, and that nothing is the signal that whatever it derived is invalid. The signal only survives if it cannot be mistaken for an ordinary empty result, so the shape of the answer is where the decision lives.

## Considered Options

- **Return `undefined` for both.** The smallest diff and the shape the reads already had. Rejected: it destroys exactly the distinction hash-addressing is for. A consumer that pinned a reorged-out block would read "entity absent", conclude the state is empty, and carry on acting on a chain that no longer exists. The failure is silent, and silent is the specific thing being engineered against.
- **A discriminated result (`{found: true, value} | {found: false}`).** Honest and impossible to ignore, since the caller must unwrap before touching a value. Rejected on cost: it changes the return type of every existing read, so every current call site and test would have to be rewritten, and it forces the unwrap on the common path (a height, which cannot fail) to serve the rare one. Widening a parameter is backward compatible; changing a return type is not.
- **Resolve-first only** (expose `resolveBlockNumber`, keep the reads on numbers). Clean, and it is half of what we did. Rejected as the *whole* answer because it makes the safe path opt-in: passing a hash straight to a read is the obvious thing to try, and it would either not typecheck or quietly do something else. The reads accept all three axes, and the resolve step is available for callers that want to branch.

## Consequences

- **The three axes are not equally fallible, deliberately.** A *height* resolves to itself with no lookup and therefore never throws, because only blocks carrying our logs get rows while every height is a valid point on the version ranges. A *hash* must have a row. A *timestamp* resolves to the latest recorded block at or before T, and to nothing at all before the first recorded block (never to the first block). `NoSuchBlockError` carries a `reason` (`unknown-hash` or `no-recorded-block-at-or-before`) so the two unresolvable cases stay distinguishable.
- **A read on the hash or timestamp axis costs one extra round-trip**, since resolution is a separate query. Folding it into the read as a sub-select would save the trip and re-introduce the bug: a sub-select matching nothing makes the as-of predicate false and returns an empty result, which is "no such block" wearing "entity absent" as a disguise.
- **The API in front of this store inherits the distinction.** When the indexer-server exposes state queries over HTTP, an unresolvable hash is its own status (a client error naming the reorg), not `200` with an empty body. This is the same requirement ADR-0006 puts on the feed's cursor, where the server validates the cursor's block hash and answers "rewind to fork block F"; both exist so that a consumer holding a stale hash is told, rather than served.
- **Block hashes are folded to lower case** on write and on lookup. Hex case carries no meaning in a hash (unlike an EIP-55 address), but SQL comparison is case-sensitive, so an echoed-back upper-case hash would fail to resolve and be read as a reorg. A false reorg signal is the one wrong answer this design cannot afford.

## Amendment, 2026-09-30 (ADR-0099): the API refuses an unrecorded hash as `block-not-recorded`, and names no reorg

The third consequence above anticipated "a client error naming the reorg" for an unresolvable hash in the API in front of the store. The API that exists is the GraphQL query layer, and it refuses a `block: {hash}` the store has no record of with its own code, `block-not-recorded` (distinct from `block-not-retained`, a RECORDED height outside retention), on every executor, carrying the hash asked for. It deliberately does NOT name a reorg: only log-bearing blocks are recorded (the first consequence above), and a snapshot-seeded store records nothing below its floor, so an unrecorded hash may be reorged out, OR a canonical block that carried no log this store records, OR one below its snapshot. The message says the hash is not recorded HERE and lists the three. The distinction this ADR exists for survives intact: "no such block" is a refusal, never an empty answer. Lookups fold the hash to lower case as writes do, on both backends (IndexedDB now resolves a hash through its `hash` index, `blockOf`).
