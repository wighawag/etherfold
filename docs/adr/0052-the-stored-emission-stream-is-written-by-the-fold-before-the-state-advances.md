# The stored emission stream is written by the FOLD, before the state advances

The stored emission stream (ADR-0006) was appended by the HTTP ingest route and by nothing else, which made it a fact about the TRANSPORT: `etherfold run` and `etherfold build` fold through `createDirectIngestion`, reach no route, and produced databases whose `_emissions` table was EMPTY -- on the deployment shape the milestone calls the default, and on the artifact `build` exists to publish. That is the same defect ADR-0050 removed for the reorg counters one task earlier, in the same place, and it contradicts that ADR's own recorded consequence that a `build`-produced database must be indistinguishable from a `run`-produced one.

We decided that **the append is a port on the receiver, supplied by whoever owns the store, and it is ORDERED BEFORE the fold**. `StreamBuilder.receive` hands each batch's emissions to an `EmissionAppender` (`@etherfold/core`) once, whichever entrance the batch arrived through; the deployment that opened the database supplies it (`emissionAppenderFor`, `@etherfold/server`, bound to the handle and to the NAMED INDEXER the host holds); and the ingest route is a CALLER of `receive` rather than the owner of a write. Two further decisions fall out of that one and are recorded below: this write is **not best-effort**, and `--indexer` becomes **optional with a default on the combined shapes**.

## Why this write is NOT best-effort, unlike the reorg count it sits beside

ADR-0050's counter is taken AFTER the batch was applied and its failure is caught and logged, because losing a count is a far better trade than rolling back the state it describes. The emission stream is the opposite trade and gets the opposite shape. A state that advanced past events the stream never received is a **hole** (`CONTEXT.md`): it is invisible to the gap check, because segments are keyed by SAVE rather than by block and a save that never happened leaves the ordinals perfectly contiguous; and it is silent, permanent and self-consistent, because on the next state discard the stream replays as though it were whole and the missing blocks are simply absent from the rebuilt state. `CONTEXT.md` already says where that is fixed -- on the ENGINE side, "by writing the stream BEFORE processing and not processing a batch that was not saved" -- and ADR-0038 is the same rule from the other end. So the append is ordered first and a failure PROPAGATES out of `receive`: nothing is processed, the cursor does not move, and the next cycle re-derives the same delta.

The accepted cost, in the other direction: if the append lands and the fold then fails, the stream is one batch AHEAD of the state and the re-derived delta is appended again. A stream may be ahead of the state or level with it, never behind (ADR-0038), so that side of the trade is survivable and a hole is not.

## Why `--indexer` may DEFAULT on `run` and `build`, and still may not on `fetch` and `index`

The emission row's key carries the NAMED INDEXER and the column is `NOT NULL`, so a fold that stores what it folded needs a name whether or not anything addresses it by one. That was the whole reason the write stayed on the route: `--indexer` was refused outright on the combined shapes, so there was no fold-side value to key on.

ADR-0036's never-defaulted rule protects the WIRE: a name a host was not built with must be a ROUTING error (`404`) and never a batch that quietly landed somewhere plausible. A combined process has no wire, no route and no second tenant, so that hazard cannot occur there, and ADR-0048's test for a default ("what does it look like when this is wrong and nobody notices?") comes out the other way: a run under an unintended name stores its emissions under that name in its own database and reads them back under the same one, so nothing is mis-answered and nothing is lost. Requiring it instead would break `etherfold run`, the readme's headline one-liner, for a discriminator that only starts to matter once two answer sets share a database. So `run` and `build` accept `--indexer` optionally and default it to `default` (`DEFAULT_INDEXER_NAME`), `fetch` and `index` still require it and default nothing, and `serve` still refuses it -- a read tier folds nothing and registers nothing.

This is not a new axis. ADR-0036 already says the name is UNIVERSAL rather than a server concept, "one discriminator, two sources of its value"; what changes is that the CLI's command table stops treating it as a wire input, which it never was.

## Considered options

- **Leave the write on the route and give the combined shapes a second writer.** Rejected on ADR-0050's own ground, and more sharply here. The shape that both CONCLUDES and RECEIVES (a split receiver: its stream-builder derives the batch, its route serves the request) would get two, and a duplicate append is not even a loud failure -- `seq` is allocated from the table, so the second copy lands at the next number and both of ADR-0006's views serve every log twice, for ever. A structural single site is what makes "exactly once" a property rather than a discipline (`packages/server/test/oneEmissionAppendSite.test.ts`).
- **Keep the append best-effort, like the counter, and log a failure.** Rejected: that is the definition of a hole. It is the one failure in this system that cannot be noticed later, by anything, including the gap check built to find damage in a stored stream.
- **Append AFTER the fold, so a failed fold cannot leave the stream ahead.** Rejected. It trades a survivable inconsistency (stream ahead) for the unsurvivable one (state ahead), and it is precisely the order the route had.
- **Move `appendEmissions` into the CLI beside `recordReorg`, mirroring ADR-0050 exactly.** Rejected, and this is the one place the two ADRs deliberately differ. The reorg keys went to `@etherfold/core` because the writer and the reader are in different packages -- a read tier owns no store and still answers "how many reverts does this database record". The emission table is the opposite: `@etherfold/server` owns its DDL, both views that read it, and the `seq` high-water read that the append and the canonical view's cursor MUST agree about. Splitting the write out would put one table's contract in two packages and duplicate the row shape. So the write stays with the table and `etherfold` takes `@etherfold/server` as a dependency, which is honest -- three of its five commands already start that server.
- **Default the indexer name to the database file's name rather than a constant.** Rejected: rows already stored must keep being found after the file is copied or moved, and a name that travelled with the path would silently fork the stored stream in two, which is the failure mode this key exists to prevent.

## Consequences

- **`--no-auto-setup` against a database nobody has migrated now STOPS a fold rather than degrading it.** The fixed tables carry `_emissions`, so a fold that cannot reach them cannot store what it folded, and it refuses the batch instead of advancing. The cycle is retried (the failure carries no `retryable: false`, and a database somebody else is migrating is exactly the case worth retrying), the cursor stays where it was, and the deployment catches up when the schema arrives. That is a deliberate change of behaviour on that flag, and it is the visible face of the rule above: a fold that cannot record what it folded must not advance past it.
- **`etherfold run` and `etherfold build` now hold a NAMED INDEXER.** They still register nothing and route nothing -- `run` injects no registry into its server, so its ingest routes still answer `501` -- but the name is on their resolved config, on their `--help`, and on every emission row they store.
- **A `build` artifact carries its stream**, which is what makes a processor-only change re-foldable from disk instead of re-fetchable from the node. That was the point of storing a stream at all, and it was unavailable on exactly the shapes that hold a local store.
- **Both of ADR-0006's views stop being a split-shape-only surface.** They answer over whatever a fold stored, given a host that resolves the name (the receiver is still the only thing that knows WHICH stream is served now, so `etherfold serve` still cannot serve them).
- **`@etherfold/server` exports `emissionAppenderFor` and its ingest route performs no durable write at all.** Everything a batch costs happens inside `receive`; the route decides who may call it and which status code each refusal is, which is what a transport is for.
