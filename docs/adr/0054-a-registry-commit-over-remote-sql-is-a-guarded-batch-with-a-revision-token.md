# A registry commit over `RemoteSQL` is a GUARDED BATCH carrying a revision TOKEN

The generation registry decides and writes in one step: `GenerationRegistryPort.commit` takes a DECISION FUNCTION, because "is this generation already registered, and does registering it breach a cap" has to be answered from the state the write is then applied to. Two writers that both read "one generation, a cap of two" and then both wrote would leave three generations behind them, with nothing afterwards able to say which write was the one too many. IndexedDB gives that for free (`readwrite` transactions serialise across tabs) and one JS heap gives it trivially. The server and CLI substrate has neither: its seam is `RemoteSQL`, which is exactly `prepare(sql)` plus `batch(statements)`, and a batch is a PRE-BUILT statement list, so there is no way to read, run JS and write while still inside one transaction.

We decided: **a commit reads the state together with a REVISION token, guards every statement it writes on that token, swaps the token for a fresh unique one as the last write of the SAME batch, and reads the token back inside that batch to learn whether it won.** A loser's statements each match zero rows, so its whole batch applies to NOTHING; it re-reads, re-runs the decision function against the state that actually holds, and tries again (bounded, then `GenerationCommitContentionError`). The token lives on the canonical-pointer row, which every commit already writes, so the guarantee costs no extra row and no extra statement.

The alternative we are explicitly refusing is a read-then-write that merely LOOKS atomic. It passes every single-writer test, and the state it corrupts -- a cap silently exceeded -- is invisible afterwards.

## Considered Options

- **Push the DECISION into SQL** (an insert guarded by a `SELECT COUNT(*) < cap` over the same rows). Rejected: the decision is not one predicate. It resolves an already-registered generation, applies two different caps, and refuses with an error that NAMES every deletable generation and stream. Expressing that in SQL forks the registry's rules into a second implementation, in a language that cannot raise `GenerationCapReachedError`, and every later rule change would have to be made twice. The rules live over a PORT precisely so a substrate inherits them.
- **A monotonically increasing INTEGER revision** instead of an opaque token. Rejected on the read-back: `remote-sql` reports no affected-row count (the same constraint pair-compaction works around by naming every row it deletes), so the only evidence a commit has is what it can `SELECT`. Under a counter, a loser reads `expected + 1` -- the winner's value, and the very number the loser was about to write -- and cannot tell a win from a loss. A value only this attempt could have produced makes the two distinguishable with one `SELECT`.
- **`BEGIN IMMEDIATE` / an explicit transaction around the decision.** Not available: `RemoteSQL` has no transaction verb, and adding one would be a change to a seam whose whole point is that D1, libSQL and anything else can satisfy it. `state-store-sqlite` already documents the same limit ("a transaction is exposed only as a batch") and copes the same way, by making the atomic unit exactly one `batch`.
- **A dedicated lock row taken and released around the commit.** Rejected: a crashed holder leaves the registry wedged until something times the lock out, which is a second mechanism with a second failure mode. The guard has no held state at all -- a loser simply wrote nothing.
- **Serialise commits in the process.** Rejected as a non-answer for the runtime this is FOR: the intended host is serverless, so two isolates are two processes, and an in-process mutex is one isolate's private opinion about a value the database owns -- the same reasoning that keeps `StreamBuilder` reading its cursor on every call.

## Consequences

- **A losing commit RE-RUNS the decision function.** So `plan` must stay a pure decision over the state it is handed, which is what the port already documents (synchronous, may throw, writes nothing when it throws). A refusal is therefore always decided from the state the write would have landed on.
- **Contention is reported, not hidden.** After `MAX_COMMIT_ATTEMPTS` losses, `GenerationCommitContentionError` says nothing was written and the caller may retry; an unbounded retry against a contended database is indistinguishable from a hang.
- **The pointer row carries a column that is not about the pointer.** `_generation_pointer.revision` is a concurrency guard on a row that otherwise names the canonical generation. That is deliberate, and it is why both the schema and the module say so: the row is the one thing every commit writes, so it is the cheapest possible place for the guard, and a table of its own would double the statements for no gain.
- **The mechanism is testable without timing.** A test wraps the handle and commits a rival's write just before the first WRITING batch of the handle under test reaches the database, which is the exact window a read-then-write cannot survive. Removing the guard turns that test red; a `setTimeout` race would not.
