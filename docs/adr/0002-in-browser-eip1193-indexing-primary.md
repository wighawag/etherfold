# In-browser EIP-1193 indexing is the primary design axis

The indexer is designed so an indexer can run **client-side, in the browser**, over a plain EIP-1193 provider — for **decentralization** (each client can index for itself, no trusted server required). This shapes the whole processor contract and is a deliberate constraint, not an accident of the code.

## Consequences

- The core stays EIP-1193-first and must not require a server to function.
- **Batch RPC is not prohibited, and the allowance is now MOOT: the engine makes no request it could batch** (ADR-0073). The correction this bullet was written to make still stands, so read it first: an early framing that batch RPC was off-limits under this ADR was inaccurate, and nothing here forbids batching. What has changed is that there is nothing left to batch. `providerSupportsETHBatch` existed so the per-hash block and transaction fetches could go out as ONE request instead of N; those fetches are deleted, so the engine's whole chain-facing surface is one `eth_getLogs` per range, one `eth_blockNumber` for the tip and one `eth_chainId` for the identity guard. The flag went with them, in the core, in `@etherfold/fetcher-host`, and as the `PROVIDER_SUPPORTS_ETH_BATCH` deployment variable of `platforms/nodejs-fetcher`. A caller's provider may still batch whatever it likes, transparently, and the engine neither knows nor cares: it simply no longer asks. Read as a cost decision this is the strongest form of what this ADR asks for, rather than a reversal of it: batching mattered here because a browser provider frequently cannot batch and pays a round trip per call, and a request that is never made costs nothing on such a provider either.
- **Block timestamps: the old constraint was obsolete, was acted on, and the fallback is now GONE** (`0957f8c`, `c681b79`, then ADR-0073). `eth_getLogs` used to omit timestamps, so `alwaysFetchTimestamps` paid for an extra `eth_getBlockByHash` per block — the worst shape of cost under this ADR, since a browser provider frequently cannot batch those calls and each is its own round-trip. `blockTimestamp` is now on the log itself (`ethereum/execution-apis#639`, merged 2025-08-25), so the core reads it from the log and the timestamp axis costs zero extra requests. EDR, the one holdout this bullet used to name, implemented it in `@nomicfoundation/edr@0.20.0` (released 2026-09-02, `NomicFoundation/edr#1644`), so the fallback had no remaining constituency and `alwaysFetchTimestamps`, `enrichEvents` and the block-timestamp cache are DELETED (ADR-0073). The field stays optional at the TYPE level, because the wire does not guarantee it: a node FORKING a remote that predates the spec change passes the absence through rather than defaulting it, and EDR's RPC response cache replays such an absence once recorded, until its `rpc_cache` is dropped. (Not, as this bullet once implied, because pre-0.20 cache entries keep answering: 0.20.0 moved the cache to `rpc_cache/v2` and ignores the rest. Same conclusion, corrected mechanism.) What the engine does about such a node is REFUSE it, naming the node, rather than silently paying a per-block request the operator did not choose.
