# The merged-ABI refusal follows the decode path, not the event set

`LogEventFetcher` refuses a `topic0` collision (one canonical signature declared twice with different decoding shapes) on the list that DECIDES a decode, and only there: on each per-address ABI ALWAYS, and on the MERGED list of every contract only when that merged list is what `decodeOnto` actually decodes against: when no contract is declared per address (`abiPerAddress.size === 0`) or when `parseAllEventsIrrespectiveOfAddresses` ignores the address. Everywhere else a shared `topic0` with two shapes is TOLERATED: both declarations are kept, each reachable only at its own address, and the shared `topic0` enters the fetch filter ONCE. ADR-0031's rule that the refusal is keyed on `topic0` rather than on the event NAME is unchanged; what moves is only WHERE the refusal is evaluated.

The reason is that the guard's own stated rationale ("nothing on the wire tells them apart") is false for the path the fetcher actually takes. `decodeOnto` resolves which ABI decodes a log by the log's ADDRESS and preselects the member by `(address, topic0)`; the merged list is consulted only on the two branches named above. So where contracts are declared per address, the address IS what tells them apart. The over-broad refusal made an ordinary combination un-indexable: an ERC-721 and an ERC-20 in one source both declare `Transfer(address,address,uint256)` and `Approval(address,address,uint256)`, differing only in their `indexed` flags, so `new LogEventFetcher(...)` threw and nothing over that source could construct. The repo's own conformance workload is exactly that shape (Stratagems as ERC-721, Gems and GemsGenerator as ERC-20), so `captureStream` could not re-capture the source it had committed and the load and replay path could not construct over it. That was recorded at the time as an observation and is discharged by this decision (the note was deleted on discharge, per the `work/` contract; its text is in git history under the slug `the-conformance-workloads-merged-source-cannot-construct-a-fetcher`).

## What ADR-0031 actually forbids, and why this does not do it

ADR-0031 forbids a **parse-config flag deciding WHICH EVENTS EXIST**, because that is what made "the chain had none" indistinguishable from "we never asked": an event spliced out of the global list never entered the fetch filter, so its logs were never requested and its absence afterwards was an absence inferred from a request that was never made. That rule is preserved here, exactly.

Under this change the event SET is IDENTICAL on both paths. Every declared `topic0` still enters the fetch filter, on the per-address path and under `parseAllEventsIrrespectiveOfAddresses` alike, and nothing is ever silently spliced out of it. What became conditional is only the REFUSAL (whether construction throws), and it follows the DECODE path rather than the event set. A refusal is loud by construction and cannot be mistaken for a quiet chain, which is the whole property ADR-0031 was defending; the failure class it names does not exist on this axis.

The one place the two rules meet is the topic-filter loop, and it is settled by a DEDUPE rather than by a throw. That loop built a `topic0 -> event` map purely to assemble the filter list, and its duplicate-`topic0` branch was documented as unreachable because `deleteDuplicateEvents` had already collapsed or refused every shared `topic0`. In the tolerated case it becomes reachable, and the right answer is that a shared `topic0` belongs in the filter ONCE: a request written down twice is not a second event, and logs are filtered by ADDRESS as well as by topic, so both declarations' logs still arrive. Throwing there would have re-introduced the refusal through the back door; splicing would have been the ADR-0031 defect itself.

## Considered options

**Keep refusing, and document a workaround for the conformance source** (split it into one fetcher per contract, as `docs/spikes/replay-parse-cost/` did) was the status quo. Rejected because the combination is ordinary rather than exotic (any source holding an NFT and a token together hits it), and because the workaround is not available on the paths that matter: `IndexerGeneration` builds ONE fetcher over the whole source, and so does `captureStream`.

**Resolve the collision by address at decode time and keep one merged list** was rejected as a bigger change than the problem: it means a second index keyed on something other than `topic0`, on the branch ADR-0031 deliberately left with the one list it has.

**Refuse per address only, and never globally** was rejected because it is wrong on the two branches where the merged list really is the decoder. With no contract declared per address there is no address to resolve with, and under `parseAllEventsIrrespectiveOfAddresses` the address is deliberately ignored; on both, a shared `topic0` with two shapes is genuinely undecidable and silently picking a winner would decode real logs into the wrong shape.

## Consequences

A source that refused to construct now constructs, which is the fix; the honest cost is that the verdict is no longer a property of the ABI alone. Turning `parseAllEventsIrrespectiveOfAddresses` ON for such a source REFUSES at construction, where the same source constructs without it, so that flag now changes whether an indexer starts. That is not the thing ADR-0031 forbids (the event set is unchanged, and the difference is a loud throw rather than a silent absence), but it is a surprise worth stating: the flag says "decode ignoring the address", and a source whose only disambiguator IS the address cannot honour it.

The private `allABIEvents` list may now hold two members answering to one `topic0`, which is safe only because it is read exactly where the refusal still runs. That made "the constructor's condition and `decodeOnto`'s route are the same question" load-bearing, and the two were separately written copies of one expression 190 lines apart, whose drift would be SILENT (the decoder would return the first member matching the `topic0` and write another address's `args` onto the event with no `decodeError`). So the predicate is computed ONCE and stored as `mergedListDecodes`, which also FREEZES the verdict at the instant the refusal was evaluated: `parseConfig` is the caller's object held by reference, and re-reading the flag per log let a mutation after construction move decoding onto the very list that was tolerated as ambiguous. Both properties are pinned structurally rather than trusted.

The per-address preselection map is unaffected: it is built from the per-address lists, whose refusal is unconditional, so no address can still hold two members under one `topic0` and preselection stays interchangeable with the whole-ABI search.

One hazard is WIDENED rather than created, and is recorded rather than repaired. A filter list in `LogParseConfig.filters` is keyed by event NAME, so it applies to every `topic0` that name covers; a tolerated collision gives that name exactly ONE `topic0` covering TWO indexed layouts, and there is no second `topic0` to key the other layout off. A filter constraining a position only one layout indexes (an ERC-721 `Transfer`'s token id is `topics[3]`, which no ERC-20 `Transfer` log has) therefore reaches the other address too and matches nothing there. That configuration used to be unreachable because construction threw. Narrowing it is a different decision from this one, so it is pinned by tests and named here instead of being silently inherited.

Finally, the gate was BLIND to all of this: the conformance suite replays through processors and never constructs a fetcher, so the workload's own source could be un-indexable with every test green. `packages/core/test/sharedTopic0AtDifferentAddresses.test.ts` constructs over the committed fixture's `source` for exactly that reason, which is why a `@etherfold/core` test reaches into another package's fixtures.
