**A deployment restarted with a changed processor goes on APPENDING to the stream it folds, asserted end to end.** This is the closure of the defect ADR-0087 was written for, on the scenario that found it: a `run` stood up over a libSQL handle, stopped, and re-run over the SAME handle with an edited bundle. `packages/cli/test/aRestartedDeploymentGoesOnAppending.test.ts` reads the stored ROWS and the ranges the process asked the node for, because the numbers this family was measured against are only distinguishable in the rows: the defect held `_emissions` at 2 and never moved again, the hand-over that was REJECTED reached 4 where 2 were correct, and what is asserted here is a stream that GROWS from 2 with no log stored twice and no range bought a second time. It also covers the edges the earlier pieces were told not to reach into: a deployment that DOES hold its own incumbent, the reconfigure path through the running endpoint, an UNHELD canonical generation still answering reads from its table namespace and on the feed (ADR-0053), `/status` still reporting one entry per generation HELD, and the stream surviving a second restart that REPLACES what the `successor` slot held, down to the replacing fold re-folding bytes it never fetched.

**`DeclinedReclaim` really does lose `writes-a-followed-stream` now.** The previous release note said so and the union still carried the member: nothing can produce it, because no generation writes a stream since ADR-0087, so a reclaim declines only where the substrate refused the deletion. The operator-facing text that explained the retired decline is corrected with it -- the reclaim endpoint's documented answers (`@etherfold/server`), the server README's description of the verb, and the promotion path's claim that drop-on-promotion still declines the ordinary processor upgrade, which it does not: the superseded generation is dropped and what the deployment keeps is the STREAM. `/status`'s `follows` is documented for what it now means on a receiving deployment (every fold re-folds the stored stream, so every entry reports `true`), and the two remaining places that said a deletion reaps the stream with the generation, or that the generation which INDEXES a stream appends to it, say what ADR-0087 made true instead.
