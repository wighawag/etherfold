One `etherfold-triggers` process hosts several apps from one config (ADR-0101). The config's default export is now `{database?, api?, intervalMs?, apps: {[name]: AppConfig}}`: each app (named by its key, a URL-safe slug) carries its own chain, feed, gate, triggers, actions, verifier and `callTimeoutMs`, and may name its own `database` (the shared one, `file:triggers.db` by default, otherwise; apps naming one URL share one connection). The one-app flat shape and its `name` are removed: a config without `apps` is refused at start with the shape to write, as is an app name that is not a slug. `createNodeService(config)` now returns `{apps, api, tick, run, close}`: one core service per app, every app's registration API mounted under `/{app}/` on one Hono app (the verifier checks the full path the client signed, prefix included, and each app's CORS answers its own origin on its own routes only), and one loop per app run concurrently, so one app's failing or hung round holds only that app. `openDatabase` takes a URL. The CLI's `tick`, `status`, `deliveries` and `journal` cover every app, one JSON line each naming its app (`tick` exits 1 when any app's round failed); `resume` and `requeue` act per app (see `--app`). In the core, a round is bounded: `createTriggerService` takes `maxPagesPerRound` (100 when absent) and `maxDeliveriesPerRound` (the deliverer's batch, 100 when absent), `consumer.catchUp({maxPages})` stops at its bound and returns normally with `hasMore` (the 10 000-page guard now throws only for an unbounded call), a round's report carries `hasMore`, and `run` starts the next round at once after a round that stopped at its page bound.
