A host whose store started from a snapshot answers GraphQL. `@etherfold/state-store`'s `SnapshotAwareStateStore` (what `openSnapshotAware` returns) now offers the query layer's two reads, `accessor(options?)` and `tip()`, wherever the store underneath has them (feature-detected, as the claimed handle `openForWriting` forwards them), so `graphqlQueryHandler` answers from a snapshot-aware store, bootstrapped or not, where it used to answer every query `internal-error`. The accessor keeps the handle's own as-of rule: every read that carries a block (`at`, a relation's children included) is checked against the NARROWED claim first, with the check `getAsOf` and `listAsOf` use, so a block below the installed floor is refused with `BlockNotRetainedError` (GraphQL code `block-not-retained`) rather than answered from rows with no history below it (ADR-0095, ADR-0028); a tip read, and every read on a store never bootstrapped, goes to the store underneath unchanged. `tip()` is the store underneath's. `@etherfold/graphql`'s query conformance suite takes `snapshotTakenAt` (`QueryConformanceOptions`): the block every fresh subject's store was bootstrapped to, under which the case asked of a store with nothing written (`an empty store`) is asked as a store holding no row, pinned to that block, since a bootstrapped store never holds no block.
