# CONTEXT — etherfold domain language

The domain glossary for `etherfold`. Agents and skills use THIS vocabulary when naming modules, tests, and discussing the system. Architectural rationale lives in `docs/adr/` (decisions); product framing lives in `work/specs/`.

## What etherfold is

A modular, TypeScript indexer for Ethereum and other EIP-1193 / JSON-RPC chains that turns a contract's event logs into a derived application **state** via a **processor**, and can run either fully in-browser (client-side indexing over EIP-1193, no server) or server-side. It supports reorgs, caching, and hydrating clients from pre-computed snapshots instead of indexing from scratch.

## Core domain terms

- **IndexingSource** — what to index: `chainId`, the contracts (`abi`, `address`, `startBlock`), optional `genesisHash`. Hashed into the sync context so a source change invalidates stale state.
- **source hash entry** (`SourceHashEntry`, the elements of `ContextIdentifier.source`) — the UNIT invalidation is decided on: one entry per (contract, event, live range), over a leading SKELETON entry at block 0 carrying what an ABI cannot describe (`chainId`, `genesisHash`, each contract's `address` and `startBlock`). Per EVENT whether or not the source declares ranges, because an ABI is REGENERATED and not hand-edited, so what moves in it most often is what nothing depends on: a non-event member (a function, an error, a constructor) contributes to NOTHING, a reorder produces identical bytes (the list is SORTED, not transcribed), and a recompilation that only spells `internalType` differently is invisible because the digest is over `decodingShapeOf`. The rest of the source is NOT free and still invalidates everything. An entry carries TWO digests, because the fetch and the fold do not depend on the same thing (ADR-0034), plus `legacyHash` on the block-0 entry alone: the whole-source digest the pre-per-event code persisted, kept purely so a stored context of that shape can be compared instead of re-indexing every existing deployment once. `legacyHash` is deliberately NOT part of the identity, so "a source whose events did not change hashes byte-identically" is a claim about `{startBlock, hash, streamHash}`.
- **the STREAM verdict and the STATE verdict** (`SourceInvalidation`, `streamMatches` / `stateMatches`) — the TWO answers `sourceInvalidationOf` gives, never one. The **stream** is raw logs fetched under a topic-and-address filter, so it survives everything that did not GROW that filter: a shrunken topic set leaves a strict SUPERSET, which is reusable by decoding less, and a removed event therefore keeps it. The **state** is a fold over DECODED events, so it dies whenever the decoding shape moved, even where not one log needs re-fetching. A renamed non-indexed parameter is the case that proves they are two questions: `topic0` hashes types and not names, so the fetch is untouched and the decode is not. Both halves keep `invalidFromBlock` (the block they are invalid FROM), because the decision naming a block is what lets a reconfigure be a REFINEMENT rather than a rewrite (`work/specs/proposed/a-reconfigure-is-not-an-outage.md`); neither collapses to a boolean. The verdict is PUBLISHED rather than internal: `ReconfigureOutcome.sourceInvalidation` carries it out of `updateIndexer`, and `SourceInvalidation` is exported from `@etherfold/core`, so a caller across the package boundary acts on the HALF and the BLOCK instead of on the one bit `stateDiscarded` collapses them into (it is `undefined` on `updateProcessor` and `reset`, which ask no source question). It is a VERDICT and never a digest comparison: `streamDigestOf` MOVES when an entry is appended above the cursor and that append is FREE (ADR-0034) — the verdict decides WHETHER anything is invalid, the **stream digest** decides WHICH stream a result belongs to. The comparison is a SET DIFF over digests rather than element-wise by index, since an un-ranged source puts every event at the same block and an insertion would otherwise shift the list. What is kept when the stream survives is only its RAW half: `LogEventFetcher.reparse` decodes a replayed stream AGAIN against the source running now, because the stored `args` are what SOME earlier ABI made of those bytes.
- **event block range** (`RangedAbiEvent`'s `firstBlock` / `lastBlock`, `@etherfold/core`) — the span of blocks ONE ABI event is live over, both bounds INCLUSIVE, `lastBlock` omitted meaning open-ended. An event is not a fact about a contract, it is a fact about a contract over a range of blocks, and saying so is what lets an upgrade APPEND an entry describing only the blocks above the cursor, which `sourceInvalidationOf` reads as "this could not have contributed yet" and therefore keeps both the state and the cached stream. It is used for INVALIDATION (as the range half of a **source hash entry**, above) and for WHICH TOPICS a fetched range requests (a range carries only the events whose declared ranges intersect it, unioned per `topic0` across contracts, and issues no `eth_getLogs` call at all where no declared event can occur; an event that DECLARES no range is open-ended from block 0 there, never narrowed on its contract's `startBlock`, so every omission follows from a declaration) and for NOTHING ELSE: decoding is by `topic0` with no block axis, because the boundary is unknowable in advance and not block-granular anyway (the upgrade transaction sits mid-block), and a true `topic0` collision is refused rather than resolved by a boundary — ADR-0033 on top of ADR-0031. Deliberately NOT `startBlock`, which means "do not look before here" per CONTRACT and is MINIMISED across them by `defaultFromBlockOf`. For an upgrade at block `b` the CORRECT declaration is `A.lastBlock = b` together with `B.firstBlock = b`, the same number twice, because a transaction earlier in `b` still fires A; the one-block overlap is preserved, and an exclusive end would make the obvious thing to type lose the pre-upgrade logs in `b`. Ranges are NORMALISED before anything reads them (an open-ended occurrence absorbs the rest from the minimum `firstBlock`; otherwise the union), so the redundant entry a generator appends when it cannot recognise a rollback costs nothing; a GAP between two ranges of one event is REFUSED at construction, because a hole is a span nobody requests. A source declaring no range REQUESTS exactly what it always requested, topic for topic, since nothing narrows until something declares; what it no longer does is hash WHOLESALE, because invalidation is per event either way (ADR-0034 on top of ADR-0033).
- **EventProcessor** — the reducer contract the core drives: `load` / `process(eventStream, lastSync)` / `reset` / `clear` / `getVersionHash`. Given a stream of events, it produces the derived `ProcessResultType` state.
- **JSObjectEventProcessor** (HISTORY; **DELETED**, ADR-0037) — the free-form JS-object reducer authored via `fromJSProcessor(...)` (`on<EventName>` handlers over an immer draft of a plain object, the object IS the state, persisted whole through a **KeepState** keeper). It is what SHIPPED, and it is gone: `@etherfold/js-processor`, the `'js-object'` **processor kind**, the `KeepState` family and the CLI's `--store file` were deleted by `work/tasks/done/retire-the-js-object-processor-path.md`. The word is kept here because it is quoted by ADRs, findings and vendored code that outlive it, and because a reader meeting it needs to know it names nothing current. There is ONE authoring path now, the **ENTITY path** (`EntityProcessor` / `EntityEventProcessor`, the whole of `work/specs/tasked/one-processor-everywhere.md`), which is what this project is FOR. What is NOT lost is the STORAGE characteristic: a plain object with history as immer reverse patches survives behind the proper seam as `@etherfold/state-store-patch` (the LIGHT store). Reorg revert there was `History.reverseBlock`; on the entity path the store owns it.
- **LogEvent** — a decoded (or parse-failed) log with block/tx coordinates; carries `removed: true` when an event is reorged out.
- **LastSync** — the sync cursor: `latestBlock`, `lastFromBlock`, `lastToBlock`, the `context` hashes, and `unconfirmedBlocks` (the recent, reorg-eligible window).
- **reorg / removed / finality** — the reorg model. `generateStreamToAppend` (core engine) shapes the fetched logs into an append stream, emitting `removed: true` markers for reorged-out blocks and pruning `unconfirmedBlocks` past the finality window. Processors consume that stream and revert-then-reapply. WHICH incoming blocks it delivers is decided by MEMBERSHIP of the retained window, by `(number, hash)` — a re-fetched block is NEW unless the window that survived this cycle's retraction already holds it — and never by a HEIGHT, because `unconfirmedBlocks` holds only EVENT-BEARING blocks and is therefore SPARSE: a threshold at the reorged block claims "we already hold everything below this", which is false wherever the chain forked below the lowest block we held logs for, and it silently and permanently lost the new branch's logs in that gap (ADR-0051). It is the same rule the REPLAY path applies, so the two entries agree. (Contract pinned by `packages/core/test/utils.test.ts`, `packages/server/test/reorgBelowTheWindow.test.ts` and `packages/processor-sqlite/test/reorg.test.ts`.)
- **a FETCH is not a REPLAY** (the IN direction of the engine, ADR-0042): the two kinds of input the engine takes, distinguished at the ENTRY rather than inside one function. A **fetch** (`IndexerGeneration.feed`, `StreamBuilder.receive`) is raw logs from a stateless `eth_getLogs`, COMPLETE over a range and carrying no verdicts, so every retraction is DERIVED here by comparing the cursor's window against the incoming blocks by NUMBER. That is why `groupLogsPerBlock` drops a `removed` marker (in a fetch one has no business existing) and why `feed` REFUSES a batch carrying one, exactly as `assertWellFormed` does on the wire. A **replay** (`IndexerGeneration.replay`, `generateStreamFromReplay`) is a stored EMISSION stream, a DELTA that already records what was applied and what was taken back, so the engine HONOURS those verdicts instead of recomputing them from a window a rebuild does not have (a rebuild starts from `freshLastSync`, whose window is EMPTY). This is the IN-direction counterpart of the OUT-direction pair the delivery side already had (`groupLogsPerBlock` in from a fetch, `groupStreamPerBlock` out to a processor). The replay rebuilds `unconfirmedBlocks` by WALKING the stream (an applied block enters the window, a retracted block LEAVES it, keyed by block HASH) and never by filtering the `removed` entries out, which would leave both branches of a reorg at one height and make the first tip cycle after a rebuild apply the replacement block a SECOND time. The same walk is what stops a CATCH-UP replay (a kept state whose stream is ahead) re-applying the finality window it reached back over.
- **stream / keepStream (ExistingStream)** — the cached raw event stream seam, so a client can resume/re-derive without refetching all logs.
- **segment / scanned extent** (`work/specs/tasked/appending-to-the-stream-costs-the-batch.md`, ADR-0035) — how a cached **stream** is stored: an append-only run of **segments** keyed by an ORDINAL index, one per batch, never rewritten, so a save costs its batch and not the history. Ordinal and not block-ranged because the stored stream is an EMISSION stream, so a reorg re-appends superseded events at their ORIGINAL block flagged `removed` and a LATER segment can hold LOWER blocks — ranges overlap, cannot key anything, and no segment may be skipped on a block bound (segmentation is a WRITE-path optimisation; the read stays a full ordered scan). A segment is `{events}` and nothing else: the three block numbers and the `context` live once, in the CURSOR RECORD beside the segments. An earlier design put a per-segment scanned extent there to let a truncated prefix resume; that recovery is withdrawn, and an inconsistent stream (a gap, a cursor without segments, an unparseable segment) is CLEARED and rebuilt rather than repaired. **No segment and no cursor record stores `unconfirmedBlocks`**: the window is READ from the entity path's serialized sync cursor, and a stream keeper's copy is read by nobody, which `captureStream` and `replayStream` already demonstrate by persisting an empty one. A stream is addressed HIERARCHICALLY — `['stream', <indexer-name>, <streamDigest>, <ordinal>]`, as ARRAY keys on IndexedDB, columns on SQL — so enumeration is a SCOPED KEY-RANGE read and never a pattern match over a flat namespace. `chainId` is deliberately NOT an address component: it is already inside the stream digest via the block-0 skeleton entry. The CURSOR is addressed within its stream's subtree, so a scoped delete removes it with the segments and `clear` cannot orphan one. A GAP in the ordinals is CLEARED along with the rest of the stream: inconsistency is not repaired. A CURSOR WITH NO SEGMENTS is not inconsistency though — it is a stream that has been scanned and found nothing yet, and clearing it would re-scan from the start block on every reload. (Filesystem stream storage is deliberately NOT supported, and the *tail* and *seal* it needed are gone with it; OPFS is the plausible next file-shaped keeper and would ride the same seam.)
- **hole** versus **gap** (the stream cache's two damage words, deliberately NOT synonyms) — a **gap** is a missing ORDINAL in the stored segments (`0`, `1`, `3`); it is detectable by reading the keys, and the rule is that any inconsistency CLEARS the subtree and lets it rebuild. A **hole** is a range of blocks the stream never RECEIVED, hidden behind a cursor that claims to cover them: events `[100..5000]` then `[6001..7000]` with a cursor saying 7000. The distinction is load-bearing because a hole is INVISIBLE to the gap check — segments are keyed by SAVE rather than by block, so a save that never happened leaves the ordinals perfectly contiguous — and it is silent, permanent and self-consistent: on the next state discard the stream replays as though it were whole and the missing blocks are simply absent from the rebuilt state. A hole is caused on the ENGINE side (a state that advanced past events the stream never received) and is fixed there, by writing the stream BEFORE processing and not processing a batch that was not saved (`the-indexer-and-its-stream-cache-agree-on-who-is-ahead`); the keeper's forward-jump guard REFUSES a write that would create one rather than repairing it, and is the durable BACKSTOP rather than the arbiter — it compares fetch RANGES, and a batch is a delta against the STATE's window, so after a freeze one routinely overlaps the stored cursor while carrying events that begin above the gap. The engine holds both cursors and is where the question is actually decided: the stream may be AHEAD of the state or level with it, never behind while still being written to, so a FROZEN stream is not appended to again until a rebuild makes the two agree (ADR-0038). Note what is NOT damage: the two cursors DISAGREEING is harmless (a cursor is a coverage claim, not a timestamp per event), and an OVERLAP is ordinary, since every cycle at the tip re-reads the last `finality` blocks. Only a forward JUMP is damage.
- **StateStore** (the STORAGE SEAM, `@etherfold/state-store`) — what a store must do for a processor to run on it: `migrate` / `applyBlock` / `getCurrent` / `getAsOf` / `listCurrent` / `listAsOf` / `revertTo` / `prune` / `readCursor` / `writeCursor` / `clearCursor`, plus the capabilities it declares. Implemented by `@etherfold/state-store-sqlite` (versioned rows over `remote-sql`), by `@etherfold/state-store-indexeddb` (versioned rows in IndexedDB: the BROWSER DEFAULT, decided as a condition in ADR-0024 and selected through `createBrowserStateStore` in `@etherfold/browser`), by `MemoryStateStore` (the reference implementation), and by `@etherfold/state-store-patch` (the LIGHT store: current state as a plain object, history as immer reverse patches, so it declares `revert-only` and `durability: 'memory-only'`). Block addressing by hash or time, and any richer query surface, sit ABOVE the seam and are a backend's own.
- **entity declaration** — `{name, id, fields}`, the whole per-entity contract an author writes. The store owns everything else: the layout, the version columns, the as-of read and the reorg revert. Whether a declaration is LEGAL is a fact about the declaration and not about the backend: the identifier rules (ASCII shape, the reserved `_` namespace, and case-insensitive uniqueness across entity names and across the columns of one row) live at the seam and are refused at DECLARATION time, on every backend. The `_` prefix means NOT A USER ENTITY rather than "the store's", because EVERY fixed table in the system lives there and two packages put tables in it: the store's own `_blocks` and `_cursor`, and the indexer-server's `_meta` and `_emissions`, which share ONE database handle with the entity tables in every combined shape. That is what makes an entity named after a fixed table impossible rather than merely unlikely, through the refusal that already existed and with no host having to declare its fixed names; a test over `packages/server/src/schema/sql/db.sql` keeps the server's half true. A genuinely engine-specific limit (SQLite's `sqlite_` namespace) is refused by that backend, also at declaration time and never at `migrate()`. The one thing no backend may do is accept a declaration and then diverge or die later.
- **version** — one COMPLETE row of an entity with a half-open block-validity range (`_lower` inclusive, `_upper` exclusive, NULL meaning live). `set` writes a whole row, so an unlisted declared field becomes NULL; `delete` closes the live version without opening a new one.
- **MutationContext** — the write surface a handler gets for ONE block (`get` / `set` / `delete`, plus `update` as sugar over get-then-spread-then-set), with read-your-writes inside that block. Uniformly async on every backend. It carries exactly one SET read, the **listing** below. A row read back inside the block that wrote it has the same shape as one read a block later (id columns present, an unlisted declared field NULL): `get` and `list` build a staged row through one construction, so the shape of a row never depends on when it was read.
- **listing** (the bounded id-prefix listing, `MutationContext.list` / `StateStore.listCurrent` / `listAsOf`) — the rows whose declared id starts with a **prefix** (a LEADING run of that entity's id columns, at least one of them), ascending in the id's own order, bounded by a REQUIRED limit, answered as `{rows, truncated}`. Never a predicate, a caller-supplied ordering or an offset: the bound is the decision (ADR-0021), because a handler runs once per event on every backend and a key-prefix range with a limit is the one shape that is an indexed range scan everywhere. It is how a one-to-many is read (children keyed by their parent, collection DERIVED WHEN READ, like a subgraph's `@derivedFrom`), so it costs nothing at write time. Order is lexicographic over the stringified id, so a numeric key must be fixed-width. Distinct from a backend's own richer read surface (`queryCurrent` / `queryAsOf`, caller-supplied SQL), which sits ABOVE the seam where a query planner exists.
- **read surface** (`createReadSurface`, `@etherfold/state-store`) — the reads GENERATED from a set of **entity declarations**, so a consumer names an entity and its declared columns instead of a table and a column string, and a renamed field breaks compilation rather than returning `undefined`. It is the same four reads the seam has (`getCurrent` / `getAsOf` / `listCurrent` / `listAsOf`), typed off the declaration by `declareEntities` (an identity function that keeps the literal types an annotation would widen away), with rows PROJECTED to the declared columns (version columns dropped, an unlisted field `null`) and nothing decoded beyond the declared storage class (ADR-0025). Its as-of parameter is whatever ITS store takes, so a hash reaches a backend that resolves one and does not compile against a backend that does not. Its SERVER-side tier is **`createQuerySurface`** (`@etherfold/state-store-sqlite`): the same four plus `queryCurrent` / `queryAsOf`, which take caller-supplied SQL. Two tiers, one schema source; the split is the same one ADR-0021 makes, because a handler runs once per event on every backend and a server-side reader does not. Distinct from the untyped, entity-name-string read handles `process()` hands back, which split on the same line: **`EntityStateView`** (`@etherfold/processor-entities`) has the seam's four reads and the capability report, and **`VersionedStateView`** (`@etherfold/processor-sqlite`) has those plus `queryCurrent` / `queryAsOf` and block addressing. The SQL pair is absent from the neutral handle rather than stubbed to throw, so asking a backend-neutral handle for a backend-specific read is a COMPILE error in the editor instead of a runtime throw in a browser tab.
- **sync cursor** (the CURSOR PORT, `StateStore.readCursor` / `writeCursor` / `clearCursor`, and `applyBlock`'s third argument) — how far a processor has got, kept BEHIND the storage seam as an **opaque string** under a caller-chosen KEY (ADR-0027). The string is a serialized `LastSync`, and the store knows nothing about that: typing the port with `LastSync<ABI>` would make `@etherfold/state-store` depend on core and invert ADR-0016, so the codec (`serializeLastSync` / `deserializeLastSync`, `@etherfold/processor-entities`) sits above it. It is at the seam and not in a keeper because only the store holds the transaction the block write happens in, so only the store can write the cursor in the SAME transaction as the block it describes; the two used to be separate round trips and the window between them wedged an indexer after a crash. The KEY names WHICH cursor and is NOT the `ContextIdentifier`: the neutral processor writes one fixed key (`SYNC_CURSOR_KEY`) and the context travels inside the value, because the core's discard-and-clear branch only runs when `load` returns something. The cursor is deliberately not versioned, not reverted and not pruned: how far the CALLER got is not entity state.
- **EntityProcessor** (`@etherfold/processor-entities`) — a processor written against the seam: entity declarations plus `on<EventName>` handlers over a `MutationContext`, naming no backend. The ONLY way to author a processor (ADR-0037); `JSObjectEventProcessor` was the same role over a free-form object and is deleted.
- **EntityEventProcessor** (`@etherfold/processor-entities`) — the `EventProcessor` the core drives that runs an **EntityProcessor** against ANY `StateStore`: the store is INJECTED, so the same processor definition indexes to SQLite on a server and to IndexedDB in a browser with nothing about the processor changed. Revert-then-apply, the block grouping, the version hash and the sync cursor live here ONCE. **`VersionedStateEventProcessor`** (`@etherfold/processor-sqlite`) is now a thin SQLite flavour of it: it builds the store from a `RemoteSQL` and substitutes the SQL-tier read handle, and holds no indexing logic of its own.
- **processor kind** (HISTORY; the concept is DELETED, ADR-0037) — WHICH of the two authoring paths a deployment was running, said by the caller as a TAG rather than sniffed: `'js-object'` (a **JSObjectEventProcessor**) or `'entities'` (an **EntityEventProcessor**). There is one path, so there is nothing to discriminate: `createIndexerState` (`@etherfold/browser`) takes the processor itself — or, since the generation container landed, the two FACTORIES that build one (`{createState, createProcessor}`), which is what every caller in this repository passes — and a processor MODULE loaded by a host (`instantiateProcessor`, `@etherfold/utils`) returns the AUTHORING object itself rather than `{kind, processor}` (which superseded ADR-0039). A module still returning the tag is REFUSED rather than unwrapped, so the retired shape cannot reach a store that would ask it for its `entities` and get `undefined`. The word is kept here because ADR-0039 and several done tasks are written in it; do not reintroduce it for a second STORE or a second BACKEND, both of which are their own axes (`--store`, `BrowserStateStoreConfig`).
- **retention** — how far back superseded versions are kept, measured in BLOCK NUMBERS and in no other unit (never a duration, never a count of updates: ADR-0019). Its floor is the finality depth, because reorg revert already requires that much. A deployment SETS it (`'revert-only'`, `{blocks: N}`, or `'unbounded'`) and a store REPORTS what it actually provides, so a caller discovers at startup what history is available instead of from a wrong answer. Note the trap: a window of N BLOCKS is not N updates of history (median 429 blocks between event-bearing blocks on the real measured stream).
- **prune** (`StateStore.prune`) — enforcing **retention** against STORAGE rather than against answers. A window bounds what a read may ask about from the moment it is configured (`assertRetained`); `prune` is what physically drops the versions it no longer covers, at the same boundary (`retentionFloor` is `retainedRange(...).from`, so the two cannot drift). It is an EXPLICIT call the host schedules and never a side effect of a write, because it costs time proportional to what it drops (ADR-0022); it is a no-op where there is no floor; and the LIVE version of an entity survives it however old it is, because that row is the current state. Distinct from the two other prunes in this repo: the core prunes `unconfirmedBlocks` past the finality window, `History` prunes reverse-patches by block distance, and the (unbuilt) `snapshot-prune-script` prunes orphaned CLI snapshot FILES, which is a different object entirely.
- **bootstrap** (`openSnapshotAware` / `StateSnapshot`, `@etherfold/state-store`; `bootstrapFromSnapshot` / `openAndBootstrap`, `@etherfold/processor-entities`) — starting a store from state somebody ELSE computed instead of replaying the chain from the start block. A **snapshot** is `{format, processor, savedAt, takenAt, cursor, rows}` where `rows` are the rows that are LIVE at `takenAt` (current rows only, measured: ADR-0028), and the rows and the cursor install as ONE `applyBlock` because a client that crashed mid-install must not come up holding rows it cannot account for. There used to be a second shape of the same word: the free-form path's snapshot, the whole state blob in the CLI's file envelope, whose FORMAT number a client that cannot read it REFUSED rather than translated (ADR-0040, `BLOB_SNAPSHOT_FORMAT`). That envelope, its writer (`--store file`) and its reader (`keepStateOnIndexedDB(name, remote)`) are DELETED with the free-form path (ADR-0037), so ONE snapshot shape is left and `ENTITY_SNAPSHOT_FORMAT` at the seam is the only envelope number. ADR-0040's rule is unaffected and is what the surviving reader still does. What has no free-form counterpart is the honesty a blob does not need, because a blob has no history to lie about: a snapshot carries NOTHING below its own block, so a bootstrapped store reports its **retention** as a window whose oldest block is the snapshot's (its **snapshot origin**, persisted under a second cursor-port key so a RELOAD is as honest as the first run), refuses an as-of read below it with `BlockNotRetainedError`, and refuses a revert reaching under it with `RevertBeyondSnapshotError` — which is deliberately NOT a `BlockUnavailableError`, on the same ground as `RevertBeyondPatchHistoryError`: that family is about a read this store cannot answer, and this is the write path, where the reorg was not undone. Client-side selection was the free-form keeper's, point for point (several locations, most advanced wins, prefer local when local is ahead, fail over on error), plus two things that keeper did not do: it walks every remaining candidate on failover, and a snapshot from another **processor version** is not a candidate at all. PUBLISHING snapshots is deliberately out of scope (`work/notes/ideas/publishing-snapshots-of-versioned-state.md`); `createSnapshot` is the minimal producer the tests need, and it cannot read rows out of a store because the seam has no "list everything" read (ADR-0021).
- **BlockUnavailableError** — the family of "this store cannot answer about that block", ADR-0015 and ADR-0019. `NoSuchBlockError` (the address resolves to no recorded block) and `BlockNotRetainedError` (the block is fine, the versions are outside retention) are its two members. Neither is ever an empty result or a tip read: an as-of read served from the tip is a plausible wrong number nothing downstream can tell apart from a true one. Deliberately NOT a member: **`InvalidBlockNumberError`** (a `TypeError`, thrown by `assertBlockNumber` inside `assertRetained`, and by the SQLite addressing layer's height axis), because every member of the family is a fact about the STORE that a caller answers by re-pinning or widening retention, while an `at` that is not a whole non-negative number is a fact about the CALL that no store configuration makes answerable.
- **conformance suite** (`@etherfold/state-store-conformance`) — the one suite a **StateStore** backend must pass to earn its place behind the seam, parameterised by a factory. It asserts EXTERNAL behaviour only (what a read returns after a write, after a revert, as of a block), never a table, a statement or a version column, so a versioned-rows backend and a patch-log backend can both be asked it; and it reads a backend's declared **capabilities** first, so each backend is tested against its own CLAIM. Its cases are data (a `{group, name, run}` list) with the vitest registration as a thin adapter, which is what lets deliberately-lying backends be asserted to FAIL it (ADR-0020). Distinct from a conformance WORKLOAD, below.
- **conformance workload** — a SUBJECT fed to the backends the conformance suite covers, as opposed to the suite's own questions. Two exist: the small hand-written declarations inside `@etherfold/state-store-conformance`, and the heavy one, **`@etherfold/conformance-workload-stratagems`** (its own package, `private` and never published because its vendored oracle is GPL-3.0 and the port is a derived work of it: ADR-0026), which replays 31,332 real logs from the LAUNCHED stratagems game on Base through the ported processor and compares against the state that game's ORIGINAL `JSProcessor` computed from the same bytes. Its parts are a golden INPUT (a committed `StreamFixture`) and a golden OUTPUT (the state the original computed; a diff on it means the processor changed meaning, which is a FINDING and not a fixture update). The golden output is now FROZEN rather than recomputable: driving the vendored original needed the deleted free-form path, so `src/oracle.ts` and the regeneration script went with it (ADR-0037). The vendored source stays, typechecked and unrun, because it is what the goldens' claim rests on; a diff is triaged by READING it rather than by re-running it. Note the trap it carries a label for: stratagems has two deployments on Base and `deployments/base` is the ABANDONED one (45 logs), while `deployments/alpha1` is the launched game.
- **tx inclusion** (`checkTxInclusion`, `@etherfold/core`; `createIndexerState(...).checkTxInclusion`, `@etherfold/browser`) — whether the state a client is about to render already accounts for a given transaction, which is what an app must know before it lays an OPTIMISTIC update over indexed state: applied on top of a state that already contains it, a non-idempotent update (a counter, a balance, an append) is counted twice. Answered from `LastSync.unconfirmedBlocks` and NOTHING ELSE stored: the window already holds whole blocks with their events, every event carries its `transactionHash`, and the set maintains itself under reorg because a reorged-out block leaves the window. Deliberately NOT answered by comparing the caller's receipt: a block HEIGHT is a local opinion about a chain rather than an identity, and the receipt's block HASH is the wrong identity, since a reorg can re-include the same transaction in a different block, so a hash comparison reports "not indexed" for a transaction that IS indexed, which is the double-count it was meant to prevent. The question is about the indexer's own chain, so only the indexer answers it. Two things make a verdict rather than one: a window hit must ALSO be behind `lastToBlock`, because `feed` publishes the whole new window and only then walks the cursor through it, so presence is not application. Its two documented limits both follow from the window being SPARSE (event-bearing blocks only): a transaction that emitted nothing indexed can never hit (`work/notes/ideas/tx-inclusion-for-a-tx-that-emitted-no-indexed-event.md`), and `absent` means "not in the window", so the caller must not ask about a transaction older than it — which one it just submitted cannot be. The optional `minedAtBlock` closes both for a caller that has a receipt, through the `below-window` branch, which rests on the same finality assumption the indexer already makes when it prunes.
- **KeepState** (HISTORY; **DELETED**, ADR-0037) — the whole-state-blob persistence seam (`fetch`/`save`/`clear` over `{state, lastSync}`) that backed the free-form path in IndexedDB, in localStorage and on the filesystem, and the shape a published blob snapshot hydrated a client from. It had exactly one caller, `JSObjectEventProcessor.keepState`, and it went with it: the SNAPSHOT half did not need keeping, because the entity path's **bootstrap** never used it (its counterpart is `openSnapshotAware` / `bootstrapFromSnapshot` at the storage seam, which is where a store's own transaction is). Nothing persists through a keeper now: a processor persists through its **StateStore**, which writes the **sync cursor** in the same transaction as the block it describes (ADR-0027).
- **createAction** — the internal promise-serialization primitive in the core `IndexerGeneration` (`_index`/`_feed`/`_load`/`_save`) that keeps overlapping load/feed/index calls from interleaving.
- **work/ contract** — the on-disk system this repo uses, defined by the reference docs in **`work/protocol/`** (copied here by `setup`). Three REGIME umbrellas — `notes/` (capture buckets: `observations`/`ideas`/`findings`), `tasks/` (the build board: `backlog`/`ready`/`done`/`cancelled`), `specs/` (the spec lifecycle: `proposed`/`ready`/`tasked`/`dropped`) — plus top-level `questions/` and `protocol/`. One markdown file per item, status = the folder it lives in (never a field). ADRs (`docs/adr/`, format in `work/protocol/ADR-FORMAT.md`) record what WE decided and why.

- **generation** (`work/specs/proposed/a-reconfigure-is-not-an-outage.md`) — ONE indexed lineage: a **stream** plus a fold over it. Identified by its STREAM plus the processor's `version` hash — the config hash is already inside the stream digest, so naming it again would be redundant. A PROCESSOR change is therefore a new generation over the SAME stream (and re-fetches nothing) while a FILTER or CONFIG change is a new stream. An indexer holds several; one is canonical. **Two fields INSIDE the system and ONE opaque value on the way out**: the registry keeps `{stream, processor}` apart because it KEYS on them, while anything REPORTING which generation answered renders them through `generationDigestOf` (`@etherfold/core`) — the indexer-server's two feed views advertise exactly that, as `generation`, on every response — so that a consumer compares the value and never parses it, and what a generation is composed of stays changeable. The word is deliberate and every obvious alternative is taken: `version` already means an entity row's half-open block-validity range AND a processor's `version` field (which is an INPUT to a generation's identity, so the same word would mean two things one sentence apart), `deployment` already means the fetcher/server topology and a browser installation, and `candidate` is taken by the entity snapshot path. Reconfiguring CREATES a generation instead of discarding state; **blue-green** (ADR-0008) is the two-at-a-time special case of the same mechanism.
- **follower** (`IndexerGeneration.followMore`, `HeldGeneration.follows`) — a non-canonical **generation** on a SHARED **stream**: one that folds a stream ANOTHER generation is indexing into. It fetches NOTHING — zero `eth_getLogs`, not fewer — and writes no segment: it re-folds the stored stream from the start and then follows it as the indexing generation appends. **Whether a successor is a follower is DETERMINED by whether it shares a stream, and is never a configuration knob** (ADR-0044, `Indexer.add`): a flag would be wrong in both positions, since "follow a stream nobody writes" never advances and "fetch a stream somebody else writes" is a second writer. It is also the only shape that keeps a generation being "a stream plus a fold over it" — a follower with a head-following poller of its own would make its state a function of ITS OWN FETCH, so re-folding the stored stream later would give a DIFFERENT state and the promise that moving the **canonical pointer** back restores answers EXACTLY would die with it. The **one-writer rule** is that only the INDEXING generation appends to a stream, and it is structural rather than conventional: the writer is handed the keeper, every follower is handed a **read-only stream view**. Which generation writes a stream is the OLDEST SURVIVING generation registered on it (`writerOf`, `@etherfold/core`; registration order and never the pointer), so promotion does not hand the append duty to a different engine mid-flight, and DELETING the writer hands it to the next oldest rather than leaving a stream nothing appends to. That restates ADR-0044's "the first one held" rather than replacing it (at the start the oldest survivor IS the first one held; see its 2026-09-05 amendment), and succession is atomic with the delete because the writer is DERIVED from the records and stored nowhere. Distinct from a generation on a DIFFERENT stream, which is not a follower at all but an ordinary indexer at a different address, fetching its own history into its own keyspace.
- **read-only stream view** (`readOnlyStream`, `@etherfold/core`) — an `ExistingStream` whose `saveNewEvents` and `clear` are NO-OPS. It exists because READ and WRITE share ONE seam: a generation handed the stream to fold is handed the thing that also appends, and the engine's save is UNCONDITIONAL, so "a generation that merely reads" is not expressible by declining to write and is not expressible by configuration either. The writes are no-ops rather than refusals because the engine does not process a batch it could not write, so a refusing keeper would freeze the fold rather than leave it read-only; and `clear` is a no-op for a sharper reason than symmetry, since the load path clears on every stream shape it cannot use and a **follower** takes those branches over a stream another generation is still indexing into. `replayStream` (a captured **StreamFixture**) is the same view over a different reader, not a second implementation.
- **pause / draining** (`IndexerGeneration.pause` / `resume` / `pauseState`, `Indexer.pause(id)`, ADR-0045) — how a **generation** STOPS indexing without being deleted, and the two words are one mechanism. **Pausing** sets `maxToBlock` to the generation's cursor and does NOTHING else: it caps `toBlock` and it truncates nothing, reverts nothing and never reaches `revertTo`, so what a paused generation answers is exactly what it answered at the instant it paused — which is what keeps it revertible-TO, since moving the **canonical pointer** back to it must restore its answers EXACTLY (story 4). **Draining** is the period of continued LIGHT POLLING that follows: while the cap is inside the reorg window the existing `getFromBlock` re-scans a SHRINKING `[latestBlock - finality, cap]` and corrects any reorg touching what is held, and once the cap falls below `latestBlock - finality` that same function asks for a block ABOVE the capped `toBlock`, so the indexer takes its existing `fromBlock > toBlock` "no new block" branch and fetches nothing. So there is no new mechanism, no timer and no state machine, and `pauseState` (`running` / `draining` / `drained`) is DERIVED from the cap and `getFromBlock` rather than stored. What it is NOT: not INSTANT (up to **finality** blocks of polling, and only while a driver keeps calling `indexMore`), not `disableProcessing()` (which stops the engine where it stands, carrying an unconfirmed window it can no longer correct — the hazard draining exists to remove), not durable (a reload comes back running), and not applicable to a **follower**, which fetches nothing and has no `toBlock` of its own to cap (`CannotPauseFollowerError`; pausing a stream's WRITER is what stops everything following it, ADR-0044). Note the one honest cosmetic residue: `unconfirmedBlocks` may still LIST blocks once drained, because the re-add rule compares against the frozen `lastToBlock` — every one of them is final, and clearing it would be the truncation this rejects.
- **stream identity** — a stream is identified by its FETCH FILTER, never by who indexed it: a wide synchronous digest over the DEDUPLICATED `streamHash` values SORTED BY `streamHash` (address, `topic0`, range — see **source hash entry**), PLUS the stream CONFIG hash. Both halves matter. Sorting by `streamHash` rather than taking the entry list in its own order is load-bearing: that list is sorted by `(startBlock, hash)`, and `hash` covers the DECODING shape, so a decode-only change reorders it and a digest over that order would fork a new stream and re-fetch everything. The config belongs because `sourceInvalidationOf` invalidates the STREAM from block 0 on a config mismatch, and `alwaysFetchTimestamps` and `alwaysFetchTransactions` each change what is STORED. `parse` belongs too, on the strength of `parseConfig.filters`, which narrows which events are parsed and kept at all. (`parse.logValues` was a third reason and is DELETED with the knob by `work/specs/proposed/the-stream-stores-only-what-the-node-said.md`: an unused stub whose only purpose, reducing what is stored, that spec removes. Nothing about this hash needs narrowing as a result.) This is ADR-0006's `{source, config}` stream keying made concrete, narrowed on the source side to the FETCH half per ADR-0034. Not `simple_hash`, which is 32 bits: as a change DETECTOR a collision costs one missed invalidation, but as a KEY it means one generation silently adopting another's stream under a filter that does not match it. Two generations may READ one stream; only the one indexing WRITES it.
- **exploration spec versus build spec** (`work/protocol/TASKING-PROTOCOL.md` §2a) — the two SPEC KINDS, distinguished by what DONE means. A **build spec**'s done is the capability SHIPPED, tasked atomically as vertical tracer-bullet tasks. An **exploration spec**'s done is CONFIDENCE plus a de-risked, sliced BUILD PLAN: its stories are reach-confidence stories (pin the seam, spike the risky part on the narrowest real case, resolve an open question into a decision, emit the plan), and the capability build becomes a FOLLOW-ON build spec ordered by `taskedAfter`. The reframe is what stops a too-uncertain ambition being tasked as FICTION — build tasks written against a seam nobody has chosen. `a-generation-can-be-seeded-from-a-published-artifact` is the worked example: it was a build spec whose Implementation Decisions read "None yet, deliberately" and two of whose four questions were seams that do not exist. An exploration spec is still just a spec in `work/specs/`, tasked atomically like any other; it adds no folder and no status.
- **generation cap** (`maxGenerations`, `maxStreams`) — a COUNT of generations or streams an indexer may accumulate, which REFUSES at the bound rather than evicting. Deliberately NOT called *retention*: **retention** is pinned below to a distance in BLOCK NUMBERS and ADR-0019 refuses a second retention mode measured in anything else. The two meet in one config object — every generation HAS a store WITH a retention window — so they must not share a word.
- **indexer** (the NAMED unit; the server and CLI multi-tenancy unit) — one indexed **answer set**: a set of generations and streams over ONE chain, holding ONE **canonical pointer**, carrying the **generation caps**, and fully isolated from every other. An indexer-server or a CLI hosts SEVERAL, each under a NAME the operator supplies at DEPLOY time (`--indexer` / `INDEXER_NAME` on every command that folds or addresses a fold: required on `etherfold fetch` and `etherfold index`, optional and defaulted on `run` and `build`, which fold under a name without routing by one; on `upload` when that verb exists); a BROWSER APP may also run several, naming them itself. **The name is UNIVERSAL, not a server-only concept** — one discriminator, two sources of its value — and it is the top level of the stream address everywhere, so no runtime needs an extra one. The browser case is not hypothetical: an app watching several accounts (an NFT viewer) names one indexer PER WATCHED ADDRESS, which is the right modelling because those datasets are PARALLEL and equally valid, with no canonical among them. Do NOT model that as generations: a **generation** is an EVOLUTION of one logical thing with ONE canonical answer, so a filter that identifies a different subject is a different INDEXER, while a filter change that refines the same subject is a new generation of it. On the server the name is a ROUTE SEGMENT (`/{indexer}/ingest`) and a NAME-KEYED REGISTRY entry (`ServerOptions.getIndexer`, resolving an ENTRY OBJECT so what a name holds can grow), and it is deliberately NOT a field in the ADR-0004 envelope: carrying tenancy in the wire format would turn a misdirected batch into a payload error rather than a routing one, so a name a host was not built with is a `404` and never a default to the one it does hold. The discriminator is STRUCTURAL, part of a composite key every server-side read and write takes, and never a field a query may omit. **Never DEFAULTED is the narrower rule it looks like**: it is a rule about ROUTING, so it binds the wire absolutely (a name a host was not built with is a `404`) and does not reach a combined process, which routes nothing and needs a name only to KEY the stream it stores, so it defaults one there (ADR-0052). It is the same hazard class the client side removed by addressing a stream HIERARCHICALLY rather than packing its components into one delimited string, where a discriminator a read can omit, or one packed so that something else can be mistaken for it, silently answers with another tenant's rows.

  **The word is deliberate, and what it REPLACED matters more than what it beat (ADR-0036).** An earlier design called this a *project* and treated it as a second axis ABOVE the indexer. That axis was deleted rather than renamed, because once an indexer is one chain and one answer set the two units are THE SAME THING, and the glossary already said so in every place that counted: an indexer holds several generations, one is canonical, and the caps are per indexer. `instance` was rejected as filler that implies a running copy (this persists with nothing running), `dataset` as inventing a word where one existed, and `deployment` was already taken twice over. The residual cost, accepted and now PAID: the class that was one source plus one processor plus one state is a GENERATION rather than the container, so the class is **`IndexerGeneration`** and the container is **`Indexer`** (`@etherfold/core`, `container.ts`). The old name it shipped under is DELETED rather than kept as an alias, and so is the call shape that handed a hook one already-built processor over one already-built store: an indexer holding several generations can never be handed either, so there is one name and one call shape.

  **One name is one chain at a time.** `chainId` is NOT an address or key component anywhere — not in the client's stream address, not as a column on the server's emission table — because it is already carried inside the STREAM identity both are keyed on (its block-0 skeleton entry hashes `chainId` and `genesisHash`). Two chains therefore produce different stream digests and cannot collide, with no guard needed. It is not an identity axis in its own right: changing an indexer's chain changes `chainId` and `genesisHash` in the block-0 skeleton entry, hence the source hash, hence the STREAM — so it is an ordinary reconfigure that makes a new generation, with the old chain's generation retained under the caps and revertible. Two chains you want live SIMULTANEOUSLY are therefore two names, because under one name the second would be read as a successor and not a sibling. Two contract deployments on ONE chain are likewise two names, since a single canonical pointer can only name one generation (stratagems' `alpha1` and the abandoned `base` are the worked example). Whether the discriminator maps to a shared table with a column, a table prefix, or a schema is a storage-ADAPTER decision, and it stays one only because the key is composite.
- **canonical pointer** — the single record naming which **generation** answers reads. Moving it IS promotion and moving it back IS revert; it is one small write, which is why promotion has no meaningful cost. Its policy has three values and ONE default everywhere (`PromotionPolicy` / `resolvePromotionConfig`, `@etherfold/core`): **`on-catch-up`** (the default — the pointer moves when the successor reaches the canonical generation's cursor), **`immediate`** (canonical on creation, before catching up; OPT-IN, for a developer who wants to see what an edit did) and **`manual`**. There is deliberately NO per-environment default: that would need a development-versus-production distinction, and nothing in a browser build can detect one, so the safe value is the default and the unsafe one is chosen explicitly. Reads RE-RESOLVE the pointer once per read unit of work and hold it, so a query cannot straddle a promotion. What the policy governs is the move the container makes ON ITS OWN: `Indexer.promote` (and therefore the revert) is never gated by it, and `manual` means "only when asked" rather than "never".
- **the promotion TRIGGER, and DROP-ON-PROMOTION** — the trigger is the successor reaching the cursor the CANONICAL generation has, compared LIVE rather than against a snapshot taken when the successor was created (a snapshot would let a successor be promoted while the incumbent had moved on, which is the state going backwards the default exists to prevent). Being a CANDIDATE for that move is armed by `Indexer.add` — creating a generation beside the live one is what asks for it — and is deliberately NOT "any non-canonical generation that is level", which would re-promote a successor on the cycle after a REVERT; like a **pause**, the arming is in memory, because the registry records what a generation IS and this is what a container is DOING with one (ADR-0046). **Drop-on-promotion** is discarding the superseded generation at the promotion. It is OFF by default (retaining is what makes the pointer moving BACK a revert rather than a re-index), and where it is on it applies only under `on-catch-up` and `manual`, where the promotion demonstrated something: under `immediate` the previous generation is RETAINED until the successor reaches the cursor it had at the promotion, resolved by ORDER rather than by an interlock. It never drops a generation that WRITES a stream another held generation follows, because the writer is the first generation held on a stream and promotion does not move that duty (ADR-0044), so dropping it would leave its follower folding a stream nothing appends to.
- **seeding** — creating a generation from a published artifact instead of backfilling from the node, which for a user-facing browser app is the PRIMARY path rather than a fallback: on a public node the backfill is frequently impossible, since old logs are not served at all. Two shapes, not equivalent: a captured **stream** (`captureStream` / `StreamFixture` / `replayStream`, which already returns an `ExistingStream`) seeds the stream, so later generations can still re-fold from it; a state **snapshot** (ADR-0028, `bootstrapFromSnapshot`) seeds the FOLD and reports a retention floor at its block, so a snapshot-seeded generation is a LEAF and cannot serve a later processor-only change.

## What must work FIRST

- **The COMBINED deployment is the milestone; the SPLIT is a deployment choice.** ADR-0003 divided the system into a **log-fetcher**, a **stream-builder**-plus-processor and a read surface, and every spec since is written per component, so the tree reads as though the split were the goal. It is not. The thing that must work end to end first is ONE process that follows a chain, folds into SQLite and answers HTTP, on any Node runtime — `work/specs/ready/one-command-runs-the-whole-pipeline.md`, whose `run` command is exactly `fetch` plus `index` in one process via `createDirectIngestion` (that spec renamed the commands twice; `serve` now means ONLY the read-only tier, see the next bullet). Splitting is then a deployment decision an operator makes when the chain-facing host and the serving host genuinely differ, and it costs no rewrite because the transport is the only difference. The browser deployment is the other first-class target and is already reachable.
- **The COMMAND SET names deployment intents, not components** (`one-command-runs-the-whole-pipeline`). **BUILT.** All five names exist in the CLI and each carries its final meaning and its final promises: **`run`** follows the chain, folds and answers queries, on one libSQL handle — the milestone and the default thing to reach for; **`build`** does the same but EXITS at the tip, producing a database or a publishable artifact; **`fetch`** is the chain-facing half, stateless, holding no cursor and no database, pushing contiguous ranges to a receiver elsewhere — and the ONLY way to run a fetcher, since the standalone `etherfold-fetch` binary was retired with it; **`index`** is the folding half, receiving those pushes and owning the database (it exposes `/{indexer}/ingest`, the WRITE path, and not the query API, and it makes no chain call, which is why its source must be given explicitly); **`serve`** is the read tier, which holds no processor, writes no indexed state and answers over a database written elsewhere. There is no DEFAULT command: a bare `etherfold` prints help, so no invocation silently means one of the five. Where an older artifact uses `serve` for the all-in-one or says "watcher", it predates this and the glossary is what to land on. Two compositions hold in the code rather than in prose, and are asserted at the COMMANDS (`packages/cli/test/equivalence.test.ts`: the same processor, the same declarations and one fixture chain including a reorg, landing on identical state and an identical cursor): `run` IS `fetch` plus `index` plus `serve` in one process (the first pairing is `createDirectIngestion`), and `build` is `run` without the serving. Three naming rules worth keeping: `serve` means ONLY serving, because spending that verb on the all-in-one is what left the read tier unnameable; `index` is the FOLDING half, because the fetching half holds no cursor, no state and no database and so has the weakest claim to the project's central verb; and a split deployment is `index` plus `serve` against ONE database, which falls out of the set rather than needing explanation. The indexer NAME is BUILT and is required on both halves of the wire (`--indexer` / `INDEXER_NAME`): `fetch` addresses `/{indexer}/ingest` and `index` registers exactly that name, refusing every other with a `404`. It is OPTIONAL on `run` and `build` and defaults there (`default`, ADR-0052), because those two hold a name without ROUTING by one — every row of the stream they store is keyed on it — and only the routing use may never be defaulted; `serve` refuses it outright, folding nothing and registering nothing. What a CLI process still holds is ONE named indexer, and a HOST registering several is a registry with more entries in it rather than a change to the route (`the-server-and-cli-hold-generations-too` owns the generations inside an entry).
- **The QUERY LAYER is deferred, deliberately.** `/status` is the whole query surface for that milestone: today the reorg counters, the schema version, health and the last error, plus the CURSOR, which arrives through `getCursorReport`, a reporter injected beside `getDB` (the server has no store dependency, and the cursor is opaque behind the seam per ADR-0027). The SEAM and the field are built: `/status` reports `cursor: {reported: true, value}` verbatim from whatever the host's reporter returned, `{reported: false, reason}` when a reporter fails, and NO field at all on a host that injects none (the Worker host). It is an object rather than a scalar so a later host can grow a per-generation dimension inside it (ADR-0047). The commands that inject one are the ones that OWN a store and also serve — `run` and `index` — which is why a split deployment's writer reports progress and its read tier (`serve`, given no reporter) reports no `cursor` field at all: that is correct rather than missing, since only the process that owns the store can read one. A richer layer is decided in principle (Hono, Yoga, Pothos over **entity declarations**, with `one-processor-everywhere` guaranteeing the schema source) and is NOT imminent. Several specs name it as their consumer; none of them should be read as evidence that it is being built.

## Server-side architecture terms

The server-side split (decided in `docs/adr/0003`-`0008`; partly built). "Processor" keeps the meaning defined above (`EventProcessor` / `EntityProcessor`, the reducer) and is NOT the name of a deployable.

- **log-fetcher** (`LogFetcher`, `@etherfold/core`) — stateless, chain-facing. Calls `eth_getLogs` and pushes contiguous block ranges of raw logs. Holds no cursor, no unconfirmed window, no reorg logic, so it can be restarted or replaced freely. One operation, `fetchAndPush()`; WHEN it runs belongs to a **fetcher host** (below), which is why it names no runtime and schedules nothing. Every chain call in a split deployment is here, including the `eth_chainId` check the chain-free receiver could never make. What it keeps between cycles is a HINT, not a cursor: the last `expectedFromBlock` the receiver reported, never persisted, dropped whenever a push fails, and corrected by a `409` — so losing it costs one request. Its transport is **`createHttpIngestion`** (same package), which maps status codes onto the two refusal families: `409` is resumable, the rest of the 4xx family is an `IngestionRefusedError` surfaced at once, a `5xx` or an unreachable server is an `IngestionUnavailableError` retried with bounded backoff.
- **a partial range is never pushed** — the sending rule of ADR-0004, and the most dangerous thing the log-fetcher can get wrong. A payload holds EVERY log in `[fromBlock, toBlock]`; truncation is expressed by LOWERING `toBlock`. An ANNOUNCED result cap shrinks the range (`RangeLogFetcher` reports how far it really got, as `toBlockUsed`); a SILENT one — exactly the cap back, no error — is treated as suspect rather than as an answer, so the range is halved until the count is under the cap, and a single block still landing on it is a `SuspectedTruncationError` and nothing is pushed. **The silent case is detected by matching the cap EXACTLY and cannot be detected otherwise**, since a capped answer and a complete one differ in nothing else: so `suspectResultCount` is a deployment's responsibility to set to its node's real cap (it defaults to 10000, the common one), and it is NOT `fetch.maxEventsPerFetch`, raising which widens the span asked for and makes truncation likelier. The reason is the receiver's inference: it cannot tell a short payload from "no logs there", so it would conclude an absence, and an absence is a reorg, and a reorg deletes state (the bug in `d24872f`).
- **fetcher host** (`@etherfold/fetcher-host`, plus `platforms/nodejs-fetcher`): the layer that decides WHEN a fetch cycle runs, which is the only platform-specific thing about fetching. The shared package holds everything that is not scheduling: the configuration a deployment supplies, the classification of a cycle into the five things a scheduler can act on (`progress` / `idle` / `contended` / `retry` / `fatal`), the wait after each, and the loop that drives them (`runFetcherLoop`). An adapter adds a runtime and nothing else, and must add nowhere to remember a block number. There is ONE schedule shape because driving the chain needs a host that can hold a PROCESS: a serverless trigger fires on a schedule rather than continuously and caps an invocation well below a first sync, which is why the serverless runtime here hosts the receiving half and not this one. Three of the five reports are not failures: `idle` (`up-to-date`) and `contended` (`yielded`) mean back off rather than alert, and only the ERROR's own `retryable` decides between `retry` and `fatal`. A host that re-derived that from a status code would retry a bad token forever. Distinct from the **log-fetcher** itself, which is the cycle; a host is the clock.
- **the wire is a deployment choice, not two implementations** (`createDirectIngestion` / `createHttpIngestion`, `@etherfold/core`): both sides of ADR-0004 are INTERFACES (`IngestionTarget` for the sender, `LogIngestion` for the receiver), so the same `LogFetcher` and the same `StreamBuilder` run split across a network or together in one deployable, with the transport as the only difference. `createDirectIngestion` is that second case in about eighteen lines: the receiver still owns the cursor, still derives every reorg and still refuses a batch that does not start where it says, because none of that came from HTTP. The one thing it must get right is that `UnexpectedFromBlockError` comes back as a CORRECTION rather than as a throw (the in-process `409`), recognised structurally so a second copy of the package cannot turn the resumable refusal into a crash. **Which shape goes where**: the COMBINED one is for a host that can hold a process (Node), where the network between the halves buys nothing; the SPLIT one is for a fetcher on such a host pushing to an indexer-server anywhere, including a Worker, which serves that half well. What is NOT a shape is a serverless fetcher of either kind, combined or fetch-only: a cron cannot follow a chain.
- **stream-builder** (`StreamBuilder`, `@etherfold/core`) — receives those ranges, is authoritative about where the next one must start (`expectedFromBlock`), derives reorgs, and REPORTS the **emission stream** it produced (`IngestionOutcome.emissions`) together with the `streamDigest` it belongs to, so a host can store it. It does not store one itself and it does not leave storing one to an entrance either: the server's `_emissions` table (append-only, retractions included, superseded rows flagged; ADR-0006) is written from INSIDE `receive`, through an `EmissionAppender` the store's owner injected and closed over the NAMED INDEXER that host holds (ADR-0052) — the same placement ADR-0050 gave the reorg count, and for the same reason, since what a fold concluded is not a fact about the transport. It was the ROUTE's, on the ground that half of that table's key is the indexer name and a route segment was the only place that value existed; making that name resolvable on a combined shape is what removed the obstacle, and a `run`-produced database carried an EMPTY emission table until it did. **The ORDER is the one thing the two ports do not share**: the count is taken after the fold and its failure is swallowed, while the append comes BEFORE and its failure REFUSES the batch, because a lost count is a number and a lost emission is a **hole**. Keyed by `{source, config}`. It is chain-free, which is the whole reason it is a separate object from `IndexerGeneration`: that class opens `load()` with `eth_chainId`, so the half of a split deployment that hosts the processor cannot use it. It reads the persisted cursor on every call rather than holding one, because an in-memory cursor is one serverless isolate's private opinion of a value the database owns. Distinct from a **wire batch** (`WireBatch`, the ADR-0004 envelope `{context, fromBlock, toBlock, latestBlock, logs}`): the batch is what crosses, the stream-builder is what receives it.
- **the cursor is the idempotency key** — the receiving rule of ADR-0004, and the reason the ingestion endpoint has no dedupe table and no idempotency header. A batch whose `fromBlock` is not the server's own `expectedFromBlock` is refused with `409` carrying that value (`UnexpectedFromBlockError`), and the sender re-sends from there; a batch re-sent after a lost acknowledgement fails exactly that check, so at-least-once on the wire becomes exactly-once in effect. `409` is the ONLY resumable refusal: a foreign `{source, config}` (`WireContextMismatchError`) or a malformed range (`InvalidBatchError`) is a `400`, because no block number makes it right. Note what the envelope deliberately lacks: no `complete` flag (completeness is an invariant, and truncation is a LOWER `toBlock`), no `removed` markers and no `unconfirmedBlocks` (the receiver derives every reorg, so that logic exists once).
- **reorg cause** (`ReorgCause`, `@etherfold/core`) — HOW a revert was concluded, and the two are never folded into one number. `contradiction` is proof (the same height now carries a different hash) and is ordinary chain activity; `absence` is an INFERENCE (a block we held is simply not in the re-delivered range) and is indistinguishable from a sender that under-delivered it. They are counted separately in `_meta` and reported on `/status` (`reorgs: {absence, contradiction, last}`), because a rising rate of the absence kind means truncation or misconfiguration, not the chain. It does not make the server unhealthy: it is a signal to investigate, not a fault. **The count is a fact about the FOLD and not about the transport** (ADR-0050): it is taken ONCE, inside `StreamBuilder.receive`, and written by whoever OWNS the store (`ReorgRecorder`, injected: in this repository by the CLI's `buildProcessor`, so `run`, `build` and `index` all count), which is why the ingest route is a CALLER of that path rather than the owner of a write. It was the route's, and a combined `run` therefore reported `{absence: 0, contradiction: 0}` for ever on the shape the milestone calls the default. The server READS them and writes none (a read tier owns no store and still has to answer), which is why the durable KEY NAMES live in `@etherfold/core` beside `ReorgCause` rather than at either end. `build` applies the fixed tables for the same reason: a database it emitted is a publishable ARTIFACT, so the counters are a property of the artifact and not of whichever process serves it.
- **indexer-server**: the deployable hosting the stream-builder plus an `EventProcessor`, owning the versioned state (keyed by `{source, config, processor}`) and serving both the state query API and the log feed. `@etherfold/server` is the platform-agnostic half of it (`/status`, `/admin/setup`, `/{indexer}/ingest`, `/{indexer}/feed`), with the database, the environment AND the registry of named indexers all injected; `platforms/*` are the hosts.
- **the two views** (ADR-0006): the two reads over the ONE stored **emission stream**, and a cursor for one is never a cursor for the other. The **retraction-aware feed** (`GET /{indexer}/feed`, BUILT) is `seq`-ordered with `removed` entries INCLUDED, for a consumer that acts optimistically and cancels a pending action when a reorg retracts it. The **canonical view** (`GET /{indexer}/canonical`, BUILT) is `WHERE alive AND blockNumber <= gate` ordered by `(blockNumber, logIndex)`, for a consumer that never wants to hear the word reorg; its gate is the CALLER's, REQUIRED on the request and never defaulted (a default would be the server choosing a consumer's risk appetite), and its cursor carries the block hash the server validates, so a reorg answers **rewind-to-fork-block** (`409 rewind-required`, carrying `forkBlock` and a `rewindCursor` at it) rather than silently skipping. `(blockNumber, logIndex)` is not a cursor over the emission stream at all (not unique there, and not monotonic after a reorg), and a synthetic sequence is wrong for the canonical view, which is why each keeps its own. An entry served by the canonical view carries no `removed` field at all, because a flag that is false on every entry invites reorg handling that can never fire.
- **pair-compaction** (`compactEmissionPairs` / `resolvePairCompaction`, `@etherfold/server`, ADR-0006) — the ONE thing that ever DELETES from the stored **emission stream**: a retracted entry (`removed = 0, alive = 0`) reclaimed TOGETHER WITH its retraction (`removed = 1`) of the same `(blockNumber, blockHash, logIndex)`, far below finality. It may exist because it is **answer-preserving for the canonical view by construction**: it only ever removes rows that view already excludes, so a gated read cannot change (asserted byte-for-byte), and an apply/retract pair has no net effect on a replay whose revert is exact. Its DEPTH is measured in BLOCK NUMBERS and in no other unit, with the finality depth as the FLOOR and a shallower one REFUSED naming both numbers rather than clamped — the same rule, spelled the same way, as **retention** (ADR-0019), because a duration would compact on wall-clock progress rather than chain progress. It is a call the HOST SCHEDULES doing BOUNDED work (at most `maxPairs` pairs, every row named by its `seq`), never a side effect of an append, exactly like **prune** (ADR-0022) — so OFF BY DEFAULT is nobody calling it rather than a flag the server reads, and no cadence is invented for a browser tab, a backfilling CLI and a long-running server at once. It leaves **holes** in `seq`, which are legal by contract and which both cursors tolerate, and it never renumbers, never drops half a pair and never touches a LIVE row. Distinct from **prune**, which enforces **retention** against the versioned STATE and is a different table, a different unit-holder and a different verb; the two share their shape deliberately and nothing else. Its one observer is a consumer lagging further behind than finality (an absent pair on the `seq` feed, and a reorg the canonical fork search can no longer name), which is already outside the window it may rely on.
- **feed cursor** (`@etherfold/server`, `src/feed/cursor.ts`): the position a FEED consumer holds between polls, an OPAQUE server-encoded string, and the read-side counterpart of the **sync cursor**'s opacity (ADR-0027) with the audience one step further out, since a **consumer** is built outside etherfold. It CARRIES the VIEW, the indexer NAME, the STREAM and the POSITION, and the first three are VALIDATED and never used to ROUTE: the route already routed, and those copies exist so that a cursor presented at the wrong indexer, for the wrong view, or against a stream no longer served is REFUSED rather than answered at a number that means something else there. The stream refusal is the one that ANSWERS, with the current stream identity plus a cursor at the position its feed STARTS at, and it is explicitly NOT a rewind: a filter change produces logs that were never on the old stream, so there is no fork block. **A REWIND is the other thing entirely** and belongs to the canonical view alone: it is a correction on the caller's OWN stream, it names a `forkBlock`, and its `rewindCursor` is meant to be followed automatically -- which is why it is a `409` (ADR-0004's one RESUMABLE refusal, the same sentence spoken to a consumer) while every cursor MISMATCH stays a `400`. ONE codec across both views (`at` is the view's own position and the codec does not interpret it), because two encoders would be two refusal paths that drift. The canonical view's `at` carries its `(blockNumber, logIndex)` position, the block HASH it is validated against, and a `since` MARK -- the stream's high-water `seq` when the cursor was minted, which is what makes "what has been retracted since you last looked" answerable, and which is deliberately not a position and never advances the read. It is deliberately not exported from the package: publishing a decoder would make the encoding a contract by the back door, which is what opacity exists to prevent. **HOLES in `seq` are legal**, so a next position is the `seq` actually SERVED and never a number plus one, and no `seq` is published on an entry at all.
- **consumer**: anything reading the FEED (a trigger/notification service). It is built OUTSIDE etherfold (ADR-0005), and what etherfold owes it is capability rather than machinery: the stored emission stream is sequenced, so a consumer can read it on its own cadence, and state is addressable at a block height (`getAsOf`/`queryAsOf`), so it can ask what was true at a point rather than only what is true now. Independent, owns its own cursor, gate, outbox and delivery; etherfold stores nothing about it. Reserve "consumer" for this read side and never call it a watcher. **In particular do not use it for a browser CALLER**: an app holding a state handle, a component re-reading after a notification, or a reader of the generated read surface is a *caller*, an *app* or a *reader*, never a consumer. Several specs still use the loose sense in prose (`a-reconfigure-is-not-an-outage` and `one-command-runs-the-whole-pipeline` both do, the latter within a few lines of citing THIS reservation as an argument); that is drift to correct on touch, not a second sanctioned meaning.
- **gate / lane**: the block bound a consumer applies before acting: `safe` (finalized) or `fast` (`latestBlock - N`, per chain, defaulting to `stream.finality`).

## Conventions

Standing per-change rules agents must follow in this repo.

- Changes that affect a published package's public API require a **changeset** (`.changeset/*.md`).
- **The code that exists is EVIDENCE, not AUTHORITY.** Read it to learn what is TRUE today; never to infer what must STAY. A shape in the tree records a decision someone made once, under constraints that may no longer hold, and it may also simply not work: reviewing the stream keeper turned up a mechanism (`streamNotYetSaved`, the unsaved-events carry-forward in `promiseToSave`) that reads as a safety net and NEVER FIRES, because the promise context it lives on is reset between cycles. So refactoring is the default rather than a licence to ask for: where an existing shape is in the way, change it, and delete what has stopped earning its keep, rather than building around it and leaving both. Nothing is published (above), so the cost of doing that is a changeset. What DOES constrain a task is its acceptance criteria, its scope fence and the ADRs it names — and a refactor that grows past the scope fence is a `## Decisions` note or a needs-attention signal, not something to smuggle in.
- **NOTHING IS PUBLISHED YET, so a breaking change costs a changeset and not a migration.** The `@etherfold/*` packages are not on npm (`work/tasks/backlog/publish-etherfold-and-deprecate-old-names.md`: "The rename landed in the tree; nothing has been published"), and the only consumers are repositories we own. So: do NOT contort a design to preserve a published type, do NOT add a compatibility shim for an external caller that does not exist, and do NOT let "this is breaking" outweigh "this is right" — delete the wrong thing rather than deprecating it beside the right one. Still WRITE the changeset, because the release that eventually happens needs the notes. This changes once the publish task lands, and this line is the thing to revisit then.
- **The blank sheet covers TYPES cheaply and BYTES ON DISK less cheaply, and the difference is a COST to weigh rather than a prohibition.** A type change costs a changeset. A PERSISTED-FORMAT change costs affected clients a RE-INDEX, and the price of that is entirely situational: trivial on a local node, and potentially IMPOSSIBLE on a public one, since old logs are frequently not served at all (which is the whole premise of `work/specs/proposed/a-generation-can-be-seeded-from-a-published-artifact.md`). So the question to ask is never "is this breaking" but **"what does re-indexing cost the people it lands on, and is a seed or snapshot available to them"**. Where a seed exists the answer is often "little, do it"; where none does, a migration earns its keep.

  **Today that set of people is EMPTY, and saying so plainly is what stops the question being asked wrongly.** Nothing is published, and the reference deployment has a live CONTRACT but no PLAYERS, so no disk anywhere holds state this project must preserve. Retrofitting it, if it ever mattered, is a re-index through the indexer-server plus a published snapshot and stream seed. So a MIGRATION is justified as PRODUCT CAPABILITY and not as debt owed to anyone: build one because an indexer whose upgrades do not blank the app is the thing being sold, not because a user is owed it. The corollary is the useful half: a one-time migration between two formats that only ever existed in UNRELEASED builds has no beneficiary at all and should be a SWEEP, not a data move. And note where the real capability lives — "an upgrade does not blank the app" is delivered by the GENERATION MODEL, not by keyspace migrations.
- **STRATAGEMS IS A CAPABILITY REFERENCE, NOT A COMPATIBILITY CONSTRAINT.** It exists to prove the system can do what a real launched game needs (a real ABI, real reorgs, 31,332 real logs, a shipped snapshot) and it is the honest yardstick for whether a design works. It is NOT a deployment whose stored bytes must be preserved: it can be retrofitted, re-seeded and re-deployed at will, because it is ours. Do not let it veto a better design, and do not cite "a launched game's users hold caches" as though it settled an argument — it does not, and treating it as a frozen production dependency would let an example dictate the architecture it exists to validate.
- Logging goes through **named-logs** (`import {logs} from 'named-logs'`), not `console.*`, in the core `@etherfold/core` package.
- A new ADR takes the next unused number and is named `NNNN-slug.md`. `pnpm check:adr` (`scripts/check-adr-numbers.mjs`, in the acceptance gate and in CI) refuses two ADRs claiming one number, because the number is a stable reference cited from source comments, `CONTEXT.md`, changesets and other ADRs. A GAP in the sequence is fine and not checked.
- Tests use **vitest**, in each package's `test/` folder; run via `pnpm --filter <pkg> test`.
- **`pnpm typecheck` is what checks `test/`.** Each package's build `tsconfig.json` includes `src/**/*.ts` only (it emits to `dist/`, so tests must stay out of it), and vitest strips types with esbuild without checking them. The per-package `tsconfig.typecheck.json` (`noEmit`, `rootDir: "."`, `include: ["**/*.ts"]` minus `node_modules`/`dist`) is the only thing that typechecks a test file. The include is deliberately the WHOLE package rather than a list of the directories that happen to hold code today, so a package-root config (`vitest.config.ts`, `playwright.config.ts`) or a new directory is covered without anyone remembering to widen a glob. **Run `pnpm build` first**: cross-package types resolve through each package's `dist/`, so `pnpm typecheck` on a clean clone reports missing modules. The acceptance gate already sequences them that way (`pnpm build && pnpm typecheck && pnpm test`).
