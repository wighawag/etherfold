# @etherfold/platform-nodejs-triggers

## 0.2.0

### Minor Changes

- 6c66aba: `etherfold-triggers` refuses, at start, a database holding rows of an app the config neither declares for that database nor lists in the new top-level `retired: string[]` (ADR-0101), naming the app and the database (its query string, which may carry a token, left out). It catches a config pointed at the wrong database, or a second service sharing one, before two services cross data; every command checks it, `run` and the operator commands alike. `retired` is how an operator removes an app or moves it to a database of its own: its old rows stay where they were (ADR-0012), and the check lets them be. An app may be both in `apps` and in `retired` (the move): it runs on its declared database. A `retired` that is not a list of strings is refused.
- 7baec42: Every call the trigger service makes to the outside times out (ADR-0101): the gate, each feed read, each predicate invocation and each delivery get an `AbortSignal` that aborts after a per-call timeout, `callTimeoutMs` (10 s when absent, `DEFAULT_CALL_TIMEOUT_MS`), one option on `createTriggerService` (and on `createConsumer`, `createDeliverer` and `registry.matcher`) and on the nodejs platform's config. The core gives up at the timeout whether or not the callee honours the signal. A timed-out gate, feed read or predicate fails the round with a `CallTimeoutError` (code `gate-timeout`, `feed-timeout` or `predicate-timeout`), journalled as `stalled` then `recovered`, the page not committed and read again next round; a timed-out delivery is retried like a `5xx`. New parameters: the gate is `(context: {signal}) => Promise<number>` (the new `Gate` type; `rpcGate` passes the signal to `fetch`), `CanonicalFeed.read(query, {signal}?)`, `ActionAdapter.deliver(delivery, {signal}?)`, a predicate's third argument `{signal}`, and `StateReader.query(document, at, variables?, {signal}?)`; each is optional for an existing implementation, and the built-ins (`canonicalFeed`, `rpcGate`, `stateReader`, `pushAction`, `rewardAction`) pass the signal to `fetch`.
- 242e79e: One `etherfold-triggers` process hosts several apps from one config (ADR-0101). The config's default export is now `{database?, api?, intervalMs?, apps: {[name]: AppConfig}}`: each app (named by its key, a URL-safe slug) carries its own chain, feed, gate, triggers, actions, verifier and `callTimeoutMs`, and may name its own `database` (the shared one, `file:triggers.db` by default, otherwise; apps naming one URL share one connection). The one-app flat shape and its `name` are removed: a config without `apps` is refused at start with the shape to write, as is an app name that is not a slug. `createNodeService(config)` now returns `{apps, api, tick, run, close}`: one core service per app, every app's registration API mounted under `/{app}/` on one Hono app (the verifier checks the full path the client signed, prefix included, and each app's CORS answers its own origin on its own routes only), and one loop per app run concurrently, so one app's failing or hung round holds only that app. `openDatabase` takes a URL. The CLI's `tick`, `status`, `deliveries` and `journal` cover every app, one JSON line each naming its app (`tick` exits 1 when any app's round failed); `resume` and `requeue` act per app (see `--app`). In the core, a round is bounded: `createTriggerService` takes `maxPagesPerRound` (100 when absent) and `maxDeliveriesPerRound` (the deliverer's batch, 100 when absent), `consumer.catchUp({maxPages})` stops at its bound and returns normally with `hasMore` (the 10 000-page guard now throws only for an unbounded call), a round's report carries `hasMore`, and `run` starts the next round at once after a round that stopped at its page bound.
- d36f854: The `etherfold-triggers` operator commands take `--app <name>` (ADR-0101): `status`, `deliveries`, `journal` and `tick` report or run that app only (without it, every app, each JSON line naming its app), and an unknown name is refused, listing the configured apps. `resume` without `--app` resumes the one paused app and refuses when several are paused (naming them) or none is; `resume --app <name>` resumes that app only, the others untouched. `requeue <id>` now prints `{"app", "requeued"}`; with `--app` it refuses a row of another app, naming it, and without it it finds the app the row belongs to (refusing, naming them, when apps on their own databases share the id). `NodeService.tick(only?)` runs the named apps only. In the core, `listDeliveries`' filter takes an `id`.
- cfc4332: The trigger service's schema is keyed by APP (ADR-0101), so two apps sharing one database never cross. Breaking: `createTriggerService`'s and `createConsumer`'s `name` option is now `app`; `createTriggerRegistry` and `createDeliverer` take an `app`; the delivery record's `consumer`, `MatchContext.consumer` and `ConsumerStatus.name` are `app`; the reward target's body carries `log.app` instead of `log.consumer`; `listDeliveries(db, app, filter)` and `readJournal(db, app, options)` take the app, and every journal entry names it (the consumer's entries no longer repeat it in their detail). Every table carries an `app` column and every unique and lookup index leads with it: deliveries are unique on `(app, action, key)`, subscriptions on `(app, kind, recipient, filter)`, accepted requests on `(app, key)`, and the deliverer's due scan, the rewind, the matcher, the quota, renew-all, list, cancel, expiry and requeue are all scoped to the app. There is no migration: `setup` over a database in the old layout refuses with an error saying the schema changed and to start from an empty database.
- bc57256: Two tickers of one app never work at once (ADR-0101): every tick runs under a per-app LEASE held in the app's `consumers` row (new columns `lease_owner` and `lease_expires`; `setup` refuses a database whose `consumers` table predates them, with no migration). The first tick of an app creates its row and takes the lease; while another ticker holds it, `tick()` does nothing and reports `{lease: 'not-leased'}`. `TickReport` is now `{lease: 'held', ...RoundReport}`, `{lease: 'not-leased'}` or `{lease: 'lost', reason}` (a round stopped at a fence), and the old fields live on the new `RoundReport`. The lease lasts `leaseMs` (60 s when absent, `DEFAULT_LEASE_MS`), a new option of `createTriggerService` and of each app in the nodejs platform's config, and is renewed under half of it, about one write per 30 s per app; the renewal writes only the lease. Before each call (the gate, a feed read, a predicate, a delivery) the tick renews under half the lease and stops under the fence margin (`callTimeoutMs` plus 5 s for the commit and 5 s for clock skew); a timeout whose margin is not under half the lease is refused at start, naming both. Every statement a tick commits or settles is guarded by the lease, so a stale holder changes nothing (a `LeaseLostError`). `run` releases the lease when its signal aborts, `service.lease.release()` releases it for a one-shot host, and `etherfold-triggers tick` releases it at the end of its round (the platform's `NodeService` gains `release(only?)`). New exports: `createLease`, `LeaseLostError`, `DEFAULT_LEASE_MS`, `LEASE_COMMIT_ALLOWANCE_MS`, `LEASE_CLOCK_SKEW_ALLOWANCE_MS`, and the types `Lease`, `LeaseGuard`, `LeaseColumns` and `RoundReport`; `createConsumer` and `createDeliverer` take an optional `lease`, `registry.matcher` an optional `fence` and `registry.expire` an optional `{lease}`.

### Patch Changes

- 1ef3817: The idempotency key `pushAction` and `rewardAction` send is now the delivery's key prefixed by its app (`<app>:<key>`, exported as `wireKeyOf`), in the `Idempotency-Key` header and in the reward body's `key`, so two apps sharing one reward service or one push domain never have one app's call absorbed as a replay of the other's (ADR-0101). A reward service sees new keys: an award already granted under the bare key would be granted once more. The tick's subscription expiry now re-checks the expiry as it writes, so a renewal landing between its read and its write is never overwritten, and only a subscription it actually expired is journalled. `etherfold-triggers run` refuses `--app` instead of silently serving every app.
- e66e561: `delegatedIdentityVerifier` takes delegated-identity 0.2's proof, the one push-notification-server 0.3's `/register` checks. A registration's body now carries the account's public key set beside `address`, `domain` and `ownershipSignature`: `keySet: {signing: {publicKey}, encryption: {publicKey}}` (an Ed25519 signing key and an X25519 encryption key, 0x hex), which the wallet's ownership signature authorizes for the app's origin, and the `SIGNATURE` header is the signing key's Ed25519 signature over the request, naming its key (`<timestamp>:<key>:<signature>`). The same client body registers at push-notification-server and at the trigger service. The old proof (a secp256k1 delegate key, a recovered request signature) is refused, with no compatibility. A signed request is still accepted once, now named by the SHA-256 of the envelope the signing key signed. The Node.js triggers platform's tests and README follow the new wire.

## 0.1.1

### Patch Changes

- e248f2a: The registration API answers CORS for the app its verifier serves, so a browser app on its own origin registers its triggers directly. A preflight (`OPTIONS`) from that origin is answered `204` with `Access-Control-Allow-Origin` set to it, `Access-Control-Allow-Methods: POST,OPTIONS`, `Access-Control-Allow-Headers: content-type,signature`, an `Access-Control-Max-Age` and `Vary: Origin`; every other response, refusals included, carries the same allow-origin and `Vary`, so the app can read a refusal's reason. Another origin gets no allow-origin, never `*`, and no credentials are allowed; the proof checks, `serverOrigin` and the signed path are unchanged.
  
  - `@etherfold/triggers`: `RegistrationVerifier` takes an optional `appOrigin`, the origin `createRegistrationAPI` answers CORS for (none when absent). `delegatedIdentityVerifier` sets it to its `domain`'s origin, the one app it serves.
  - `@etherfold/triggers`: an unexpected failure inside a registration route is answered as a JSON `500 internal-error` (with the CORS headers, the cause logged and not sent) instead of being rethrown to the server, whose bare 500 a browser could not read.
  - `@etherfold/platform-nodejs-triggers`: `etherfold-triggers run` serves it with no change to a config that names a verifier.

## 0.1.0

### Minor Changes

- 6a51ff5: First release of etherfold's reference trigger service, moved into this repo from `wighawag/etherfold-triggers` with its history (ADR-0100). It runs as its own process beside `etherfold run`, never inside the indexer-server (ADR-0005), and reaches the indexer only over HTTP.
  
  - `@etherfold/triggers` (was `etherfold-triggers`, never published): the platform-neutral core. A consumer of `/{indexer}/canonical` on the safe lane that commits its cursor and the deliveries a page implies in one batch, rolls its undelivered outbox back on a rewind and pauses on a generation change; subscription triggers registered with a proof (`delegatedIdentityVerifier`, the one push-notification-server's `/register` checks) and expiring unless renewed, and global rules whose predicate may read the indexer's state as of the log's block (`stateReader`); an outbox with a per-type delivery policy (a TTL, a retry budget, a dead letter); the `pushAction` and `rewardAction` adapters; `createTriggerService` composing them.
  - `@etherfold/platform-nodejs-triggers` (was `etherfold-triggers-nodejs`, never published): the same on Node.js and libSQL, as the `etherfold-triggers` command (`run`, `tick`, `status`, `resume`, `deliveries`, `requeue`, `journal`) reading one config file. Its README is the operator guide.
  
  Both are MIT, like the rest of etherfold.
