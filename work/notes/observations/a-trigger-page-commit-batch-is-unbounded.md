# A trigger page's commit batch has no bound on its statement count

Observed 2026-11-27 in the whole-range review of `one-trigger-service-serves-several-apps`. Every single statement of the trigger core binds at most 16 parameters, under D1's 100 (`work/notes/findings/d1-caps-bound-parameters-per-query-at-100.md`), and a subscription kind's filtered match is capped by `MAX_FILTERABLE`. But the consumer commits a whole feed page in one `db.batch`: one delivery insert per match, plus the state write and journal rows, so a page of many logs each matching many subscribers makes a batch of unbounded length. D1 (and a metered libSQL host) cap statements per batch or per request. When a D1 host is built, measure the cap, and bound it there (a smaller feed page for that host, or a page split across batches that keeps the state write last, so the cursor still moves only with its deliveries).
