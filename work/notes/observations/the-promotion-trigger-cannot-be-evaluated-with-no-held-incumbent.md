---
title: 'The promotion trigger cannot be EVALUATED when the container holds no fold for the canonical generation, which is the restart shape'
slug: the-promotion-trigger-cannot-be-evaluated-with-no-held-incumbent
observed: 2026-09-16
---

2026-09-16 — Measured while driving `promotion-arms-from-the-slot-so-a-restart-can-finish-an-upgrade`, which routed to needs-attention on it. Recorded here because a stopped build leaves no diff, and because it changes what two tasks and one ADR symptom can promise.

ADR-0084's third symptom, and the task written from it, name TWO things that stop a generation registered at `open` from ever being promoted: the `opened` gate (`applyPolicyTo` returns while `!opened`) and the in-memory candidate set (`settlePromotion` returns on an empty one). Narrowing the gate to "arm what `successor` names" fixes both. It is not enough, and the pointer still never moves.

The narrowing was implemented exactly as the task specifies and measured on a `run` deployment stood up the way `packages/cli/test/theDeploymentSelectsItsPromotionPolicy.test.ts` stands one up, stopped, and re-run over the SAME libSQL handle with a changed processor module. **The arming half works**: `applyPolicyTo` sees `canonical` on an unchanged restart and does not arm (so `immediate` does not move a host's own fold), and sees `successor` on a changed-processor restart and arms. The successor then reaches the tip (`lastToBlock` 1000050) and `canonical` is still the V1 generation, with the settle reporting no held fold for the canonical generation on every cycle.

**BLOCKER 1, the trigger has nothing to compare against.** `settlePromotion` reads `const current = this.folds.find(fold => sameGeneration(fold.record, canonical)); if (!current) return;`. On a redeploy the container holds exactly ONE fold, the new one: `openReceivingIndexer` takes a single `generation` option, and the OLD processor's code is not in the build at all, so a fold for the incumbent is unbuildable BY CONSTRUCTION. The same fact `promote`'s JSDoc already leans on ("it does NOT require this container to hold a FOLD for the target") is what makes the automatic trigger inert here. The trigger's target is `cursorOf(current)` — the incumbent's persisted cursor, which lives in the incumbent's own table namespace, and the container cannot build a store for a generation it holds no fold for; only the HOST knows that convention, which is why `dropState` is INJECTED.

This is already documented as accepted behaviour, which is why nobody noticed it blocks the upgrade story: the JSDoc above `settlePromotion` says a canonical generation this container holds no fold for "simply means there is nothing to compare a successor against, so the pointer does not move on its own". That sentence is true and was written about a different situation; after ADR-0084 it is the situation the headline promise depends on.

Closing it is a DESIGN decision and not a small gap. Either a new injected port (read the cursor of a generation I hold no fold for, the symmetric sibling of `dropState`, reaching core + cli + server + browser), or a SECOND trigger rule for the no-held-incumbent case (e.g. the successor has reached the chain tip it just observed, sound because nothing can be ahead of the tip, but a different rule). It changes the one safety property `on-catch-up` exists for, it contradicts ADR-0046 and `CONTEXT.md`'s glossary as written ("the trigger is the successor reaching the cursor the CANONICAL generation has, compared LIVE"), and `readyForPromotion` / `PromotionView` are SHARED with the chain-facing twin, so whoever decides it decides it for both containers. No ADR, task or note owns it today.

**BLOCKER 2, nothing calls the settle in this shape on `run`.** `settlePromotion` has exactly two callers: `applyPolicyTo` (once, at `add`, when the successor has folded nothing) and `rebuildMore`. `packages/cli/src/index.ts` gates `rebuildMore` on `container.followers().length > 0`, and the restart-shape successor is NOT a follower: `add` computes `follows` from "do I already hold a fold on this stream", and at `open` the fold list is empty, so it is `false`. Removing that gate is cheap, but WHERE the settle gets its turn against the ingest path is the same decision `an-index-process-advances-the-successor-it-registered` is explicitly told to make, so it should be made once, by whichever task owns the drive loop, rather than forked.

What remains deliverable from the stopped task without any of this: a restart after a revert re-promotes nothing under every policy value (a generation `predecessor` names is never armed), `immediate` does not move a host's own canonical fold, deleting `candidates` / `opened` / the now-unused `fold` parameter of `movePointer`, and the `immediate` and `manual` thirds of the policy criterion. Only `on-catch-up` across a restart needs the two blockers above.
