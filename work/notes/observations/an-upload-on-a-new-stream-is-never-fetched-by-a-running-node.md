2026-09-26, seen by the conductor at Gate 3 on `a-processor-bundle-is-uploaded-to-a-running-node` and `a-run-node-with-nothing-configured-waits-for-its-first-upload`. The maintainer decided that an upload carrying different contracts (a new event, an upgraded contract) is a legitimate change and registers a successor on its NEW stream rather than being refused. It does register. But a `run` holds ONE fetcher over one source: the configured one, or (with nothing configured) `ReceivingIndexer.fetchedSource`, which is the first fold's source and is set once and never moves (ADR-0093's "Where it lives"). So nothing appends to the successor's new stream, it cannot catch up, and it is never promoted; the admin listing reports such a generation as `stream-not-fetched`. After a restart with nothing configured the fetched source is again the canonical generation's, so a restart does not help either. The tests assert only that the registration happens (`packages/cli/test/aRunNodeWithNothingConfiguredWaits.test.ts`, "registers a second upload as `successor`..."; `packages/cli/test/aBundleIsUploadedToARunningNode.test.ts`, "a node whose source came from its processor module..."), never that it advances. The re-read after a filter change has the same shape on a running node. Consequence: The Graph-style flow works end to end for an upload that keeps the same contracts, and does not complete for the "add an event" deploy the decision was made for. Whether the fetcher should follow the successor's stream (a second writer, or re-pointing at promotion) is a design question for the maintainer.
