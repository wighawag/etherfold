2026-09-17 — Noticed while driving the ADR-0086 bundle-identity family. The first seven tasks landed green (#160 through #166); `the-declared-version-and-the-drift-report-are-deleted` then STOPPED, and the stop is correct. The build agent's full analysis is on `main` in the surface commit `0e500dd9`; this note records the GRAPH-level shape of it, which is what whoever re-scopes has to decide about, plus what I verified independently.

The task body says "Four migrate batches have already moved every caller, so this is a removal rather than a change." That is false, and it is false for a structural reason rather than a sloppy one. Every arrival that HAS bytes was migrated. The arrivals with NO bytes were deliberately left on the declared path by those same four batches, each deferral written down as a decision at the time, and each one handed to a task that is `blockedBy` the contract task. So the contract task cannot land without building parts of the tasks waiting behind it.

Three remainders, all verified against the code rather than taken from the stop report:

**The browser's HMR arrival.** `updateProcessor` in `packages/browser/src/IndexerState.ts` still compares declared hashes, and it receives an already-built `EntityEventProcessorLike` rather than the author's module object, so there is no seam at which a handler-source derivation could be called without a change that belongs to `a-module-handed-to-a-tab-is-identified-by-its-handler-sources`. Deleting `getVersionHash()` leaves that path, `liveReload.test.ts`, `reconfigure.test.ts` and `examples/browser-reference` with no identity source at all.

**The CLI's unbundled path.** 71 `importModule` sites across twelve CLI and utils suites stand deployments up by injecting an in-memory module object, which cannot produce bytes to hash. Deleting the declared identity forces those suites onto real bundles AND introduces the user-visible refusal that is the entire subject of `a-path-naming-an-unbundled-entry-point-is-refused`.

**`examples/event-processor-nfts`.** Its `build:db` script runs `etherfold build -p ./dist/cli.js`, a `tsc` output that imports its ABI and so is not self-contained, and `src/entities.ts` still carries `version: '1.0.0'`. The root `test` script includes `examples/*` on purpose, so this is inside "the whole tree is green".

**The edge that is simply inverted.** `a-module-handed-to-a-tab-is-identified-by-its-handler-sources` lists the contract task in `blockedBy`, and its stated reason is entirely PROTECTIVE: "which removes the fingerprint's OLD role, and must not remove the derivation this needs". Running it BEFORE the contract task satisfies that concern strictly better than running it after, because the derivation is then certainly present. Two things corroborate it. Its own Prompt already contemplates either order ("Read `packages/core/src/utils/fingerprint.ts` **if it still exists at the point you start**, or the done record of `the-declared-version-and-the-drift-report-are-deleted` if it does not"). And the derivation it needs exists today and independently of the seam method being deleted: `processorCodeFingerprint` is exported from `packages/core/src/utils/fingerprint.ts`, while what the contract task removes is `getCodeFingerprint()` from the processor seam. So this edge costs the family a deadlock and buys nothing.

**A second edge worth a look, less certain.** `a-snapshot-is-labelled-with-the-identity-it-was-computed-under` is blocked on the contract task because "the value this writes does not exist in its final form until the declared version is gone". The value exists NOW: a snapshot's label comes from `lastSync.context.processor`, which the four batches already moved to the arrival identity, so a producer on a bundle arrival already labels correctly and one on the declared path already labels with what it actually ran under. That reads like a purity argument rather than a mechanism one, so this leaf may be buildable today. Worth a human's judgement rather than an assumption.

**The one edge that is real.** `a-path-naming-an-unbundled-entry-point-is-refused` genuinely must follow the contract task, and its own reason says why: until the declared path is gone, an unbundled entry point is a legitimate configuration and refusing it would be wrong.

So the missing piece is a FIFTH migrate batch ahead of the contract task, moving the CLI suites and `examples/event-processor-nfts` onto bundle arrivals while deleting nothing and refusing nothing, exactly as the other four batches were shaped. With that batch landed and the HMR edge inverted, the contract task becomes the pure removal it describes.

**A secondary contradiction inside the task, which any re-scope should fix while it is there.** Acceptance criterion 1 requires `utils/fingerprint.ts` to be "gone from the published surface and from the tree", while the same task's "What to build" and Prompt both say the derivation SURVIVES and instruct leaving what the HMR task needs. Those cannot both be met. The criterion wants rewording to something like "`getCodeFingerprint()` is gone from the processor seam; `processorCodeFingerprint` survives in its new role", and it should state whether `packages/core/test/processorFingerprint.test.ts` and its fixtures stay — they test the surviving derivation rather than the drift report, so removing them under criterion 2 would delete live coverage.

Nothing here is a defect in the four batches. Each was green, each stayed inside its own packages, and each wrote its deferral down where the next reader would find it, which is the only reason this was cheap to diagnose.
