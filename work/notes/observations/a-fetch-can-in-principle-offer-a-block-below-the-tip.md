title: 'A fetch can in principle offer a block below the store tip, which is now a loud refusal instead of quiet corruption'
slug: a-fetch-can-in-principle-offer-a-block-below-the-tip

2026-09-10, noticed while landing `applyblock-refuses-a-height-below-the-recorded-tip`. `generateStreamToAppend` decides which incoming blocks are NEW by MEMBERSHIP of the retained window and deliberately not by a height threshold (ADR-0051), so it will deliver a block the window never held even when the store already holds higher ones. Every reorg shape reaches `applyBlock` after a `revertTo` that has taken the tip back under it, which is why the whole suite stays green; the shape that does not is a node that UNDER-DELIVERED a range earlier (a truncated `eth_getLogs`, a wrong filter) and returns those logs on a later re-fetch with the window's blocks unchanged. Before this task that applied a version whose `_lower` sat under the live one and closed the live one at a block below its own opening; now it is refused with `block N is not above the recorded tip T`, which wedges the cycle instead. Refusing is the better of the two, so nothing here is a defect to fix -- what is unrecorded is whether a wedged fold is the response we want for a node that under-delivers, or whether that deserves its own diagnosis (the engine already tells `absence` from `contradiction` for reverts, and this is the same family of evidence).
