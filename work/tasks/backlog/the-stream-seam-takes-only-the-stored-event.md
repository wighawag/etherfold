## What to build

Move the kept-stream seam onto the stored-event type, so an implementor of the keeper interface CANNOT accidentally persist a decoded event and finds out at COMPILE time. The type already exists and refuses decoded events; the strip already produces raw-only objects at runtime. This task makes the seam itself say so, which is the breaking `@etherfold/core` change the spec is about.

Both halves of the seam move: the fetcher (what a keeper hands BACK) and the saver (what a keeper is HANDED). Every implementation and every test fake in the repo moves with them in this one change, because the seam types are the single point they all resolve through: core's own segmented keeper, the degrading wrapper, the read-only wrapper (and the reader type it is built on), the browser's IndexedDB keeper, the server's stored emission stream, and the keepers built inline in the core, browser and server tests. Re-grep before you start rather than trusting that list. The captured fixture is NOT among them any more — a sibling task took it off the seam first, on purpose.

**The seam's CONSUMERS move with it too, and there is more than one.** The re-decode entry point (`reparse`) was already widened by the type task, but it is NOT the only thing the load and follow paths do with what `fetchFrom` returned: the follower path also derives an emission mark per stored event and compares the stored slice against what it already folded (`emissionMarkOf` / `hasAlreadyFolded` in core's indexer). Those read RAW fields only, so widening their parameter types to accept the stored shape is the correct move and is in scope here — do not cast at the call site and do not narrow what they answer. Grep the three `fetchFrom` call sites in the indexer and follow every value derived from the returned `eventStream`; if a consumer genuinely needs the decoded half, that is a finding to surface, not something to paper over with an assertion.

The previous task left ONE commented, temporary assertion at the indexer's save call site, because the stripped batch could not satisfy a seam that still declared decoded events. Narrowing the seam is what makes it unnecessary FOR THE BATCH: delete that half, and if anything else in the repo carries a comment pointing at this task, close that too.

**Decide the `lastSync` WINDOW explicitly — it is the one place the compile-time guarantee does not follow the runtime one.** The saver takes a batch AND a `LastSync`, whose unconfirmed blocks hold events; the previous task strips those at runtime, but `LastSync` is the SHARED cursor type the processor seam and the load path also speak, so narrowing it in place is not on the table. Choose deliberately between (a) leaving the window typed decoded, with the seam's docstring stating plainly that the window is stripped at runtime and that the compile-time refusal covers the batch only, or (b) giving the seam its own stored-window variant of the cursor type, used ONLY by the two seam function types. Whichever you pick, do NOT fork or re-mean `LastSync` itself for the processor/load/wire callers, and record the choice and its reason in your `## Decisions` block: an unstated hole here is exactly the ambiguity this spec exists to remove.

Note that the window rides in BOTH directions: the saver TAKES a `LastSync` and the fetcher RETURNS one. Today no shipped keeper hands a populated window back (the segment keeper stores none and returns an empty one, and the server's reader has none to give), so the return side costs nothing at compile time under either branch — but a test fake that echoes back what it was handed will be returning a raw window under a decoded declaration. Under (b), scope the stored-window variant to both seam function types so the two directions agree; under (a), say in the docstring that the window is raw at runtime in both directions.

**Know what each branch costs before you pick.** Under (a) a stripped window is still not assignable to a decoded `LastSync`, so ONE conversion survives at the save boundary forever — it is no longer the previous task's TEMPORARY assertion and must not keep claiming to be: re-comment it as permanent by design, saying that the window is raw at runtime and typed decoded because the cursor type is shared. Under (b) that conversion disappears and the cost is a second cursor-shaped type on the seam. Both are defensible; leaving a cast behind a comment that names this task as its remover is not.

**Say which direction the type governs, and pin it.** Segments written before this change still hold `args` and `eventName` forever, and no rewriting migration is performed. So: the stored type governs WRITES from here on; READS tolerate a decoded half and ignore it (the re-decode drops and re-derives it anyway); nothing on disk is rewritten. Adopting a stricter stored type must cost an existing deployment no rebuild. That is a claim about bytes already written, so it needs a test that writes a segment the way the previous version did — decoded halves and all — and then replays it.

Where an implementation reads back what it stored and cannot prove the shape to the compiler (a row from SQL, a record from IndexedDB), it may assert the stored type at that boundary, as those implementations already do today. What must NOT happen is a widening on the seam itself, or a keeper quietly re-typed to a SUPERTYPE that lets a decoded event through. There are TWO such escape hatches in this module, not one: the base event type (the supertype every decoded event extends) and `EmittedLog`, the raw-log alias the server's emission-append path speaks. Either would make a keeper compile while enforcing nothing, and `EmittedLog` is the likelier of the two to be reached for, because the server keeper you are narrowing sits next to code that already uses it. Neither is an acceptable annotation for a seam type or for a keeper's declared shape, and `EmittedLog` is not to be re-pointed at the stored type here: the earlier task states the relation between them in the stored type's docstring, and this task must not contradict it.

The seam is described in the project glossary (`CONTEXT.md`, the **stream / keepStream** entry), and that description is what the next author will build against. It must name the stored-event type once this lands, so the term cannot be re-forked under another name.

## Acceptance criteria

- [ ] The keeper seam's fetcher and saver types are expressed in terms of the stored-event type, and the repo builds, typechecks and tests green with every implementation and test fake moved onto them.
- [ ] Every consumer of what `fetchFrom` returns compiles against the stored shape by having its own parameter WIDENED (the re-decode, and the follower path's emission-mark and already-folded checks), not by an assertion at the call site.
- [ ] The BATCH half of the temporary assertion the previous task left at the indexer's save call site is GONE, and no comment anywhere still promises a narrowing this task owes. If the window's disposition leaves a residual conversion at that boundary, it is a SINGLE one, it is documented as permanent by design with the reason, and it no longer names this task.
- [ ] The `lastSync` window's disposition is decided and STATED in the seam's docstring: either the window stays typed decoded and the docstring says the compile-time refusal covers the batch only (the runtime strip covers the window), or the seam takes a stored-window variant used only by these two function types. `LastSync` itself is not forked or re-meant for the processor, load or wire callers.
- [ ] A keeper implementation that returns or accepts DECODED events no longer compiles, asserted by extending the existing type test with `@ts-expect-error` cases at the seam (not merely at the type alias). Remember that the browser tests pass their keeper through as `never` at several call sites, so those tests passing proves nothing about the compile-time half.
- [ ] READS still tolerate a decoded half: a segment written the way the PREVIOUS version wrote it (events carrying `args`/`eventName`) still replays end to end, its decoded half ignored rather than refused, with no migration and no rebuild. Pin this with a test rather than leaving it to be discovered.
- [ ] `fetchFrom` answers the same membership and order for the same `fromBlock`, with the same raw halves, and the existing kept-stream, follower, promotion, degrading and refold tests pass with only type-level adjustment.
- [ ] `CONTEXT.md`'s **stream / keepStream** glossary entry names the stored-event type as what the seam speaks, so the term is pinned rather than left to be re-invented.
- [ ] No implementation is re-typed to a supertype to make it compile — neither the base event type nor `EmittedLog`, both of which a decoded event satisfies — and the seam is not widened to a union that would re-admit the decoded half. `EmittedLog` keeps its own meaning and its own callers on the emission-append path, unchanged by this task.
- [ ] A changeset records this as a BREAKING `@etherfold/core` change, naming what a third-party keeper implementor has to change.
- [ ] Tests cover the new behaviour, mirroring the repo's existing test style.

## Prompt

> Goal: narrow the kept-stream keeper interface onto the stored-event type, so "the stream stores only what the node said" is enforced by the compiler at the seam rather than by discipline in each keeper. This is the breaking API change the spec exists for.
>
> Vocabulary: the keeper seam is `ExistingStream` (`fetchFrom` / `saveNewEvents` / `clear` / optional `setStreamConfig`) and the two function types it is built from; a STORED EVENT is the raw log plus the reorg verdict, with the decoded half (`args`/`eventName`/`decodeError`) structurally refused; the DECODED half is what some ABI made of the raw bytes and is re-derived on read (ADR-0034); `LastSync` is the cursor plus the unconfirmed reorg window, and it is SHARED with the processor seam.
>
> Where to look, by concept rather than by path: core's public types (the fetcher/saver/seam types), core's stream module (the segmented keeper, the degrading wrapper, the read-only wrapper and its reader type), core's indexer where it calls the seam — all THREE `fetchFrom` call sites (the two load branches and the follow path) and the save call site, including the temporary assertion the previous task left there for you to delete — the browser package's IndexedDB stream keeper, the server package's stored emission stream reader, and the inline keepers and fakes in the core, browser and server tests. Grep for the seam types yourself first: the set above is a starting point, not a contract, and a stale list is exactly the sort of premise this repo asks you to check.
>
> Expect the change to be MECHANICAL but WIDE: it is one edit to two type aliases, plus an annotation sweep across every implementation, plus a widening of the helpers that CONSUME what a keeper returned. The re-decode was widened for you by the earlier task; the follower path's emission-mark and already-folded helpers were not, and they read raw fields only, so widen their parameters rather than asserting at the call site. If some implementation cannot be made to compile without widening the seam or reaching for the base event type, STOP and surface it rather than weakening the seam — the base type is the supertype every decoded event extends, so a keeper typed with it enforces nothing and a decoded event would slip through in silence.
>
> The judgement you own is the `lastSync` window: the batch narrows, but the window's events live inside a cursor type the processor also speaks. Either leave the window decoded and SAY so in the seam's docstring (the runtime strip is what makes it raw, and ONE documented, permanent conversion survives at the save boundary as the price), or give the seam its own stored-window variant used by these two function types alone (no conversion, one more type). Not forking `LastSync` for everybody else is the constraint; leaving the hole unstated, or leaving a cast still commented as temporary, is the failure.
>
> The direction the type governs is the other subtle part, and it is a real acceptance criterion, not a note: WRITES narrow from here on, READS tolerate a decoded half and ignore it, and nothing already on disk is rewritten. Segments written by the previous version keep their decoded halves forever, the re-decode discards them anyway, and a developer upgrading must pay no rebuild. Test it by writing a segment the old way and replaying it.
>
> Constraints: ADR-0034 (the decoded half is a cache re-derived on read; a stream that cannot be re-read is cleared), ADR-0035 (the stream cursor contract), ADR-0044 (one definition of read-only on this seam — the read-only wrapper stays the single one; the fixture has already left the seam). Where a keeper reads its own storage back, an assertion at that boundary is acceptable and is what those keepers already do; a widening at the SEAM is not, and neither is reaching for a supertype that admits a decoded event — the base event type or `EmittedLog` — to make an implementation compile. `CONTEXT.md`'s **stream / keepStream** entry is the glossary the next author reads: it must name the stored-event type when you are done.
>
> Done means: the seam names the stored type, every implementation, fake and consumer moves with it, the previous task's temporary assertion is gone (or, for the window alone, re-documented as permanent), the window's disposition is stated, a type test proves a decoded keeper does not compile, an old-shape segment still replays, the glossary is updated, and `pnpm typecheck`, `pnpm test`, `pnpm build`, `pnpm format:check` and `pnpm changeset status` pass.
>
> FIRST, check this task against current reality (it is a launch snapshot and may have DRIFTED): does it still match the code, the relevant ADRs, and the tasks it depends on? If a dependency landed differently than this task assumes, or an ADR superseded an assumption here, do NOT build on the stale premise — route the task to needs-attention with the discrepancy as the reason.
>
> RECORD non-obvious in-scope decisions you make while building, in a `## Decisions` block at the end of your FINAL REPORT. Do not write the done record, the commit message or the PR body yourself. If a choice meets the ADR gate (hard to reverse, surprising without context, a real trade-off) — "the stored type governs writes, reads tolerate a decoded half, nothing is migrated" is a candidate — also write the durable WHY as an ADR in `docs/adr/` and name it in the block.

## Open questions

Lens 4c fork risk, and a concrete hole in the-stream-seam-takes-only-the-stored-event: its criterion forbids re-typing an implementation to the base event type, but EmittedLog is a SECOND supertype with the identical hole (a decoded event satisfies it), and it sits right beside the server keeper this task narrows. A keeper annotated EmittedLog would compile and enforce nothing, which is exactly the failure the spec minted a new name to prevent. Fixed by the edits: task 3 must state the relation in the new type docstring and leave EmittedLog untouched; task 5 forbids both supertypes.
