## What to build

The vertical tracer bullet of this spec: ONE call in `@etherfold/core` that takes a list of locations, fetches a published seed, installs it by WRITING through the public keeper seam, and returns an outcome as DATA. This task installs an artifact it treats as ALREADY TRUSTED; the admission checks are the next task, and they run BEFORE the first write once they land.

**The loader borrows the state-snapshot path's vocabulary and not its predicates** (ADR-0063): a location list with an optional head fetched first, failover across mirrors where an unreachable one is logged and skipped rather than thrown, and "nothing usable was found" returned as data a host acts on. Two predicates differ, because a stream has two bounds where a snapshot has one: a seed that does not reach back to the block the client asks from is REFUSED rather than merely ranked lower, and "prefer local when local is ahead" becomes "install only into a subtree this install may write", because an installer has no de-duplication and an overlapping batch would duplicate events.

**"Only into an EMPTY subtree" is now the WHOLE rule, and it is DECIDED (ADR-0067).** An earlier draft of this task made reconciling it with a resume its "one real design job". Do not do that work: the reconciliation was attempted and found unsound, and the ADR records why. Nothing can tell a partial install of THIS seed from a stream the client indexed itself -- in this deployment the publisher and the client are the same build, so the stored `context` is identical, and `fetchFrom` does not expose the cursor's `startBlock`. A resume would therefore duplicate events on an overlap, or leave a hole, silently.

So: install only into a subtree with NO cursor record and NO segments. Anything else is refused as data with its own reason, and a caller that wants to replace an existing stream CLEARS it first, deliberately. An interrupted install leaves a prefix that is cleared and redone, which costs the keeper writes alone (about 200 ms of a ~1 s install on a real device).

**The emptiness check must not be the thing that destroys the stream it refuses.** This is the sharpest trap in the task, so treat it as a first-class requirement rather than an implementation detail. `ExistingStream` exposes exactly one read, `fetchFrom`, and that read MUTATES: `createSegmentedStream` clears the entire subtree when the stored cursor's `startBlock` is above the block it was asked from, and it does so before answering. A probe that asks from the capture's own (low) `fromBlock`, which is the number this task otherwise puts in front of you, is exactly the shape that fires it on a client that already holds a stream starting higher. That client would lose its whole cached stream to a call whose only purpose was to decide the seed cannot be installed, which contradicts the refusal contract this task ships. So: probe in a way the clearing branch cannot fire (asking from a block no stored cursor can start above is the obvious way, and there are others), and PROVE it with a test rather than reasoning about it. The keeper's other clearing branches (segments with no cursor record, a gap in the ordinals, a segment that does not parse) are damage repair the keeper owns and are not this task's to defeat.

**Installing is a run of ordinary saves and nothing else.** No new keeper operation, no substrate access, no second copy of the segmentation rules: `createSegmentedStream` already owns the ordinals, the cursor record, the stream's `startBlock` and the hole refusal. Three block rules carry the whole arithmetic, and each is forced by something the keeper or the load path already does:

- the FIRST batch's `lastFromBlock` is the CAPTURE's own `fromBlock`, never its first event's block, because that value becomes the stream's `startBlock` and the load path clears the entire subtree when `startBlock` is above the block asked for;
- each later batch continues the previous one exactly (`lastFromBlock` is the previous `lastToBlock + 1`), because above that the keeper refuses the batch as a hole and below it is an overlap that silently duplicates;
- the LAST batch's `lastToBlock` is the capture's own coverage END, above its last event-bearing block, or the client re-scans every quiet block at the end of the capture, which is exactly the fetch a public node will not serve.

Batches are cut on BLOCK boundaries. The stream CONFIG is set (resolved) before ANY call that addresses a subtree, the emptiness probe included and not merely before the first write, or the probe inspects one subtree while the install writes another. The `context` written is the SEED's own, verbatim: writing the client's own hashes would make the load path's identity check compare the client against itself.

**How the published bytes become an envelope is this task's to own, and it decides the pin.** The artifact is a single COMPACT GZIPPED document, so a fetch has to end in decompressed JSON somehow, and there are two arrangements a host may use and the loader must handle BOTH (ADR-0066 makes the hash transport-invariant, so the arrangement no longer decides anything): the loader inflates the body itself (a `.gz` served as opaque bytes), or the host declares `Content-Encoding: gzip` and the runtime inflates transparently. Handle both, and RECORD how you detected which one you got, because the next task's integrity check hashes whatever this one calls "the bytes it received" and the producer printed its hash over a domain it declared. Read what the producer actually landed and match it: this used to decide the pin under ADR-0065's withdrawn amendment; under ADR-0066 the hash is over the DECOMPRESSED octets, so both arrangements produce the same value and the loader simply has to end up holding those octets either way, and the mismatch would only show up in a real deployment. Cheap and worth it: make at least one fetch case serve the artifact the way a real host would, rather than handing the loader bytes a test constructed.

**Story 11 is an assertion here, not a build, and what it asserts is damage that does NOT happen.** A partial install is a contiguous prefix with an honest cursor, so it is safe to CLEAR; it is not resumed (ADR-0067). Assert that a fresh call against a subtree an interrupted run left behind is REFUSED, through the ordinary entry point, and that the refusal leaves that prefix intact rather than destroying it. A caller that wants to replace it clears it first, deliberately.

**Where the real-artifact case runs.** The producer task commits its reference seed beside the committed 31,332-event capture, in the private conformance-workload package. Two homes are available for the case that installs it and neither needs a new dependency: that package's own suite already imports `@etherfold/core` and owns the capture and its gzip-aware fixture IO, or a core test reads the committed bytes through a repo-root-relative URL, which core tests already do for repo-wide checks. Pick one, say which in `## Decisions`, and do NOT copy the artifact into a second place. Run that heavy case on core's in-memory keeper, not on `fake-indexeddb`: `work/notes/observations/fake-indexeddb-write-cost-grows-quadratically.md` measured the shim's write cost growing as roughly `mutations^2`, so a 31,332-event install under it is not a slow test, it is an unfinishable one. Keep any `fake-indexeddb` case small.

**One guard on shipping order.** Until the admission checks land, this call verifies nothing. Do not advertise it as a safe public entry point in that state: either leave it unexported from the package entry (reachable by core's own tests, with the export landing in the admission task) or export it under a name and a JSDoc that say plainly it checks nothing yet. Say which you chose and why.

## Acceptance criteria

- [ ] One call fetches a seed from a list of locations and installs it, returning an OUTCOME as data (installed, with where it reached, or not installed, with a reason), never throwing for an ordinary condition.
- [ ] Selection is asserted: an unreachable mirror is skipped and a later one is used; a seed that does not reach back to the block the client asks from is refused rather than ranked; an install into a subtree holding a stream that is NOT this seed's own contiguous prefix is refused rather than topped up; no locations at all is its own reason.
- [ ] A NON-EMPTY subtree is refused whatever it holds: a foreign stream, a stream this client indexed itself, and this seed's own half-written prefix are all refused by the same bare emptiness test. There is no discriminator and none is to be invented (ADR-0067).
- [ ] An install refused because the subtree holds a stream it may not write leaves that stream INTACT: its segments and its cursor record read back exactly as before the refusal. Assert it on the case that actually breaks, a stored stream whose `startBlock` is ABOVE the block the installer would ask from, since that is the input on which `fetchFrom` clears the subtree.
- [ ] The ORDERED location list is honoured and failover walks it, INCLUDING to a BUILD-EMBEDDED artifact at a relative, hostless path listed last: with the remote unreachable, the install still succeeds from the embedded one (story 12, the shape the reference deployment ships).
- [ ] An unreadable format is reported as a refusal reason, not propagated as a throw from the parser.
- [ ] How the published gzipped document becomes a parsed envelope is EXPLICIT and asserted: whether the loader inflates the body itself or relies on the transport declaring its encoding, at least one case exercises the arrangement a real host would produce, and the choice is recorded because the next task's content-hash check is computed over exactly those bytes and the producer printed its hash over a domain it declared.
- [ ] The install writes ONLY through the public keeper seam: no substrate access, no new keeper operation, and the segmentation rules are not restated.
- [ ] The three block rules are asserted through observable consequences, not by reading internals: after installing, the stream's start reaches back to the capture's `fromBlock`; the cursor reads the capture's coverage END, above its last event-bearing block; and no batch is declined.
- [ ] The RESOLVED stream config is an ARGUMENT to the install, which sets it on the keeper itself before any subtree-addressing call, the emptiness probe included (ADR-0067). The install is therefore correct whether or not a generation has been constructed, and nothing depends on what a previous caller left configured. The stored context is the SEED's own.
- [ ] A generation folds the installed stream with `eth_chainId` as the ONLY call the node ever sees, enforced by a provider that THROWS on anything else rather than by counting calls afterwards.
- [ ] An install interrupted partway, then called again through the ORDINARY entry point against the subtree it left behind (what a closed tab produces), is REFUSED with the not-empty reason and leaves that prefix byte-for-byte intact. After the caller clears the subtree, the same call installs cleanly and lands on a stream identical to an uninterrupted install of the same artifact.
- [ ] The reference artifact committed by the producer task is installed in at least one case, so the path is exercised on a real published shape and not only on synthetic events; that case runs on an in-memory keeper rather than under `fake-indexeddb`, and reads the committed artifact where the producer put it rather than copying it.
- [ ] The call is not advertised as a verified entry point while it verifies nothing (unexported, or exported with a name and JSDoc that say so), and the choice is recorded.
- [ ] Tests cover the new behaviour, mirroring the repo's existing test style, and reuse the existing fake-chain and in-memory-keeper test world rather than a second one.
- [ ] A changeset records the `@etherfold/core` change.
- [ ] The repo acceptance gate is green.

## Prompt

> Build the loader: fetch a published stream seed from a list of locations and install it through the keeper seam, so a generation folds it with no node in the loop.
>
> FIRST, check this task against current reality (it is a launch snapshot and may have DRIFTED): read the envelope the producer task actually landed and write against THAT, not against this description of it. Read the ADRs named below and confirm they still stand. If the artifact's shape or a decision moved, route to needs-attention rather than building on the stale premise.
>
> The decision that governs the whole task is ADR-0063 ("A published stream seed arrives through its OWN loader, and installs through the KEEPER SEAM"). Read it in full, including "Why the install is the seam, and not a new operation", its three block rules, and "A partial install is a contiguous prefix, not damage". `docs/spikes/pin-the-seam-a-published-stream-arrives-through/install.mjs` is the prototype that PINNED that install and it is worth reading, but it is prototype code answering a question, not the implementation: it copies the strip (now exported), it fetches nothing, and it checks nothing. `work/notes/findings/what-a-published-stream-seed-costs-to-install.md` says the artifact is a single compact document and that the chunked, resumable shape is deliberately NOT built.
>
> Vocabulary (`CONTEXT.md`): the **stream / keepStream (ExistingStream)** seam speaks `StoredLogEvent`; a **segment** is one save at an ORDINAL with the **cursor record** beside it, written in ONE commit; a **hole** is blocks a stream never received behind a cursor claiming them, and it is what the keeper's forward-jump refusal exists to prevent; a stream's **coverage claim** is how far it reaches, above its last event-bearing block; **stream identity** decides WHICH subtree the write lands in, and the address is DERIVED from the client's own source plus the config it was given, never supplied by the seed. `readOnlyStream` and the one-writer rule mean an installer writes through the very `ExistingStream` the generation will be handed.
>
> READ THE KEEPER'S READ PATH BEFORE YOU WRITE THE EMPTINESS CHECK. `ExistingStream` has one read and it mutates: `createSegmentedStream`'s `fetchFrom` clears the whole subtree when the stored cursor starts ABOVE the block it was asked from, and that is the branch a probe asking from the capture's low `fromBlock` walks straight into on a client that already has a stream. Refusing an install must never be what deletes the stream it refused. Choose a probe whose asked-from block cannot trip that branch, and write the test that would have caught it: populate a subtree with an ordinary indexing run starting well above the seed's `fromBlock`, attempt the install, assert the refusal AND that every segment and the cursor are still there unchanged. A refusal test that starts from an EMPTY subtree cannot see this defect, which is why it is called out here.
>
> THE SUBTREE CHECK IS A BARE EMPTINESS TEST, and ADR-0067 is why: no cursor record and no segments, or refuse. Do not reintroduce a resume, and do not invent a discriminator to make one work -- that was tried on paper and is unsound, because a locally-indexed stream and this seed's own prefix are indistinguishable through this seam.
>
> Where to look, by concept: core's stream folder holds `createSegmentedStream` (every rule an installer must NOT restate, and the clearing branches above), the fixture module, and the new seed envelope. The state-snapshot remote path in `@etherfold/processor-entities` is the VOCABULARY to borrow (locations, an optional head, failover, refusal as data) and explicitly not the predicates to copy. Core's own test world already provides a fake chain and an in-memory keeper, and the browser package drives the real IndexedDB keeper under `fake-indexeddb`: use what exists, but keep the 31,332-event artifact OFF `fake-indexeddb` (`work/notes/observations/fake-indexeddb-write-cost-grows-quadratically.md`: the shim's write cost grows as roughly `mutations^2`).
>
> The reference artifact lives where the producer task committed it, beside the committed capture in the private conformance-workload package. Install it from there, either from that package's own suite (it already imports `@etherfold/core`) or from a core test reading the bytes through a repo-root-relative URL, the way core's repo-wide checks already do. Do not commit a second copy.
>
> The load-bearing assertions, as external behaviour: a generation folds the seeded stream with `eth_chainId` as the only node call, enforced by a provider that throws on everything else (copy that technique from the spike, it is better than counting calls afterwards); the cursor after installing reads the capture's coverage end rather than its last event's block; a refused install writes NOTHING and DELETES nothing, asserted by reading the keyspace; and an interrupted install resumes its WRITES from the keeper's own cursor and lands identical to an uninterrupted one.
>
> One thing to be careful about, because it is a foot-gun this repo already documented: a snapshot-seeded generation that ALSO keeps a stream can trip `work/notes/observations/a-follower-can-self-clear-the-writers-stream-through-the-read-only-view.md`. ## Note on the build pin, superseded

The tasking loop raised one blocking issue against every task in this set: ADR-0065 pinned trust to a
build-named content HASH without saying a hash of what. That is settled, but not the way the first
amendment settled it. **ADR-0066 supersedes ADR-0065 on the trust anchor and the byte domain**, and a
builder should read it before either:

- **Trust is the HOST the build NAMES**, not a content hash. A build cannot pin the hash of a ROLLING
  artifact, and rolling is how this is deployed: the reference deployment held one web build against a
  snapshot republished every hour. `bootstrapFromSnapshot`, the path that already ships and works,
  verifies no hash at all.
- **A content hash is OPTIONAL**, for a release-tied immutable artifact, where it is the strongest
  thing available. When present it is SHA-256 over the DECOMPRESSED octets, taken after transfer
  decoding and before `JSON.parse`.
- **There is NO hosting constraint.** The earlier rule forbidding `Content-Encoding: gzip` is
  withdrawn: hashing the decompressed octets is transport-invariant, so it does not matter whether a
  host serves the file opaque or compresses it in transit.
- **Same-origin is not a condition anywhere**, and the refusal it once justified is gone. The app may
  be served from any IPFS gateway while the artifact lives on a known host, so the two origins never
  match by construction.

## Decisions

- **Outcome shape**: `{status:'installed', from, at, reachesBackTo, events, segments}` / `{status:'not-installed', reason}`, mirroring `bootstrapFromSnapshot`'s `BootstrapOutcome` (status + `from`/`at` + a `NotInstalledReason` union) so the two published-artifact paths read the same. `at` is the coverage END and `reachesBackTo` the coverage start, because a stream has two bounds where a snapshot has one and a host renders both. Alternative considered: a bare boolean plus a thrown error (rejected: every refusal here is an ordinary condition). Touches the admission task, which extends `NotInstalledReason` with identity/integrity/coherence/capture-depth reasons and adds no new status.
- **The subtree probe is non-destructive by ASKING FROM `Number.MAX_SAFE_INTEGER`**: no stored cursor's `startBlock` can be above it, so `fetchFrom`'s clear-on-does-not-reach-back branch is unreachable whatever is stored. Alternatives considered: asking from the seed's coverage start (this is the defect, and my test proves it deletes the stream), and adding a presence read to `ExistingStream` (rejected: it widens a seam third parties implement, ADR-0060/ADR-0044, for one caller). The keeper's other clearing branches are damage repair it owns; each leaves an empty subtree, which is what the probe then reports. Touches the admission task, which must inherit this probe rather than adding a second inspection.
- **There is NO rule that tells this seed's own prefix from a stream the install may not top up, and none was invented** (ADR-0067). The test is bare emptiness: no cursor record and no segments. A locally-indexed stream, a foreign stream and this seed's half-written prefix all get the same reason, and the caller clears deliberately.
- **The reference-artifact case lives in a CORE test** (`packages/core/test/streamSeedInstallReference.test.ts`), reading `packages/conformance-workload-stratagems/fixtures/stratagems-alpha1.seed.json.gz` and the capture beside it through a repo-root-relative URL, the way core's repo-wide checks already do. The alternative (the workload package's own suite) was the nicer home but is unreachable while the call is unexported, since that package imports `@etherfold/core`'s built entry. No second copy of the artifact exists. Consequence worth naming: while unexported, nothing can drive the install through the REAL IndexedDB keeper, so the end-to-end assertion that an install lands in the subtree the client reads (address resolution from source + config) is not made here; what is asserted is that the resolved config is set on the keeper before any addressing call. That assertion belongs with the export, in the admission task.
- **The gzipped body is decompressed by the LOADER when it is still gzipped, detected from the BYTES**: if the received body starts `1f 8b`, one gzip layer is peeled with `DecompressionStream('gzip')`; otherwise it is used as-is. Headers were rejected as the discriminator because a runtime that decoded `Content-Encoding: gzip` transparently removes that header from what a script can see, hosts disagree on `Content-Type` for a `.gz`, and a gateway may re-compress an opaque file. **A later integrity check therefore hashes the DECOMPRESSED payload octets** — exactly ADR-0066's domain and exactly what `streamSeedContentHash`/`streamSeedPayloadOf` (which the producer used) take, so the two ends agree. `streamSeedPayloadFrom` is exported from the module (not the package) so a test can pin those octets and the admission task can hash them without a second implementation. Touches the admission task's pin.
- **Default batch size is 1,000 events**, cut on block boundaries. Basis: that is the value the device measurement of this install path used (`docs/spikes/measure-what-a-published-stream-costs-to-install-and-pick-its-shape`, via the spike's `maxEvents: 1000`), so the published ~1 s / 51 MB figures describe the shipped default rather than an untested one. It is an option (`maxEventsPerBatch`). The finding's 4,000–8,000 recommendation is about DOWNLOAD chunks, not saves, and is deliberately not borrowed.
- **The call is NOT exported from the package entry**, and its JSDoc opens with "THIS CALL VERIFIES NOTHING YET". Chosen over exporting it under a hedged name because the admission task exports it under this name, so an interim public name would be a rename plus a deprecation for one task's duration; and because "unexported" is the version of the guard that cannot be missed by a consumer who does not read JSDoc. Touches the admission task (export + trust-contract JSDoc land there).
- **A caller states the reach-back block with `reachBackTo`, defaulting to the source's own earliest `startBlock`** (`defaultFromBlockOf`), which is precisely the block a fresh generation's `load()` asks from — so the ordinary caller states nothing and the default cannot disagree with the load path. Explicit override exists for a client that will ask from elsewhere. This is a user-visible default, hence recorded.
- **A DECLINED batch mid-install THROWS rather than returning a refusal.** Every refusal reason means "nothing was written"; a decline mid-install leaves a prefix, so folding it into the same vocabulary would break that invariant. It can only happen if another writer touched a subtree this call found empty, which the one-writer rule forbids, so it is not an ordinary condition. The prefix left behind is a contiguous stream with an honest cursor and is refused (and cleared) by the next call like any other. Touches the admission task's reason list: no `declined` reason exists.
- **Locations are plain strings, with no `head` sibling**, unlike `SnapshotLocation`. A head exists in the snapshot path to RANK mirrors before downloading; ADR-0066 makes ORDER the selection here, so there is nothing to rank, and no head/manifest ARTIFACT exists to fetch (the seed is published as one document). Adding a `StreamSeedHead` type would be new vocabulary for a document nothing emits. A string is also what makes a relative, hostless build-embedded path expressible.
- **`latestBlock` written into the cursor is the seed's `chainHeadAtCapture`** — the envelope's only observed-tip field, and `latestBlock` is defined as the observed tip rather than progress through it. Recorded because the wrong choice is silent: `latestBlock: 0` sends `getFromBlock` back to the source's start block on the next load, which is the full re-scan the seed exists to avoid.
- **`CONTEXT.md`'s seeding entry was corrected on touch**: it described a partial install as "a resumable contiguous prefix (ADR-0063)" and did not mention ADR-0067, so the glossary asserted the opposite of what this task ships. I rewrote that clause to the empty-subtree rule, named the module and its unexported state, and added the probe's reason. No other glossary text changed.
