## What to build

The correctness cliff ADR-0084 exists to remove, now that the fact it needs is durable.

> **RE-SCOPED 2026-09-16, after a measured build STOPPED on this task.** The first launch of this task said the only things stopping a successor registered at `open` from being promoted were the `opened` gate and the in-memory candidate set, which is what ADR-0084's third symptom says. An agent implemented exactly that narrowing, measured it, and the pointer still never moved. There are THREE parts, not one, and all three are in scope here because none of the others is sufficient alone. The measurement and the reasoning are in `work/notes/observations/the-promotion-trigger-cannot-be-evaluated-with-no-held-incumbent.md`, which is READ-FIRST for this task. ANSWERED and cleared 2026-09-17; the decisions are in `work/questions/task-promotion-arms-from-the-slot-so-a-restart-can-finish-an-upgrade.md`.

A generation registered at `open` can never be promoted. Not late: never. `open()` adds the fold the host was built with and only THEN sets `opened`; `add()` ends in `applyPolicyTo`, whose first line returns while `!opened`; and `settlePromotion` returns immediately on an empty candidate set. So a developer who restarts with a changed processor gets a successor that catches up and sits there for ever, with nothing reported and no policy value that changes it.

**Part one, the gate.** The gate is RIGHT and must not simply be removed. Its recorded reasoning is that applying the policy at open would let `immediate` promote whatever the host happened to be built with, and let `on-catch-up` undo a revert recorded in a previous session. That second hazard is real: after a revert the pointer sits on an older generation while a newer one is still registered, so arming every non-canonical generation at open would re-promote exactly what an operator deliberately reverted away from. Slots answer it. Arm what `successor` names; never arm what `predecessor` names. The question stops being "how did this fold arrive" and becomes "what is this fold FOR", which is now a durable fact rather than an inference.

**Part two, the trigger cannot be EVALUATED in the restart shape.** `settlePromotion` reads `const current = this.folds.find(fold => sameGeneration(fold.record, canonical))` and returns when there is none. On a redeploy the container holds exactly one fold, the new one, and the old processor's code is not in the build, so a fold for the incumbent is unbuildable by construction. The trigger's target is `cursorOf(current)`, which goes through `fold.processor.load(...)`.

That is an INCONSISTENCY rather than a missing capability, and seeing it that way is what keeps this task small. The comparison does not need to run the incumbent: it needs one number, `lastToBlock`, which is a row read as `store.readCursor('lastSync')` and decoded by `parseStoredCursor`, in a store addressed by `tableNamespace: generationDigestOf(id)` -- derived from the generation IDENTITY, which the registry still has after a restart. Nothing in that is handler logic. The read tier ALREADY resolves a generation's state this way, with no engine at all, and the container's own module JSDoc and `promote`'s docstring both state that rule deliberately. `cursorOf` is the one read that still goes through the processor, which is why it alone breaks on a restart. Make it follow the rule the rest of the runtime already follows.

**Part three, nothing CALLS the settle in the restart shape on `run`.** `settlePromotion` has exactly two callers: `applyPolicyTo` (once, at `add`) and `rebuildMore`. The CLI gates `rebuildMore` on `container.followers().length > 0`, and a restart-shape successor is NOT a follower, because `add` computes `follows` from "do I already hold a fold on this stream" and at `open` the fold list is empty. So the trigger is not merely blocked, it is never reached.

## Acceptance criteria

- [ ] A successor registered at `open` is promoted when it catches up, so restarting with a changed processor finishes the upgrade instead of stalling for ever. Asserted END TO END on a restarted deployment, since a build that satisfied every other criterion here and left this one unreachable is exactly what happened last time.
- [ ] A restart after a deliberate REVERT does NOT re-promote the generation that was reverted away from, under any policy value. This and the criterion above are the pair that makes the narrowing safe, and neither is sufficient alone.
- [ ] `immediate` still does not promote the fold a host was merely built with when that fold is already canonical: a host starting normally does not move its own pointer for no reason.
- [ ] `manual` still WAITS. A successor sitting armed in a slot must not creep forward because the slot exists: the slot says what a generation is FOR, the policy still says WHEN.
- [ ] The cursor of a generation this container holds NO FOLD for can be read, through the same kind of injected seam `dropState` already uses and for the same stated reason (the registry cannot know the namespace convention, so whoever named the tables supplies it). Every host that constructs a registry port supplies it.
- [ ] Reading that cursor NEVER requires the generation's processor, and nothing in this change retains, re-imports or reconstructs past processor code. That is a separate question and is explicitly out of scope here (see the Prompt).
- [ ] A fold added with its OWN source has its cursor read with the pair it ACTUALLY folded under, not with the container's source paired against the fold's config. Folded in from `a-folds-cursor-is-read-with-the-source-it-folded`, which is CANCELLED: it corrects the same function this task rewrites. Note honestly that this fixes nothing observable TODAY, because neither implementation of `load` uses `source` to choose a cursor (`work/notes/observations/the-source-argument-to-load-is-inert-so-the-cursor-defect-is-latent.md`), so it is a contract correction rather than a bug fix and the changeset should say so.
- [ ] An unreadable cursor stays `undefined` and never reads as zero, so "has not loaded" remains distinguishable from "level at block 0" in the comparison.
- [ ] A slotted successor is DRIVEN on `run`, so the settle is actually reached in the restart shape rather than gated out by a follower check that a restart-shape successor cannot satisfy.
- [ ] The three policy values become observable on every path that can hold a successor, not only through the reconfigure endpoint, so the input added by `the-cli-selects-its-promotion-policy` means the same thing however the successor arrived.
- [ ] The in-memory armed-candidate set is DELETED, not left agreeing with the slot: promotion reads the slot.
- [ ] Tests cover the new behaviour, mirroring the repo's existing test style.
- [ ] A changeset accompanies the change (`pnpm changeset`).

## Decisions

**Which hazard each clause of the arming condition rules out, and one that rules out nothing.** The condition is stated positively — `slotHolding(slots, fold.record) === 'successor'` — because `add` always leaves the arriving fold in exactly one slot, so it excludes exactly two things. **`predecessor` is load-bearing and measured**: removing it makes a restart after a revert under `immediate` re-promote what the operator reverted away from, which is ADR-0046's hazard. **`canonical` rules out nothing observable**: I removed it and all seven cases still passed, because `moveCanonicalTo` writes nothing when the target is already what the pointer names, so the "promote whatever the host was built with" hazard is already neutral one layer down. I kept it anyway and said so at the choice site: the alternative (`!== 'predecessor'`) would arm the fold the pointer already names, make the rule depend on a distant no-op for its safety, and produce log lines asserting something false about that generation. This touches nothing else; it is the whole of the `run`/`index`/browser promotion behaviour and is what ADR-0046's amendment now records.

**The cursor-reading seam is on `GenerationRegistryPort`, returns a NUMBER, and is required on the port type.** Alternatives considered: a `ReceivingIndexerOptions.readCursor` beside `port` (smaller blast radius, but it splits one fact — where a generation's state lives — across two injection points, when `dropState` already established the port as its home), and returning the decoded `LastSync` (rejected: the window holds whole decoded blocks, and the comparison needs one number — the same reasoning ADR-0047 gives for not handing the cursor to `/status`). It is **required on the port type** (like `dropState`) so no substrate can silently omit it, and **optional in each factory's options** exactly as `dropState` is. Hosts that supply it: the CLI's `openFolding` (production), the core/server/CLI test hosts that stand a receiving container up. The browser's `openGenerationRegistryOnIndexedDB` takes it **optionally** and supplies nothing today — a tab runs the chain-facing container, whose trigger reads its held engines' cursors, so requiring it there would be a required option nothing consults. That is a deliberate exception to "every host that constructs a registry port supplies it", documented at the option.

**The per-fold identity check moved from the container to the port's contract.** The old `cursorOf` answered `undefined` when the stored cursor named another processor, which mattered because it read through a possibly-shared store. Addressing by identity makes that structurally impossible on every host in this repository (the namespace *is* the pair), so the CLI's implementation does not re-check it; the port's JSDoc states the rule ("a cursor another fold wrote answers `undefined`") so a host that maps several identities to one store still owes it.

**`settlePromotion` now consults the policy itself** (`promotionOnAdd(...) !== 'arm'` returns), because arming is no longer something a container remembers. Behaviour is identical to before under all three values; what changed is that the policy check moved from arming-time to settle-time, which is what keeps `manual` waiting while a successor sits in a slot.

**`run`'s gate was deleted rather than replaced** with a cheaper "is anything promotable" check. Such a check needs a registry read to answer, which is most of what it would save; the unconditional call costs about three registry reads per cycle in a gap the loop already waits, and it matches the prune beside it, which is unconditional for the same reason. It touches `run` only — `an-index-process-advances-the-successor-it-registered` still owns where a rebuild gets its turn against the ingest path on `index`.

**ADR-0046 was amended, ADR-0057 deliberately was not.** ADR-0046 owns the arming rule and two of its statements became false for the receiving container ("`open` arms nothing", "a successor created in a previous session does not auto-promote after a reload"), so both carry amendments naming this task and the chain-facing twin's unchanged behaviour. ADR-0057 needed nothing: its only sentence on this subject points at ADR-0046 for the arming, and its own `everCanonical` bullet was already amended by the slots task; the route it decides is untouched. ADR-0084's front-matter `not yet implemented` came off, as that ADR itself instructed, and its STILL-OPEN block became a LANDED block naming the three parts. `CONTEXT.md`'s "promotion TRIGGER" entry was rewritten, because it stated as domain language that the arming is in memory — now true only of the chain-facing container.

**Test hosts got two small shared seam helpers** (`packages/cli/test/utils/generationState.ts`, `packages/server/test/utils/generationDatabases.ts`) rather than five copies of the same four lines; the server's reads the cursor row with plain SQL, because `@etherfold/state-store-sqlite` is not one of that package's dependencies and adding one for a test double would be the heavier change. `theDeploymentSelectsItsPromotionPolicy.test.ts` was **not** rewritten onto the now-shorter restart path: what it asserts is the reconfigure endpoint, which nothing else covers. It gained a header pointer to the new file instead.
