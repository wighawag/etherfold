## Problem Statement

An operator running several apps that want chain-driven notifications (a public demo of jolly-roger, several games built on template-commit-reveal) must run one `etherfold-triggers` process per app today: `createTriggerService` composes ONE consumer over ONE named indexer with ONE set of definitions, the verifier accepts ONE domain, and the push action pushes under ONE domain. Each app then costs its own process, port, config, database and deployment, while push-notification-server and missiv already serve many apps from one deployment. On top of that, two configs that name the same database (both default to `file:triggers.db`) silently cross their deliveries and subscriptions (`work/notes/observations/two-trigger-services-on-one-database-cross-their-deliveries.md`).

## Solution

One `etherfold-triggers` process hosts several APPS, each declared in the one config file under a short app name, each with today's per-app settings (domain, feed, chain and gate, actions with their tokens, verifier, trigger definitions). Every app's state lives in tables keyed by the app, so all apps can share ONE database (the default) or an app can be given its own, with the same schema either way. Each app runs its own consumer, cursor, gate, outbox and registration API, under `/{app}/...`; a failure in one app holds only that app. No deployment of the trigger service holds live data (maintainer, 2026-11-26), so this is a clean 0.x break: one config shape, one route layout, no migration.

## User Stories

1. As an operator, I want to declare several apps in one config file, so that one process and one deployment serve my demo and my games.
2. As an operator, I want each app named by a short slug of my choosing (not its domain), so that routes, CLI flags and log lines read cleanly even for a domain like `localhost:5173`.
3. As an operator, I want every app to carry its own domain, feed (`etherfold` URL and indexer), chain and gate, actions and tokens, verifier and trigger definitions, so that apps on different chains, indexers and push domains coexist.
4. As an operator, I want all apps to share one database by default, so that a remote SQL host (Turso, D1) holds one database for the whole family.
5. As an operator, I want to give one app its own database when I choose, so that a noisy or sensitive app can be separated without a different schema.
6. As an operator, I want the schema to be identical whether apps share a database or not, so that moving an app between the two layouts is copying its rows, never a redesign.
7. As an operator, I want two apps that both name an action `push`, a subscription kind `new-greeting` or a rule key `third-greeting:<account>` never to collide, so that app names alone isolate them.
8. As an operator, I want each app's deliveries sent only through that app's own action adapters, so that no app is ever pushed under another app's domain or token.
9. As an app developer, I want my app's registration API at `/{app}/subscriptions` (and `/renew`, `/cancel`, `/list`) on the shared service, with the verifier checking my proof against MY domain and the path I signed including the prefix, so that one service origin serves every app's clients.
10. As an app developer, I want CORS answered for my app's origin on my app's routes only, so that one app's pages cannot call another app's registration API from the browser.
11. As an operator with a single app, I want the same config shape and the same `/{app}/...` routes as a multi-app operator (an `apps` map of one), so that there is one way to configure and call the service and adding a second app changes nothing for the first.
12. As an operator, I want one app's failing render, rule or predicate, or its unreachable feed, to hold only that app's consumer and never another app's, so that one broken game does not silence the demo.
13. As an operator, I want each app's delivery attempts bounded per round, so that one app with a large backlog cannot starve the others' deliveries.
14. As an operator, I want `status`, `resume`, `deliveries`, `requeue` and `journal` to take `--app <name>`, and with no `--app` to report every app with its name, so that I see which app is paused or stalled.
15. As an operator, I want a generation change that pauses one app's consumer to say which app in `status` and in the journal, so that with many apps I know which one waits for my `resume`.
16. As an operator, I want every journal row to name its app, so that one app's rewinds, stalls and dead letters can be read on their own.
17. As an operator, I want to remove an app by deleting it from the config, with its rows left in the database (ADR-0012: never a quiet DELETE), so that removing an app is reversible.
18. As an operator, I want the service to refuse to start when two apps name the same app slug, or when a database already belongs to a consumer the config does not declare, so that a misconfiguration fails loudly instead of crossing data; and I want to name the apps I have retired from a database, so that removing an app or moving it to its own database does not make every later start refuse.
19. As an operator who may later host this on Cloudflare, I want the core to keep running one bounded round per app without owning a timer, so that a Worker or a Durable Object alarm can drive the same core.
20. As an operator, I want two tickers of the same app (two processes on one database, overlapping Cron Triggers) never to work at once, enforced by the service itself, so that a host misconfiguration cannot send every notification twice.
21. As an operator on a metered SQL host, I want an idle round (nothing new on the feed, nothing due) to write nothing, so that several mostly idle apps ticking every few seconds do not spend my write allowance.
22. As an operator driving the service from a scheduler (`etherfold-triggers tick` from cron, or a restart of `run`), I want a finished or stopped ticker to release its lease, so that the next tick or the restarted process works at once instead of waiting out the lease.
23. As an operator, I want every call the service makes to the outside (the feed, the gate, a state read, a delivery) to time out, so that a hung endpoint of one app neither holds that app for ever nor stalls another app.

## Implementation Decisions

- **An app is the unit**, named by an operator-chosen slug (URL-safe), not by its domain. **The app slug IS the consumer name**: the existing `consumer` column of `deliveries`, `consumers.name` and `MatchContext.consumer` are renamed `app` (clean break, no duplicate column), and the `name ?? indexer` default of the nodejs platform goes away (the key of the `apps` map is the name).
- **No new `domain` field.** The domain stays where it is today, inside the operator-built verifier (`delegatedIdentityVerifier({domain})`) and push action (`pushAction({domain})`) of each app. The comment in `identity.ts` that justifies one app per service ("a second app's users would be pushed under the first's domain") is rewritten: the reason now is per app, since each app has its own verifier and actions.
- **Config shape**: the config file's default export is `{database?, api?, intervalMs?, retired?, apps: {[name]: <per-app config>}}`, always; today's flat one-app shape is removed (no live deployments). The per-app config is today's config minus the process-level fields and `name`. A per-app `database` overrides the top-level one. Top-level settings (database, API port and host, interval, retired apps) are the process's; everything ADR-0013 calls operator code (rules, renders, predicates, action adapters) stays per app.
- **Schema keyed by app**: every table carries an `app` column, and every unique index and lookup index leads with it: deliveries unique on `(app, action, key)`, subscriptions unique on `(app, kind, recipient, filter)`, subscription conditions looked up by `(app, kind, arg, value)`, the journal and accepted requests carrying `app`, the `consumers` row keyed by `app`. Every query filters by app, named here because each one would otherwise leak across apps: the due-deliveries scan in the deliverer, the rewind's count and updates, the subscription matcher (unfiltered and filtered lookups), the `subscribe` upsert and its conflict target `(app, kind, recipient, filter)`, the `subscription_conditions` insert-select from `subscriptions`, the per-recipient quota count, `renewAll`, `list`, `cancel` and `find` in the registry, `expire`, the replay check (`accepted_requests` keyed by `(app, key)`), and every CLI command (`status`, `deliveries`, `journal`, and `requeue`, which refuses an id that is not the named app's). This is the decision that makes a shared database and a database per app the same schema.
- **Composition**: one `createTriggerService` per app over the shared (or its own) database, given its app name; the platform composes N of them. The core gains the app key, the lease and the timeouts, and nothing about hosting several apps; the multi-app loops, routing and the guard are the platform's.
- **Rounds: one loop per app, concurrently.** The Node platform runs each app's own `run` loop (the core's existing loop), all in the one process, so one app's slow round never delays another's. Each app's tick is bounded: a maximum number of feed pages and a maximum number of delivery attempts per round.
- **Every outbound call times out.** The feed read, the gate, each `stateReader` query and each action adapter's delivery are given an `AbortSignal` with a per-call timeout (10 s by default, configurable per app, together with the lease duration; see the fence below). A timed-out feed or state read fails the round like a refused one (the page is not committed, the journal records the stall); a timed-out delivery is a retryable outcome, like a `5xx`.
- **Routing**: one HTTP server; app `x`'s registration API is always mounted at `/x/...`, whatever the number of apps, and the verifier checks the FULL path the client signed (the prefix included; Hono's `c.req.path` is the full mounted path).
- **No migration**: the schema change is a breaking 0.x release; an existing database is not upgraded, and `setup` over a database in the old layout refuses with a message saying to start from an empty one.
- **A per-app lease, in the core.**
  - *Columns*: `consumers` gains `lease_owner` (a random id per service instance, `crypto.randomUUID()`, available on Node, Bun and Workers) and `lease_expires` (ms).
  - *Acquire or renew*: one statement, `INSERT INTO consumers (app, ..., lease_owner, lease_expires) VALUES (...) ON CONFLICT (app) DO UPDATE SET lease_owner = excluded.lease_owner, lease_expires = excluded.lease_expires WHERE consumers.lease_owner = excluded.lease_owner OR consumers.lease_expires < ? RETURNING ...`. It creates the row on an app's first tick, and an empty `RETURNING` means another owner holds a live lease: the tick does nothing and reports `not-leased`.
  - *Cadence*: the lease lasts 60 s by default. The renewal writes ONLY `lease_owner` and `lease_expires`, never the cursor, stream, generation or pause, so it can neither undo an operator's `resume` (which rewrites cursor and stream from the CLI) nor move a cursor backwards after a takeover. Between renewals the tick relies on the state read every step already does (`consumers` read per page), which also returns `lease_owner` and `lease_expires`, so checking ownership costs no extra query. Cost: about one write per 30 s per app (about 86k a month per app; under 2% of D1 Paid's included writes for 10 apps; see the finding below).
  - *Fencing, by deadline*: before EACH outbound call (the gate, each feed read, each state read, each delivery attempt) the tick checks the time left on its lease (a clock read). If less than half the lease remains it renews first (any fence check may renew, not only the tick's start); if less than the FENCE MARGIN remains after that, it stops the round. The margin is the app's per-call timeout plus a commit allowance (5 s) and a clock-skew allowance (5 s), so with the defaults 20 s of the 60 s lease, and every single call started inside the lease ends inside it. The service refuses to start an app whose margin is not under half its lease (with the 60 s default, a per-call timeout of 20 s or more), naming both values.
  - *Fencing, by the commit*: every statement of a step's commit batch (the delivery inserts, the rewind's updates, the state write, the journal rows) is guarded by the lease: the inserts become `INSERT ... SELECT ... WHERE EXISTS (SELECT 1 FROM consumers WHERE app = ? AND lease_owner = ? AND lease_expires > ?)` and the updates carry the same predicate. A stale holder's commit therefore changes nothing even if every timeout and margin failed, which is what stops it from overwriting the new holder's cursor or re-inserting a delivery into a key a rewind just freed. Every settle (delivered, retry, dead, expired, and the no-adapter dead letter) is also guarded, so a stale attempt's outcome does not overwrite the new holder's.
  - *What the lease covers*: the whole tick. A `not-leased` tick runs neither `expire`, nor the feed, nor `deliverDue`. Deliberately LEASE-FREE, because they are row-level actions of a person rather than of a ticker, and each is already safe beside one: the registration API's writes (subscribe, renew, cancel, the replay record), and the operator's CLI `resume` and `requeue`. `resume` acts only on a paused consumer, whose ticks do nothing, and `requeue` only flips a dead row back to pending.
  - *Release*: a ticker releases its lease (`UPDATE consumers SET lease_expires = 0 WHERE app = ? AND lease_owner = ?`) when a one-shot `tick` command ends and when `run` stops gracefully, so a cron-driven `tick` or a restart proceeds at once. A crashed ticker's lease lapses within 60 s.
  - *Clock assumption*: expiry is written from the ticker's clock, and tickers of one app are assumed to agree within the skew allowance (NTP-synchronised hosts; on Workers the platform clock).
  - Delivery stays at-least-once (adapters must honour the idempotency key, as now); the lease removes the systematic double delivery of concurrent tickers, not the rare retry after a crash.
- **An idle round writes nothing.** Today every advanced step rewrites the `consumers` row even when the page was empty, about 518k writes a month per app at the 5 s default interval. The state write is skipped when the page carried no entries, inserted no delivery, and changed neither stream, generation nor pause. On an empty page the position does not move; only the cursor's `since` mark (the stream's high-water mark) does, so keeping the older cursor is deliberate and safe (an older mark only makes the fork check conservative). The newest cursor is written by the next GUARDED step write (a non-empty page, a rewind, a pause), never by the lease renewal.
- **Guard, in the platform**: at start, for each database, the platform reads its `consumers` rows and refuses when one names an app that the config neither declares for that database nor lists in `retired`, naming the app and the database. `retired` is how an operator removes an app (story 17) or moves one to its own database (story 6): the old rows stay, the guard lets them be.
- **Cost basis**: per-database cost is negligible on Turso and on D1 Paid (`work/notes/findings/a-database-costs-almost-nothing-on-d1-and-turso.md`); the shared default is chosen for fewer moving parts and static-binding simplicity on D1, not for price.
- **ADR**: a new ADR-0101, "a trigger service hosts several apps in one app-keyed schema, each app behind its own lease", recording the app-keyed schema, the core lease and the shared-database default; ADR-0005 gains a "complemented by ADR-0101" note (each consumer owns its state, which may now be an app-keyed slice of a shared database rather than a whole database). The platform README's "one service serves one app" is rewritten.

## Testing Decisions

- External behaviour through the core's existing seam (an in-process `@etherfold/server` folding a real processor, read over `fetch`, as the current tests do): two apps over one database, each following its own indexer, with colliding action names, kind names and rule keys, each receiving exactly its own deliveries through its own adapters.
- Isolation: one app whose predicate always throws stalls (journalled under its name) while the other app's deliveries proceed in the same rounds.
- Registration: a proof for app A's domain is refused on `/b/subscriptions`; a request signed for `/a/subscriptions` succeeds there and is refused if replayed; CORS answers only the app's own origin.
- Single app: an `apps` map of one serves `/{name}/subscriptions` and the existing behaviour suite passes once moved to that layout.
- Lease: two services over one database for the same app, ticked concurrently, deliver each due row once, and the one without the lease reports `not-leased`; the first tick of an app with no `consumers` row creates it and holds the lease; after the holder stops renewing, the other takes over once the lease lapses; a tick whose remaining lease is under the fence margin stops before the next page or delivery attempt.
- Stale holder: a holder whose lease has lapsed and been taken commits a page (with deliveries, a rewind, a cursor) and the database is unchanged; its settle of a delivery is also a no-op.
- Release: two `etherfold-triggers tick` commands in a row both deliver (the first released its lease); a gracefully stopped `run` lets a new `run` tick at once.
- Timeouts: an app whose feed, gate or state read HANGS (accepts the connection, never answers) stalls only itself, journalled as a stall after the timeout, while another app's deliveries proceed; a delivery that hangs is retried after the timeout; an app configured with a per-call timeout whose margin is not under half its lease is refused at start.
- Fence: a page making several state reads renews the lease mid-page when it falls under half, and stops before a call when under the margin; an operator `resume` (new stream cursor) is not undone by the ticker's next lease renewal.
- CLI by app: `status`, `deliveries`, `journal` with `--app a` show only app a, without `--app` they show every app labelled by name, and `requeue --app a <id of an app b row>` is refused.
- Per-app registry queries: app A's `subscribe` (same kind name, recipient and filter as app B), `renew`, `list`, `cancel` and quota never see or touch app B's subscriptions of the same recipient, and the same signed-request key accepted for app A does not count as a replay for app B.
- Idle writes: an idle tick on an app holding a fresh lease issues no write (counted at the `remote-sql` seam).
- Guard: a database written by app `a` is refused by a config that declares only `b`, and accepted when `a` is listed in `retired`.
- Bounded rounds: an app with more due deliveries than its per-round bound leaves the rest for the next round.
- Idle cursor: an empty page whose cursor moved is not written, and the next read from the older cursor returns no entries.

## Out of Scope

- **Uploaded trigger bundles** (definitions arriving like `etherfold upload`, hot-loaded without a restart). Deferred and kept in `work/notes/ideas/a-trigger-service-that-serves-several-apps.md`: it needs ADR-0094's one-source-of-truth split, a `(context) => definitions` interface so bundles carry no secrets or URLs, and it is impossible inside a Worker isolate (`work/notes/findings/a-worker-cannot-instantiate-a-processor-from-bytes.md`).
- **A Cloudflare platform for the trigger service** (a `platforms/cf-worker-triggers` on D1, driven by a Cron Trigger, or a Durable Object alarm where sub-minute latency matters). Its own spec; this one only keeps the core drivable that way (story 19).
- **Third-party tenants**: every app here belongs to the one operator who runs the service; running mutually untrusted apps' code in one process needs a sandbox and is not attempted.
- **The feed side**: whether the apps' indexers live on one multi-indexer `etherfold node` or on one `etherfold run` each (`work/notes/ideas/the-combined-run-holds-several-named-indexers.md`). Each app names its feed URL and indexer, whatever serves them.
- **Per-app rate limits of ADR-0011 (digests, the delivery-rate bound)**: still unbuilt (`what-the-first-build-left-out.md`); when built they are per app by construction.

## Further Notes

- The core is already platform-neutral (Hono, viem, `remote-sql`, `fetch`; no Node API), and `TriggerService.tick()` is already one round callable by any host, so a Cloudflare host is mostly a new platform package: a `scheduled` or alarm handler calling `tick()` per app, a fetch handler mounting the registration APIs, D1 through `remote-sql`, and a config that is a function of the Worker's `env` (secrets are bindings, not `process.env`). The constraints it must respect are in the finding above: Workers Paid, 1,000 D1 queries and 10,000 subrequests per invocation (each feed page, gate read, state read and delivery is at least one), bounded rounds, and no overlapping ticks of one app, which the core's lease now enforces (a Cron Trigger suffices; a Durable Object alarm is only for sub-minute latency).
- A synchronous infinite loop in one app's render or predicate still freezes the whole process; acceptable for one operator's own apps, and the README should say so.
