## Q1

**'task:promotion-arms-from-the-slot-so-a-restart-can-finish-an-upgrade' was bounced — how should we proceed?**

> The task's load-bearing premise is FALSE against the code, and I measured it rather than argued it. The premise is that the ONLY things stopping a successor registered at `open` from being promoted are the `opened` gate and the in-memory candidate set ("`add()` ends in `applyPolicyTo`, whose first line returns while `!opened`; and `settlePromotion` returns immediately on an empty candidate set"). ADR-0084's third symptom says the same, quoting only the FIRST line of `settlePromotion`. There are two further blockers, and both sit squarely inside acceptance criterion 1 ("a successor registered at `open` is promoted when it catches up") and the `on-catch-up` third of criterion 4.
>
> WHAT I MEASURED. I narrowed the gate exactly as the task specifies (arm iff `slotHolding(slots, fold.record) === 'successor'`), made `settlePromotion` read the slot instead of `candidates`, and stood a `run` deployment up the way `packages/cli/test/theDeploymentSelectsItsPromotionPolicy.test.ts` does, stopped it, and re-ran it over the SAME libSQL handle with a changed processor module. The arming half works perfectly: `applyPolicyTo` sees `slot = canonical` on an unchanged restart (not armed, criterion 3 holds) and `slot = successor` on a changed-processor restart (armed). The pointer still never moves. After 3 seconds of drive cycles the successor is at `lastToBlock: 1000050` (the tip) and `canonical` is still the V1 generation, with `settlePromotion` reporting `BLOCKED: no held fold for the canonical generation` on every cycle. I then reverted every experimental edit and deleted the probe; the working tree is clean and `git diff` is empty.
>
> BLOCKER 1 - THE TRIGGER CANNOT BE EVALUATED IN THE RESTART SHAPE. `packages/core/src/receivingContainer.ts:1266`, `if (!current) return;` in `settlePromotion`, where `current` is the HELD FOLD for the canonical generation. On a redeploy the container holds exactly ONE fold, the new one: `openReceivingIndexer` takes a single `generation` option, and the old processor's code is gone from the build, so a fold for the incumbent is unbuildable BY CONSTRUCTION (this is the same fact `promote`'s own JSDoc leans on - "It does NOT require this container to hold a FOLD for the target"). The trigger's target is `cursorOf(current)`, which is `current.processor.load(...)` - the incumbent's persisted cursor, which lives in the incumbent's OWN table namespace (`VersionedStateStore` is constructed with `tableNamespace: generationDigestOf(id)`; `readCursorStatement` is per-`names`). The container has no way to build a store for a generation it holds no fold for; only the HOST knows that convention, which is why `dropState` is INJECTED (`packages/cli/src/folding.ts:481`). So making criterion 1 true requires either a new injected port ("read the cursor of a generation I hold no fold for", the symmetric sibling of `dropState`, reaching core + cli + server + browser) or a SECOND trigger rule for the no-held-incumbent case (e.g. "the successor has reached the chain tip it just observed", which is sound because nothing can be ahead of the tip, but is a different rule). Either is a DESIGN decision, not a small factual gap: it changes the one safety property `on-catch-up` exists for (never move the pointer onto a fold that is behind), it contradicts ADR-0046 and `CONTEXT.md`'s glossary as written ("the trigger is the successor reaching the cursor the CANONICAL generation has, compared LIVE"), and `readyForPromotion` / `PromotionView` in `packages/core/src/generation/promotion.ts` are SHARED with the chain-facing twin, so deciding it here pre-empts `the-chain-facing-container-holds-its-generations-in-slots`, which is also in `work/tasks/ready/`. Nothing in ADR-0084, the spec or this task mentions it, and I found no ADR, task or note that owns it.
>
> BLOCKER 2 - NOTHING CALLS `settlePromotion` IN THE RESTART SHAPE ON `run`. `settlePromotion` has exactly two callers: `applyPolicyTo` (once, at `add`, when the successor has folded nothing) and `rebuildMore`. `packages/cli/src/index.ts:440` gates `rebuildMore` on `container.followers().length > 0`, and the restart-shape successor is NOT a follower: `add` computes `follows` from "do I already hold a fold on this stream", and at `open` the fold list is empty, so it is `false` (measured: `follows: false`). So on a restarted `run` the trigger is not merely blocked, it is never reached. Removing that gate is cheap, but WHERE the settle gets its turn against the ingest path is the same decision `an-index-process-advances-the-successor-it-registered` is explicitly told to make ("Decide explicitly where the rebuild gets its turn... say what you chose and what it costs under load"), so deciding it here silently forks that task's answer.
>
> WHAT IS STILL DELIVERABLE UNCHANGED, if you want the task re-scoped rather than redesigned: criteria 2 (a restart after a revert re-promotes nothing, under every policy value - `create` rule 2 leaves a generation `predecessor` names where it is, so it is never armed), 3 (`immediate` does not move a host's own canonical fold - measured), 5 (delete `candidates`, `opened`, and the now-unused `fold` parameter of `movePointer`), and the `immediate` and `manual` thirds of 4. Only `on-catch-up` across a restart needs the two blockers above.
>
> SUGGESTED RE-SCOPE. (a) Re-title THIS task to what the slot actually buys and cut criterion 1 down to "a successor registered at `open` is ARMED, and `immediate` promotes it at open while `manual` waits" - that is honest, testable at the named seam, and is a clean prerequisite. (b) Raise a NEW task for "the promotion trigger works when this container holds no fold for the canonical generation", carrying the choice between an injected per-generation cursor read and a tip-based rule, and amending ADR-0046 + `CONTEXT.md`'s trigger sentence; it must land before `an-index-process-advances-the-successor-it-registered`, whose criterion "a restarted `index` with a changed processor FINISHES the upgrade" has the same dependency. (c) Fold the `followers().length > 0` gate decision into whichever of those owns the drive loop.
>
> ONE MORE THING WORTH AN OBSERVATION NOTE (noticed while measuring, NOT fixed, and left out of the tree so this stop leaves it clean): after a restart with a changed processor the deployment APPENDS NOTHING TO ITS STORED EMISSION STREAM. The only held fold reports `writes: false` (measured), because `writerOf` names the oldest surviving generation on the stream - the incumbent - and no fold for the incumbent is held, so `appendEmissions` is handed to nobody while the successor happily consumes the wire. `reconcileWriters` does not fix it: `shouldWrite` is `false` and already matches `fold.writesStream`, so it is a no-op. `packages/core/src/receivingContainer.ts`, `add` / `reconcileWriters`, reproduced by the probe described above.
