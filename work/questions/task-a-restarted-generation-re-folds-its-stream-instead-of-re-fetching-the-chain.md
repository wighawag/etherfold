## Q1

**'task:a-restarted-generation-re-folds-its-stream-instead-of-re-fetching-the-chain' was bounced — how should we proceed?**

> The task's central premise is false against the current tree, and it is ADR-0087's own sentence that is false. This was BUILT and MEASURED, not inferred; the patch and the numbers are in `docs/spikes/a-restarted-generation-re-folds-its-stream-instead-of-re-fetching-the-chain/`.
>
> **1. FALSE PREMISE: "handed the wire by machinery that already exists".** ADR-0087's considered-options entry for this exact task says the restarted follower "re-folds the stored stream, lands on the coverage, and is handed the wire by machinery that already exists". It is not. `ReceivingIndexer.reconcileWriters` (`packages/core/src/receivingContainer.ts`) hands the wire only to the fold `writerOf` NAMES. A restart registers the successor BESIDE the incumbent, so `writerOf` still names the incumbent, which is registered and NOT HELD; `shouldWrite` is already `false`, equals `fold.writesStream`, and the loop `continue`s. That is the identical no-op ADR-0087 identifies as the defect three paragraphs earlier, in "The defect that forced it" ("`reconcileWriters` does not repair it: `shouldWrite` is already `false` and matches, so it is a no-op rather than a hand-over"). The document credits as machinery the very no-op it condemns.
>
> **2. MEASURED CONSEQUENCE: a redeploy stops indexing the chain for ever.** With the fix applied, a `run` stood up over a real libSQL handle, stopped, and re-run with an edited bundle asks the node for exactly `["eth_chainId"]` across the whole run: zero `eth_getLogs`, zero `eth_blockNumber`. A follower has no receiver, so `liveIngestions()` is empty and the fetch side has nowhere to push. The deployment re-folds to the previous tip, is promoted by `on-catch-up`, serves reads and looks healthy. Today's behaviour is expensive (re-fetch the whole chain) but LIVE; after this change it is cheap and DEAD, which is the silent-failure class this repo treats as the worst outcome and is the same "no refusal, no warning, and the state looks fine" shape ADR-0087 exists to close. On `build` it is worse than a stall: `driveCycles` (`packages/cli/src/index.ts`) classifies `NoLiveReceiverError` as `nothingToFeed` and re-throws it BEFORE the exit `rebuildMore`, so a re-run `build` with changed bytes FAILS OUTRIGHT without folding anything, breaking three cases in `packages/cli/test/aRerunBuildSettlesItsPointer.test.ts` that the blocker landed yesterday.
>
> **3. THE `blockedBy` NAMES THE WRONG DEPENDENCY.** It names `run-and-build-drive-the-folds-they-hold-rather-than-one-captured-receiver`, and the launch measurement it quotes ("17 of them on `the opening fold of this ReceivingIndexer has no receiver`") identified the SYMPTOM (a getter throwing) rather than the cause (nothing FETCHES). That task made the assembly tolerant of a follower opening fold; it did not give a follower-only process a way to fetch, and it could not — the fetch is still a side effect of a fold's indexing loop. Only `whoever-fetches-a-stream-writes-it-and-the-stream-outlives-every-fold` moves the fetch and the append off the generation, which is precisely what makes a deployment holding nothing but a follower go on fetching. ADR-0087 says so itself under Consequences: "The append is driven by the FETCH, not by a fold's indexing loop... This is the real work of the proposal".
>
> **SUGGESTED RE-SCOPE.** Re-order the family: land `whoever-fetches-a-stream-writes-it-and-the-stream-outlives-every-fold` FIRST, then this task, whose core change is small, correct and already written (apply the patch in the spike folder). Amend ADR-0087's considered-options entry for this option to delete "and is handed the wire by machinery that already exists" and say instead that the narrow fix REQUIRES the fetch to have moved off the generation, so the ordering claim ("can land first") is reversed. Two other findings belong in the same amendment, both measured:
>
> (a) `streamCanReceive`'s "unknown position" is TWO facts and only one may refuse. `!this.lastSync` refusing is inert (`promiseToIndex` loads before it fetches). `streamLastToBlock === undefined` must STAY permissive: it is the documented absence of a stream, not an unknown position (`forgetStoredStream`: "there is no stream on disk any more, so nothing constrains the next write"). Refusing there declines the first save of every fresh deployment, and it also destroys the case `packages/core/test/streamSeedInstall.test.ts` protects by name (`locallyIndexedAbove`) — a stream lost while its STATE survived is re-opened at the state's resume point and the new subtree RECORDS that resume point as its own `startBlock`, so a read from below it is answered `does-not-reach-back` rather than served. That is an honest partial stream, not a hole; refusing left it never written and that suite red in two cases. Furthermore the duplicate the ADR attributes to this method was never on this path: the hand-over it measured writes through `StreamBuilder.storeStream` over an append-only `EmissionAppender`, which reads nothing back and has NO hole guard of any kind, while `streamCanReceive` is `IndexerGeneration`'s over an `ExistingStream` that `load` always reads first. The hazard is real and it is in the other method; guarding it belongs with whoever moves the write duty.
>
> (b) It is ELEVEN tests encoding today's behaviour, not five. The extra six: `packages/cli/test/aChangedContextCreatesASuccessor.test.ts` (6 — its hand-rolled container supplies `appendEmissions` and no `replay`, and its `transferEvent` fixture writes `topics: []`, which no replay can `reparse`, so re-scoping it needs a real-topic fixture as well as the read end), `packages/cli/test/aRerunBuildSettlesItsPointer.test.ts` (3), `packages/cli/test/aSuccessorLandsInADurableSlot.test.ts` (1, `maxStreams` reached where it was not), `packages/cli/test/anIndexProcessAdvancesItsSuccessor.test.ts` (1, the case that disables the rebuild schedule and relies on the wire to advance a restarted successor).
