## Q1

**'task:publish-writes-the-stream-seed-when-asked' was bounced — how should we proceed?**

> Premise drift: the task (and ADR-0095 / spec `a-build-publishes-what-a-browser-app-starts-from`, stories 3 and 11) assumes a stream seed can be produced from a build database alone, from the stored stream read back through `storedEmissionReplaySource` plus core's envelope, strip, digest and content hash. That is false for the seed's IDENTITY. `StreamSeed.context.source` must carry the per-event source hash entries (`sourceHashesOf(source)`, including `streamHash`), because `installStreamSeed` recomputes the digest from them (`streamDigestOfSourceHashes`) and the tab's load compares them (`streamMatches`). The database never stores them: `_stream_coverage.source` holds the 32-bit whole-source WIRE context (`wireContextOf`, written by `StreamWriter.storeStream` and `StreamBuilder.storeStream`), and the canonical generation's cursor carries the same wire context. Verified on a real `build` of the CLI fixture: the digest from either stored `source` is `cf6fc503...` while the generation's stream is `ee5edb4d...`, so every produced seed would be refused by every tab. The source cannot be rebuilt inside `publish` either: it needs a chain id (`resolveSource` calls `eth_chainId`) or `--deployments`, and `publish` refuses `--node-url` and `--deployments` by design (the command table from `publish-writes-a-state-snapshot-a-browser-app-starts-from`). Where the seed's source identity comes from is a load-bearing, hard-to-reverse design decision a human should make. Candidate re-scopes: (a) persist the source hash entries at fold time (for example in the coverage claim or the generation registry row beside the bundle, ADR-0092), a schema and ADR change touching core's `StreamWriter`/`StreamBuilder` and the server schema, as a new blocking task; (b) let `publish --seed` take the source (accept `--deployments`/`INDEXING_SOURCE`, or a chain id for the bundle's `contractsDataPerChain`) and check `streamDigestOf(source, config) === generation.stream` before writing, which amends the `publish` command table; (c) have the library take a `sourceOf` callback like `declarationsOf`, which moves the question to the CLI and still needs (a) or (b) there. Separately, a stored stream with an uncompacted reorg is refused by the install as `incoherent` (two block hashes at one height, see work/notes/observations/a-stored-stream-seed-with-a-reorg-is-refused-as-incoherent.md), so the producer must drop matched apply/retract pairs or the core rule must change; the re-scoped task should decide which. A draft of everything else (server producer, `--seed` flag, stream-keyed index entry, printed pin, and tests covering chunked reads, pair dropping and index merging) is saved outside the repo at /tmp/etherfold-publish-seed/wip.patch.
